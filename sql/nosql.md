# SQL vs NoSQL

Коротко: **SQL** — про строгую структуру, транзакции и целостность данных.
**NoSQL** — про гибкость схемы, горизонтальное масштабирование и скорость.

## Типы NoSQL баз

| Тип | Примеры | Модель данных | Типовое применение |
|---|---|---|---|
| **Key-Value** | Redis, DynamoDB | ключ → значение | кеш, сессии, счётчики, rate limiting |
| **Document** | MongoDB | JSON-документы | сущности с гибкой/вложенной схемой, каталоги |
| **Column-family** | Cassandra | широкие строки по ключу | time series, журналы, огромные объёмы записи |
| **Graph** | Neo4j | вершины и рёбра | связи: соцграфы, рекомендации, антифрод |

## Масштабирование

| | SQL | NoSQL |
|---|---|---|
| Основной путь | Вертикальное (сервер побольше) | Горизонтальное из коробки |
| Репликация/шардирование | Возможны, но сложны в эксплуатации | Встроены в архитектуру, шардинг «легко» |
| Консистентность | Сильная (ACID) | Чаще eventual (настраивается: кворумы, `w=majority`) |
| Когда брать | Деньги, инварианты, сложные JOIN-запросы | High load, гибкая схема, простые паттерны доступа по ключу |

## Что проговорить на собеседовании

- Выбор не «религиозный», а от данных и паттернов доступа: транзакции и
  связность → SQL; масштаб и доступ по ключу → NoSQL; часто — оба сразу
  (PostgreSQL как источник истины + Redis как кеш).
- «NoSQL быстрее» — не сама по себе: скорость получается из отказа от
  JOIN'ов, транзакций и строгой консистентности.
- CAP-теорема: при сетевом разрыве выбираешь между консистентностью и
  доступностью; у многих NoSQL это настраивается на уровне запроса.
- В PostgreSQL есть `JSONB` + GIN-индексы — «документная» гибкость внутри
  реляционной БД часто закрывает потребность в отдельной Mongo.
