# Шардирование и репликация

Два независимых механизма масштабирования БД, которые на собеседованиях
любят путать. Разбор с примерами: <https://highload.tech/sharding-i-replikatsiya/>

## Главное различие

| | Репликация | Шардирование |
|---|---|---|
| Что делает | **Копирует** одни и те же данные на несколько серверов | **Разрезает** данные на части, каждая живёт на своём сервере |
| Масштабирует | Чтение (и отказоустойчивость) | Запись и объём данных |
| Каждый узел хранит | Всё | Свою часть |

Обычно применяются вместе: данные шардируются, каждый шард — со своими
репликами.

## Репликация

- **Primary → replica**: пишем в primary, читаем с реплик.
- Синхронная — коммит ждёт подтверждения реплики (надёжно, медленнее);
  асинхронная — не ждёт (быстро, но есть **replication lag**: реплика
  может отдать устаревшие данные).
- Классический вопрос-ловушка: «прочитал сразу после записи и не увидел
  свою запись» — это чтение с отстающей реплики (read-your-writes
  решается чтением с primary или sticky-сессиями).

## Алгоритмы шардирования

| Алгоритм | Как | Плюсы / минусы |
|---|---|---|
| **Range-based** | id 1–1M → shard 1, id 1M–2M → shard 2 | просты range-запросы; риск горячих шардов (новые записи бьют в последний) |
| **Hash-based** | `shard = hash(user_id) % N` — самый популярный | ровное распределение; range-запросы по ключу невозможны, решардинг при смене N болезненный (лечится consistent hashing) |

## Что проговорить на собеседовании

- Ключ шардирования выбирается под основной паттерн доступа: почти все
  запросы должны попадать в **один** шард (иначе scatter-gather по всем).
- Кросс-шардовые JOIN и транзакции — боль: либо денормализация, либо
  сага/двухфазный коммит, либо пересмотр ключа.
- Решардинг (добавление узлов) при `hash % N` требует перекладки данных —
  поэтому берут consistent hashing или виртуальные шарды.
