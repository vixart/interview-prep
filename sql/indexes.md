# SQL: индексы

Как устроен поиск в БД, какие бывают индексы и — подробно — как работают
составные индексы.

Диалект по умолчанию **PostgreSQL**; заметные отличия MySQL 8 (InnoDB) и
SQL Server отмечены. Общая теория — [`theory.md`](theory.md), практика —
[`questions.md`](questions.md).

**Схема примеров** (та же, что в остальных файлах):

```
employees (id, name, salary, dept_id, hired_at, manager_id)
orders    (id, customer_id, product_id, amount, ordered_at, status)
```

## 1. Как БД ищет строки

### Без индекса — Seq Scan

```sql
SELECT * FROM employees WHERE dept_id = 20;
```

БД читает **все** страницы таблицы с диска и проверяет условие для каждой
строки. Сложность O(N): миллион строк — миллион проверок.

Это не всегда плохо. Если условию удовлетворяет большая доля таблицы
(грубо, > 5–20%), последовательное чтение выгоднее: диск читает подряд
идущие страницы быстрее, чем прыгает по случайным адресам. Планировщик
это знает и может сознательно проигнорировать индекс.

### С индексом — Index Scan

Индекс — отдельная структура на диске, где значения колонки хранятся
**отсортированными** и рядом с каждым лежит указатель на строку в таблице.

```sql
CREATE INDEX idx_employees_dept ON employees (dept_id);
```

Поиск идёт в два этапа:

1. **Спуск по дереву** — найти в индексе позицию нужного значения.
   O(log N), реально 3–4 обращения к страницам даже на миллионах строк.
2. **Обращение к таблице** (heap fetch) — по указателю прочитать саму
   строку, потому что в индексе лежит только `dept_id`, а нужны все колонки.

Второй этап — часто самое дорогое. Каждая найденная строка = случайный
доступ к своей странице. Поэтому индекс выгоден, когда он отсекает
**мало** строк из многих.

## 2. Устройство B-tree

Индекс по умолчанию везде — B-tree (точнее B+-дерево). Сбалансированное
дерево, где данные лежат только в листьях.

```
                      ┌───────────────┐
        root          │  100  │  500  │        ← корень, 1 страница
                      └───┬───┴───┬───┘
              ┌───────────┘       └───────────┐
        ┌─────▼──────┐                 ┌──────▼─────┐
внутр.  │ 20 │ 60    │                 │ 700 │ 900  │   ← навигация
        └──┬─┴──┬────┘                 └──┬──┴───┬──┘
     ┌─────┘    └────┐                ┌───┘      └────┐
  ┌──▼──┐        ┌───▼──┐          ┌──▼───┐       ┌───▼──┐
  │5,12 │◄──────►│20,45 │◄────────►│700,80│◄─────►│900,95│  ← листья
  └──┬──┘        └───┬──┘          └───┬──┘       └───┬──┘
     ▼               ▼                 ▼              ▼
   строки в таблице (heap): указатели ctid / RID / PK
```

Ключевые свойства:

| Свойство | Следствие |
|---|---|
| Дерево сбалансировано, все листья на одной глубине | время поиска одинаково для любого значения |
| Страница ~8 КБ вмещает сотни ключей (высокий fanout) | глубина 3–4 уровня на миллиардах строк |
| Листья связаны в **двусвязный список** | диапазонный запрос = спуск + линейный проход по листьям |
| Значения в листьях **отсортированы** | индекс умеет отдавать данные в порядке `ORDER BY` без сортировки |

Из последних двух пунктов растёт всё остальное, включая поведение
составных индексов.

**Что B-tree умеет:** `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`, `IN`,
`IS NULL`, `LIKE 'префикс%'` (только якорь слева), `ORDER BY`,
`MIN`/`MAX`, `DISTINCT` по ведущей колонке.

**Что не умеет:** `LIKE '%суффикс'`, `<>`, поиск по значению внутри
JSON/массива, полнотекстовый поиск.

## 3. Кластерный и некластерный индекс

Принципиальное различие между СУБД, часто спрашивают.

### PostgreSQL — всё некластерное

Таблица (heap) лежит неупорядоченно. Все индексы — вторичные, в листе
хранится `ctid` — физический адрес строки (номер страницы + смещение).

Команда `CLUSTER table USING index` физически пересортирует таблицу
**один раз**, но порядок не поддерживается — новые строки пишутся куда
придётся.

### MySQL/InnoDB — кластерный первичный ключ

Таблица **и есть** B-tree по первичному ключу: в листьях лежат целые
строки. Отсюда следствия:

- Поиск по PK — одно дерево, без обращения к heap. Быстро.
- Вторичный индекс хранит в листе **не адрес, а значение PK**. Поиск по
  вторичному индексу = два спуска: по вторичному дереву → по кластерному.
  Это называется *bookmark lookup*.
- Поэтому **каждый вторичный индекс в InnoDB неявно составной**:
  `(cols…, PK)`. Индекс `(dept_id)` физически это `(dept_id, id)`.
- Отсюда правило: **короткий PK**. Длинный PK раздувает все вторичные
  индексы. И — не брать случайный UUID как PK: вставка в середину дерева
  вызывает расщепление страниц.

### SQL Server

`CLUSTERED INDEX` задаётся явно (по умолчанию создаётся на PK). Без него
таблица — heap. Кластерный индекс может быть только один.

## 4. Виды индексов

### По структуре

| Тип | Где | Для чего |
|---|---|---|
| **B-tree** | везде, по умолчанию | равенство, диапазоны, сортировка. 95% случаев |
| **Hash** | PG, MySQL(MEMORY) | только `=`. В PG почти не нужен: B-tree не хуже и умеет больше |
| **GIN** | PG | «много значений в одном поле»: `jsonb`, массивы, полнотекстовый поиск |
| **GiST** | PG | геометрия, диапазоны (`tsrange`), `EXCLUDE`-ограничения, поиск ближайших |
| **BRIN** | PG | огромные таблицы с естественным порядком (лог по времени). Индекс крошечный, хранит min/max на блок |
| **SP-GiST** | PG | несбалансированные деревья: квадродеревья, префиксные деревья |
| **Bitmap** | Oracle, отчасти PG* | колонки с малым числом значений в аналитике |
| **FULLTEXT** | MySQL | полнотекстовый поиск |

\* В PostgreSQL нет постоянных bitmap-индексов, но есть **Bitmap Index
Scan** — планировщик строит битовую карту в памяти на лету и умеет
пересекать (`BitmapAnd`) или объединять (`BitmapOr`) несколько обычных
индексов. Это важно для раздела про составные индексы.

**Примеры:**

```sql
-- поиск по ключу в JSONB
CREATE INDEX idx_orders_meta ON orders USING GIN (meta);
SELECT * FROM orders WHERE meta @> '{"channel": "mobile"}';

-- лог событий за год, 500 млн строк, всегда фильтр по времени
CREATE INDEX idx_orders_time_brin ON orders USING BRIN (ordered_at);
-- индекс на десятки КБ вместо гигабайтов B-tree
```

### По логике

**Уникальный** — индекс + ограничение целостности.

```sql
CREATE UNIQUE INDEX idx_users_email ON users (email);
```

`PRIMARY KEY` и `UNIQUE` реализованы поверх уникального индекса
автоматически — отдельно создавать не нужно, это частая лишняя работа.

⚠️ В PostgreSQL уникальный индекс **не считает `NULL` дубликатами**:
несколько строк с `NULL` пройдут. Нужно иначе — `UNIQUE NULLS NOT
DISTINCT` (PG 15+).

**Частичный (partial)** — индексируется подмножество строк.

```sql
CREATE INDEX idx_orders_active ON orders (customer_id)
WHERE status = 'active';
```

Идеально, когда запросы всегда идут по «горячей» части, а таблица в
основном состоит из холодной. Индекс в разы меньше и попадает в кэш.
Условие запроса должно **логически покрываться** условием индекса, иначе
планировщик его не возьмёт. В MySQL частичных индексов нет.

Приём: уникальность только среди активных строк.

```sql
CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL;
```

**Функциональный (по выражению)** — индексируется результат выражения.

```sql
CREATE INDEX idx_employees_lower_name ON employees (lower(name));
SELECT * FROM employees WHERE lower(name) = 'ann';  -- сработает
```

Выражение в запросе должно совпадать с выражением в индексе. Функция
обязана быть `IMMUTABLE`.

**Покрывающий** — см. [раздел 6](#6-покрывающий-индекс-index-only-scan).

### Индексы на внешние ключи

**MySQL/InnoDB создаёт индекс на колонку `FOREIGN KEY` автоматически.
PostgreSQL — нет.** Это частый вопрос и частая проблема в PG.

Индекс на дочерней колонке нужен не для самой ссылки, а для проверок при
изменении родителя. Без него `DELETE`/`UPDATE` родительской строки
вызывает **полный скан дочерней таблицы** — на каждую удаляемую строку,
чтобы убедиться, что ссылок не осталось (или каскадно их обработать).
На больших таблицах это превращает удаление одной строки в минуты.

```sql
CREATE INDEX idx_orders_customer ON orders (customer_id);
```

По умолчанию — индексировать все внешние ключи. Обойтись без индекса
можно, если выполняется всё сразу:

- по этой колонке не делается выборок и соединений;
- колонка не является **префиксом** другого индекса (тогда он уже
  покрывает — см. [5.2](#52-правило-leftmost-prefix));
- родительские строки никогда не удаляются и их ключ не меняется.

## 5. Составные индексы

Индекс по нескольким колонкам. Здесь больше всего подводных камней и
именно про них спрашивают на собеседовании.

```sql
CREATE INDEX idx_emp_dept_salary ON employees (dept_id, salary);
```

### 5.1 Как он хранится

Ключ индекса — **конкатенация колонок**, отсортированная
лексикографически: сначала по первой колонке, при равенстве — по второй,
и так далее. Ровно как в телефонном справочнике: сначала по фамилии,
внутри одной фамилии — по имени.

Для данных:

| id | name | salary | dept_id |
|----|------|--------|---------|
| 1 | Ann | 300 | 10 |
| 2 | Bob | 200 | 10 |
| 3 | Cate | 200 | 20 |
| 4 | Dan | 100 | 20 |
| 5 | Erik | 100 | NULL |

листья индекса `(dept_id, salary)` выглядят так:

```
(10, 200) → id=2
(10, 300) → id=1
(20, 100) → id=4
(20, 200) → id=3
(NULL, 100) → id=5        ← в PG NULL сортируется в конец (NULLS LAST по умолчанию)
```

Всё поведение составного индекса выводится из этой картинки. Отсортирован
он **по паре целиком**, а не по каждой колонке отдельно.

### 5.2 Правило leftmost prefix

Индекс `(a, b, c)` может **искать** (делать seek) по префиксам слева:

| Условие в запросе | Работает? |
|---|---|
| `WHERE a = 1` | ✅ да |
| `WHERE a = 1 AND b = 2` | ✅ да |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✅ да, полностью |
| `WHERE a = 1 AND c = 3` | ⚠️ частично: seek по `a`, `c` проверяется фильтром |
| `WHERE b = 2` | ❌ seek невозможен |
| `WHERE b = 2 AND c = 3` | ❌ seek невозможен |

**Почему.** Посмотрите на листья выше. Значения `salary` упорядочены
только *внутри* одного `dept_id`. Глобально по индексу колонка `salary`
разбросана: 200, 300, 100, 200. Искать по ней нельзя — БД не знает,
с какой ветки начать спуск.

Аналогия: в телефонном справочнике легко найти всех Ивановых и легко
найти Иванова Петра. Но найти всех Петров без фамилии — только перебором
всей книги.

⚠️ **Важная оговорка, которую часто упускают.** «Не работает» = «нельзя
сделать seek». Полностью просканировать индекс от начала до конца БД всё
равно может, и иногда так и делает: если индекс сильно меньше таблицы,
Index Scan / Index Only Scan по всему индексу дешевле Seq Scan по таблице.
В плане это видно как отсутствие `Index Cond` при наличии `Filter`.
Это не оптимизация, а «меньшее из зол».

**Порядок колонок в `WHERE` не важен.** `WHERE b = 2 AND a = 1` и
`WHERE a = 1 AND b = 2` — одно и то же, оптимизатор переставит условия.
Важен порядок колонок **в определении индекса**.

### 5.3 Правило равенство → диапазон → сортировка

Главное практическое правило порядка колонок:

> Сначала колонки под `=`, затем **одна** колонка под диапазон или
> `ORDER BY`, всё остальное после — только как фильтр или покрытие.

**Почему диапазон «закрывает» индекс.** Пока условия на равенство,
дерево сужается до одной точки, и следующая колонка внутри неё
по-прежнему отсортирована. Как только пошёл диапазон, БД читает
**подряд идущий кусок** листьев, а внутри этого куска следующая колонка
уже не упорядочена.

Разберём на паре запросов с индексом `(dept_id, salary)`:

```sql
-- ✅ идеально: равенство, потом диапазон
SELECT * FROM employees WHERE dept_id = 10 AND salary > 150;
```

```
(10, 200) ← спуск сюда, дальше читаем подряд
(10, 300) ←
(20, 100)   стоп, dept_id изменился
```

Оба условия отработали как `Index Cond`. Читаем ровно нужное.

```sql
-- ❌ плохо: диапазон в ведущей колонке
SELECT * FROM employees WHERE dept_id > 5 AND salary = 200;
```

```
(10, 200) ← подходит
(10, 300)   читаем и отбрасываем
(20, 100)   читаем и отбрасываем
(20, 200) ← подходит
```

Индекс отработал только по `dept_id`, `salary` стал фильтром: прочитали
весь диапазон, большую часть выбросили. Здесь нужен индекс
`(salary, dept_id)`.

### 5.4 Порядок колонок и селективность

Распространённый миф: «самую селективную колонку ставить первой».

На самом деле:

1. **Первично — какие запросы вы обслуживаете.** Порядок диктуется
   правилом из 5.3, а не статистикой. Колонка под `=` идёт перед колонкой
   под диапазон, даже если она менее селективна.
2. **Между колонками под `=` порядок почти не влияет на скорость поиска** —
   дерево всё равно сужается до точки. Влияет на другое:
   - какие **другие** запросы сможет обслужить этот же индекс по
     leftmost prefix;
   - размер индекса: одинаковые значения подряд лучше сжимаются, поэтому
     низкоселективную колонку выгоднее ставить первой.

**Экономия на индексах через префиксы.** Индекс `(a, b, c)` покрывает
запросы по `(a)`, `(a, b)` и `(a, b, c)`. Три отдельных индекса не нужны.
Это главный аргумент за продуманный порядок колонок.

```sql
-- вместо трёх индексов
CREATE INDEX ON orders (customer_id);
CREATE INDEX ON orders (customer_id, status);
CREATE INDEX ON orders (customer_id, status, ordered_at);
-- достаточно одного
CREATE INDEX ON orders (customer_id, status, ordered_at);
```

### 5.5 Составной индекс и ORDER BY

Индекс возвращает данные уже отсортированными — это позволяет убрать шаг
сортировки и, что важнее, выполнить `ORDER BY … LIMIT` без чтения всей
выборки.

С индексом `(dept_id, salary)`:

| Запрос | Сортировка из индекса? |
|---|---|
| `ORDER BY dept_id, salary` | ✅ прямой проход по листьям |
| `ORDER BY dept_id DESC, salary DESC` | ✅ обратный проход |
| `ORDER BY dept_id, salary DESC` | ❌ направления смешаны |
| `WHERE dept_id = 10 ORDER BY salary` | ✅ внутри одного `dept_id` порядок есть |
| `WHERE dept_id > 5 ORDER BY salary` | ❌ диапазон разрушил порядок по `salary` |
| `ORDER BY salary` | ❌ не префикс |

Под смешанные направления создаётся индекс с явными модификаторами:

```sql
CREATE INDEX idx_emp_dept_sal ON employees (dept_id ASC, salary DESC);
```

Про `WHERE dept_id > 5 ORDER BY salary`: обратите внимание, что это тот же
эффект, что в 5.3 — диапазон в ведущей колонке ломает и фильтрацию по
следующей, и сортировку по ней.

### 5.6 IN-списки

`IN` — это набор равенств, и индекс с ним работает:

```sql
SELECT * FROM employees WHERE dept_id IN (10, 20) AND salary = 200;
```

БД делает несколько спусков — по одному на значение из списка
(в PG это видно как `Index Cond: (dept_id = ANY ('{10,20}'))`). Индекс
`(dept_id, salary)` отработает обеими колонками.

Но у приёма есть предел: список из тысяч значений превращается в тысячи
спусков, и планировщик в какой-то момент переключится на Seq Scan.

### 5.7 Skip scan

Что делать, если индекс `(a, b)`, а запрос только по `b`, и ведущая
колонка имеет мало разных значений?

Есть оптимизация: перебрать все различные значения `a` и для каждого
сделать точечный спуск по `b`. Фактически `WHERE b = x` превращается в
`WHERE a IN (все значения a) AND b = x`.

| СУБД | Поддержка |
|---|---|
| MySQL 8.0.13+ | Skip Scan Range Access, в плане `Using index for skip scan` |
| Oracle | index skip scan, давно |
| PostgreSQL 18+ | skip scan для B-tree добавлен |
| PostgreSQL ≤ 17 | нет; обходной путь — рекурсивный CTE или отдельный индекс |

Работает только когда ведущих значений мало. На высокой кардинальности
это дороже полного скана, и оптимизатор откажется.

Не закладывайтесь на skip scan при проектировании — правильный индекс
надёжнее.

### 5.8 Составной индекс vs несколько одноколоночных

Что лучше для `WHERE dept_id = 10 AND salary = 200` — один индекс
`(dept_id, salary)` или два отдельных?

**Составной почти всегда быстрее.** Он сразу сужает до нужных строк.

Два отдельных индекса PostgreSQL умеет комбинировать через
**BitmapAnd**: пройти оба индекса, построить битовые карты страниц,
пересечь их, потом прочитать таблицу. Это работает, но:

- читаются оба индекса целиком в части подходящих значений;
- построение и пересечение битмапов стоит времени и памяти;
- при большом объёме битмап становится «lossy» — вырождается до уровня
  страниц, и приходится перепроверять строки (`Recheck Cond`).

Когда всё же брать отдельные индексы: если колонки используются в
запросах в **разных сочетаниях и по отдельности**, и заранее непонятно,
какая комбинация встретится.

### 5.9 Разбор: подбираем индекс под запрос

```sql
SELECT id, amount
FROM orders
WHERE customer_id = 42
  AND status = 'shipped'
  AND ordered_at >= '2026-01-01'
ORDER BY ordered_at DESC
LIMIT 20;
```

Идём по правилу из 5.3:

1. **Равенства:** `customer_id`, `status` → в начало.
2. **Диапазон + сортировка по одной колонке:** `ordered_at` → следующая.
   Совпадение диапазона и `ORDER BY` в одной колонке — удачный случай:
   индекс закрывает и фильтр, и порядок, а `LIMIT 20` остановит чтение
   после 20 строк.
3. **Покрытие:** в `SELECT` нужен `amount` — добавим его, чтобы не
   ходить в таблицу.

```sql
CREATE INDEX idx_orders_lookup
  ON orders (customer_id, status, ordered_at DESC)
  INCLUDE (amount);
```

План:

```
Limit
  ->  Index Only Scan using idx_orders_lookup on orders
        Index Cond: ((customer_id = 42) AND (status = 'shipped')
                     AND (ordered_at >= '2026-01-01'))
```

Ни `Sort`, ни `Filter`, ни обращения к heap.

Порядок `(customer_id, status, …)` даёт бонусом поддержку запросов
просто по `customer_id`.

А вот такой вариант — ошибка:

```sql
CREATE INDEX ON orders (ordered_at, customer_id, status);  -- ❌
```

Диапазон стоит первым, значит `customer_id` и `status` станут фильтрами:
прочитаем все заказы с начала года и отбросим 99%.

## 6. Покрывающий индекс (Index Only Scan)

Если **все** колонки запроса есть в индексе, обращение к таблице не
нужно — второй, самый дорогой этап поиска исчезает.

```sql
CREATE INDEX idx_emp_dept_salary ON employees (dept_id, salary);

SELECT dept_id, salary FROM employees WHERE dept_id = 10;
-- Index Only Scan
SELECT * FROM employees WHERE dept_id = 10;
-- Index Scan + heap fetch: нужны name, hired_at и остальное
```

**`INCLUDE` — неключевые колонки** (PG 11+, SQL Server давно):

```sql
CREATE INDEX idx_emp_cover ON employees (dept_id) INCLUDE (name, salary);
```

Колонки в `INCLUDE` лежат только в листьях, по ним нельзя искать и
сортировать, зато они не раздувают внутренние узлы дерева. Годится, когда
колонка нужна только для чтения. Отдельная польза: `UNIQUE (a) INCLUDE (b)`
— уникальность по `a`, покрытие по `b`.

⚠️ **Нюанс PostgreSQL.** Index Only Scan работает только если страница
отмечена как «полностью видимая» в *visibility map*. Из-за MVCC свежие
изменения сбрасывают эту отметку, и в плане появляются `Heap Fetches`.
Карту обновляет `VACUUM` — на активно обновляемой таблице index only scan
без регулярного вакуума деградирует. В MySQL/InnoDB такого нет, там
покрывающий индекс виден в плане как `Using index`.

## 7. Когда индекс не работает

| Ситуация | Почему | Решение |
|---|---|---|
| `WHERE UPPER(name) = 'ANN'` | функция на колонке — в индексе лежат исходные значения | функциональный индекс или `ILIKE` |
| `WHERE EXTRACT(YEAR FROM hired_at) = 2026` | то же самое | `hired_at >= '2026-01-01' AND hired_at < '2027-01-01'` |
| `WHERE salary + 100 > 500` | арифметика на колонке | перенести вычисление вправо: `salary > 400` |
| `WHERE id_text = 123` | неявное приведение типов | привести литерал к типу колонки |
| `WHERE name LIKE '%ann%'` | нет якоря слева, префикс неизвестен | триграммный индекс: `pg_trgm` + GIN |
| `WHERE status <> 'done'` | отрицание не сужает диапазон | частичный индекс `WHERE status <> 'done'` |
| `WHERE b = 2` при индексе `(a, b)` | не leftmost prefix | переставить колонки или новый индекс |
| Условие выбирает 30% таблицы | Seq Scan дешевле | это нормально, не чинить |
| Таблица маленькая | всё в одной-двух страницах | нормально |
| Устаревшая статистика | планировщик ошибся в оценке | `ANALYZE table` |

Правило, покрывающее половину строк таблицы: **колонка в `WHERE` должна
быть «голой»**, все преобразования — на стороне константы.

## 8. Цена индексов

Индексы не бесплатны, и на собеседовании это ждут услышать:

- **Запись замедляется.** Каждый `INSERT`/`DELETE` и каждый `UPDATE`
  индексированной колонки обновляет все затронутые индексы. Десять
  индексов — десять деревьев на строку.
- **Место на диске.** Индекс легко занимает столько же, сколько таблица.
- **Больше кандидатов планировщику** — время планирования растёт.
- **Разбухание (bloat).** В PG при обновлениях страницы фрагментируются;
  лечится `REINDEX CONCURRENTLY`.

Практические следствия:

- Не индексировать «на всякий случай» — только под реальные запросы.
- Дубли вроде `(a)` при существующем `(a, b)` — удалять, префикс уже
  покрыт.
- Перед массовой загрузкой индексы имеет смысл снести и создать заново
  после — это быстрее, чем поддерживать дерево на каждой строке.
- В проде создавать через `CREATE INDEX CONCURRENTLY` (PG) — обычный
  `CREATE INDEX` берёт блокировку на запись.

## 9. Как проверять

**План запроса:**

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT …;
```

Что читать в плане:

| Строка | Значение |
|---|---|
| `Seq Scan` | индекс не используется |
| `Index Scan` | спуск по индексу + чтение таблицы |
| `Index Only Scan` | индекс покрывает запрос |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | много строк, БД собирает битмап страниц |
| `Index Cond:` | условие отработало **индексом** — то, что нужно |
| `Filter:` + большой `Rows Removed by Filter` | строки прочитали и выбросили — индекс неполный |
| `Heap Fetches:` | сколько раз пришлось идти в таблицу при Index Only Scan |
| `rows=… ` в оценке vs `actual rows=…` | расхождение на порядок — беда со статистикой |

**Неиспользуемые индексы:**

```sql
SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

`idx_scan = 0` за длительный период — кандидат на удаление (кроме тех,
что поддерживают ограничения).

В MySQL: `EXPLAIN`/`EXPLAIN ANALYZE`, колонки `key` (какой индекс выбран),
`key_len` (сколько байт префикса составного индекса реально задействовано —
прямой ответ на вопрос «сколько колонок сработало»), `rows`, `Extra`
(`Using index` = покрывающий, `Using filesort` = сортировка не из индекса).

Полный разбор `EXPLAIN` — узлы плана, `cost` vs `actual`, алгоритмы
соединений — в [`optimization.md`](optimization.md#explain).

⚠️ `CREATE INDEX` без `CONCURRENTLY` берёт блокировку на запись до конца
построения — см. [`locks.md`](locks.md#табличные-блокировки).

## 10. Шпаргалка

**Устройство**

- B-tree: сбалансированное, глубина 3–4, листья отсортированы и связаны
  в список.
- Поиск = спуск O(log N) + обращение к таблице за строкой.
- PG: таблица-heap, все индексы вторичные. InnoDB: PK кластерный,
  вторичный индекс ссылается на PK.

**Составной индекс `(a, b, c)`**

- Отсортирован лексикографически по всему ключу.
- Seek работает по префиксам слева: `a`, `(a,b)`, `(a,b,c)`.
- Порядок колонок: **`=` → диапазон/`ORDER BY` → остальное**.
- Диапазон в колонке закрывает индексный поиск и сортировку по всем
  следующим колонкам.
- Порядок условий в `WHERE` не имеет значения, порядок в `CREATE INDEX` —
  имеет.
- Один индекс `(a,b,c)` заменяет три: `(a)`, `(a,b)`, `(a,b,c)`.
- `IN` = набор равенств, индекс работает.
- Составной обычно быстрее двух одноколоночных с BitmapAnd.

**Что помнить помимо**

- Покрывающий индекс убирает поход в таблицу; `INCLUDE` — для колонок
  только на чтение.
- Функция на колонке в `WHERE` убивает индекс.
- Частичный индекс — лучший инструмент для «горячего» подмножества.
- Индексы замедляют запись и занимают место; лишние — удалять.
- `EXPLAIN`: `Index Cond` хорошо, `Filter` с большим
  `Rows Removed by Filter` плохо.
