# SQL: блокировки и изоляция

Что спрашивают на собеседовании про конкурентный доступ: аномалии, уровни
изоляции, виды блокировок, дедлоки.

PostgreSQL по умолчанию, отличия MySQL/InnoDB отмечены.
Оптимизация запросов — [`optimization.md`](optimization.md).

---

## ACID

Четыре свойства, которые гарантируют надёжную обработку транзакций.
Критичны там, где потеря или искажение данных недопустимы (банковские
системы, платежи).

| Свойство | Суть |
|---|---|
| **Atomicity** (атомарность) | Транзакция — неделимая единица: либо выполняются все её шаги, либо ни один (откат), как будто транзакции не было |
| **Consistency** (согласованность) | Транзакция переводит базу из одного корректного состояния в другое, не нарушая ограничений целостности (баланс не уйдёт в минус, если это запрещено constraint'ом) |
| **Isolation** (изоляция) | Параллельные транзакции не влияют друг на друга: каждая работает так, будто выполняется в одиночку, и не видит чужих незакоммиченных изменений |
| **Durability** (долговечность) | После коммита изменения сохранены навсегда и переживают сбои: перезагрузки, отключение питания (WAL, fsync) |

Изоляция — единственное свойство «с ручкой настройки»: уровни изоляции
ниже и есть компромисс между строгостью и производительностью.

---

## Зачем

Две транзакции работают с одними данными одновременно. Без координации
получаются **аномалии** — результаты, невозможные при последовательном
выполнении.

| Аномалия | Что происходит |
|---|---|
| **Dirty read** | Прочитали то, что другая транзакция ещё не закоммитила. Она откатится — вы работали с несуществующими данными |
| **Non-repeatable read** | Прочитали строку дважды внутри одной транзакции и получили разные значения: между чтениями кто-то её изменил |
| **Phantom read** | Повторили запрос с тем же `WHERE` и получили **новые строки**: кто-то вставил подходящие |
| **Lost update** | Две транзакции прочитали значение, посчитали новое и записали. Изменение первой затёрто |
| **Write skew** | Каждая транзакция читает данные, принимает по ним решение и пишет в *разные* строки. По отдельности всё корректно, вместе — нарушен инвариант |

Классический пример lost update: два процесса читают `balance = 100`,
оба вычисляют `100 - 10` и пишут `90`. Списали 20, а баланс `90`.

Write skew: два врача на дежурстве, каждый проверяет «есть ли ещё
дежурный кроме меня», видит второго и уходит. Оба ушли.

## Уровни изоляции

Стандарт SQL определяет четыре уровня — по тому, какие аномалии
разрешены:

| Уровень | Dirty read | Non-repeatable | Phantom |
|---|---|---|---|
| READ UNCOMMITTED | ✅ возможен | ✅ | ✅ |
| READ COMMITTED | ❌ | ✅ | ✅ |
| REPEATABLE READ | ❌ | ❌ | ✅ по стандарту |
| SERIALIZABLE | ❌ | ❌ | ❌ |

Что важно знать про реальные СУБД, потому что они не совпадают со
стандартом:

**PostgreSQL** — по умолчанию `READ COMMITTED`.

- `READ UNCOMMITTED` не реализован: работает как `READ COMMITTED`. Грязных
  чтений в PG не бывает в принципе.
- `REPEATABLE READ` — это snapshot isolation: транзакция видит снимок
  данных на момент своего начала, поэтому **фантомы тоже не возникают**.
  Но write skew возможен.
- `SERIALIZABLE` — SSI, отслеживает опасные пересечения и **откатывает**
  транзакцию с ошибкой сериализации. Приложение обязано уметь повторять
  такую транзакцию.

**MySQL/InnoDB** — по умолчанию `REPEATABLE READ`.

- Фантомы предотвращаются **next-key locks** (см. ниже), а не снимком.
- Обычный `SELECT` не блокирует ничего — читает из MVCC-снимка.

Практический вывод: `READ COMMITTED` покрывает большинство задач,
а от lost update защищаются явными блокировками, а не уровнем изоляции.

## Пессимистичные и оптимистичные блокировки

**Пессимистичная** — «сначала захвачу, потом работаю».

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- строка заблокирована
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
COMMIT;                                                 -- блокировка снята
```

Второй транзакции `SELECT ... FOR UPDATE` по той же строке будет **ждать**
коммита первой. Lost update невозможен.

**Оптимистичная** — «поработаю, а при записи проверю, что никто не влез».
Блокировок нет, есть колонка версии:

```sql
UPDATE documents
SET text = 'новый текст', version = version + 1
WHERE id = 42 AND version = 7;
```

Если кто-то успел раньше, `version` уже 8, `UPDATE` затронет 0 строк —
приложение видит конфликт и повторяет операцию.

| | Пессимистичная | Оптимистичная |
|---|---|---|
| Когда | Конфликты частые, повтор дорогой | Конфликты редкие |
| Цена | Ожидание, риск дедлока | Повтор всей операции |
| Где типично | Списание денег, склад | Редактирование документов, REST API |

## Виды блокировок

### По режиму

- **Shared (S)** — на чтение. Несколько S на одной строке уживаются.
- **Exclusive (X)** — на запись. Несовместима ни с чем.

### По гранулярности

Строка → страница → таблица. Чем крупнее, тем меньше накладных расходов
на учёт и тем меньше параллелизма.

**Эскалация блокировок** — когда транзакция набрала слишком много
строковых блокировок, СУБД может заменить их одной табличной. Есть в
SQL Server и Oracle; **в PostgreSQL и InnoDB эскалации нет**.

### Строчные блокировки в PostgreSQL

```sql
SELECT ... FOR UPDATE;         -- полная блокировка строки на изменение
SELECT ... FOR NO KEY UPDATE;  -- слабее, не мешает FK-проверкам
SELECT ... FOR SHARE;          -- другие читают, но не меняют
SELECT ... FOR KEY SHARE;      -- держит только ключ (используется внешними ключами)
```

Модификаторы ожидания:

```sql
SELECT ... FOR UPDATE NOWAIT;      -- не ждать, сразу ошибка
SELECT ... FOR UPDATE SKIP LOCKED; -- пропустить занятые строки
```

`SKIP LOCKED` — основа очередей на таблицах: несколько воркеров разбирают
задания без конфликтов. Так работает relay в
[Outbox](../patterns/outbox.md#relay-публикация).

⚠️ В PostgreSQL **читатели не блокируют писателей, а писатели —
читателей**. Это следствие MVCC: `UPDATE` создаёт новую версию строки,
старую продолжают видеть старые снимки. Блокируются только конкурирующие
записи одной строки.

### Строчные блокировки в InnoDB

| Тип | Что блокирует |
|---|---|
| **Record lock** | Запись индекса |
| **Gap lock** | Промежуток между записями индекса — чтобы туда нельзя было вставить |
| **Next-key lock** | Record + gap перед ней. Режим по умолчанию на REPEATABLE READ |

Next-key locks и есть механизм защиты от фантомов в MySQL.

⚠️ Отсюда важное следствие: **InnoDB блокирует записи индекса, а не
строки таблицы**. Если запрос не может использовать индекс, он
заблокирует все просмотренные записи — фактически всю таблицу.
Плохие индексы в MySQL превращаются в проблему конкурентности,
а не только скорости.

### Табличные блокировки

Берутся неявно: `SELECT` — слабую, `UPDATE` — сильнее, DDL —
`ACCESS EXCLUSIVE`, несовместимую ни с чем.

Практическое следствие в PG: `ALTER TABLE` ждёт завершения всех
транзакций, работающих с таблицей, а сам при этом **блокирует новые
запросы в очереди за собой**. Одна долгая транзакция + `ALTER TABLE` =
встал весь доступ к таблице. Поэтому в проде:

```sql
SET lock_timeout = '3s';           -- не висеть в очереди бесконечно
CREATE INDEX CONCURRENTLY ...;     -- создание индекса без блокировки записи
```

## Дедлоки

Взаимная блокировка: транзакция A держит строку 1 и ждёт строку 2,
транзакция B держит строку 2 и ждёт строку 1.

```
A: UPDATE accounts SET ... WHERE id = 1;   -- взял 1
B: UPDATE accounts SET ... WHERE id = 2;   -- взял 2
A: UPDATE accounts SET ... WHERE id = 2;   -- ждёт B
B: UPDATE accounts SET ... WHERE id = 1;   -- ждёт A  → дедлок
```

**Как разрешается.** СУБД обнаруживает цикл ожидания и **откатывает одну
из транзакций** с ошибкой. PostgreSQL проверяет через `deadlock_timeout`
(по умолчанию 1 с). InnoDB строит граф ожидания и убивает транзакцию,
которая изменила меньше строк.

**Как избегать:**

1. **Единый порядок захвата** — самое главное. Если все транзакции берут
   строки в порядке возрастания `id`, цикл невозможен.
2. Короткие транзакции: не держать блокировку через сетевые вызовы и
   пользовательский ввод.
3. Захватывать всё нужное сразу, а не докупать по ходу.
4. Всегда иметь **ретрай** на уровне приложения — полностью исключить
   дедлоки нельзя.

## Advisory locks

Блокировка не по данным, а по произвольному числу — своего рода мьютекс
в базе. Удобно для «пусть эту задачу выполняет только один инстанс».

```sql
SELECT pg_try_advisory_lock(12345);  -- true, если захватили
-- ... работа ...
SELECT pg_advisory_unlock(12345);
```

Вариант `pg_advisory_xact_lock()` снимается автоматически при завершении
транзакции — почти всегда безопаснее.

## Диагностика

**PostgreSQL — кто кого ждёт:**

```sql
SELECT pid, state, wait_event_type, left(query, 60) AS query,
       pg_blocking_pids(pid) AS blocked_by
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Долгие транзакции — главный источник проблем, их ищут так:

```sql
SELECT pid, now() - xact_start AS duration, state, left(query, 60)
FROM pg_stat_activity
WHERE state <> 'idle' ORDER BY duration DESC;
```

Особое внимание к состоянию `idle in transaction` — транзакция открыта,
запросов нет, блокировки держатся. Обычно это баг в приложении
(забыли `COMMIT`).

**MySQL:** `SHOW ENGINE INNODB STATUS` (секция `LATEST DETECTED DEADLOCK`),
таблицы `performance_schema.data_locks` и `data_lock_waits`.

## Шпаргалка

- **Аномалии:** dirty read → non-repeatable read → phantom → lost update →
  write skew.
- **Уровни:** RU / RC / RR / SERIALIZABLE. PG по умолчанию RC, MySQL — RR.
- PG `REPEATABLE READ` = snapshot isolation: фантомов нет, write skew есть.
  Только `SERIALIZABLE` даёт полную корректность, ценой откатов и ретраев.
- **MVCC:** в PostgreSQL читатели и писатели не блокируют друг друга.
- **Lost update** лечится `SELECT FOR UPDATE` (пессимистично) или колонкой
  `version` (оптимистично), а не уровнем изоляции.
- **InnoDB блокирует записи индекса**, а не строки: нет индекса — заблокирована
  вся таблица. Фантомы закрываются next-key locks.
- **Дедлок** — цикл ожидания; СУБД откатывает одну транзакцию. Профилактика:
  единый порядок захвата + короткие транзакции + ретрай.
- **`SKIP LOCKED`** — очереди на таблицах без конфликтов между воркерами.
- **Транзакции держать короткими.** Почти любая проблема с блокировками
  начинается с долгой транзакции.
