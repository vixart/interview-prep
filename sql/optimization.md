## Подзапросы и JOIN

Оптимизатор старается **развернуть подзапросы в JOIN** — так называемая
раскрутка (unnesting). Это не наивное выполнение «строчка за строчкой»,
а переписывание плана.

Если развернуть не удалось, порядок по скорости примерно такой:

| Форма | Как выполняется |
|---|---|
| `JOIN` | один проход, оптимизатор выбирает алгоритм соединения |
| **Некоррелирующий** подзапрос | выполняется **один раз**, результат подставляется |
| **Коррелирующий** подзапрос | выполняется **для каждой строки** внешнего запроса |

```sql
-- некоррелирующий: подзапрос не зависит от внешней строки, считается один раз
SELECT * FROM employees WHERE salary > (SELECT AVG(salary) FROM employees);

-- коррелирующий: ссылается на e2 снаружи, в худшем случае N выполнений
SELECT * FROM employees e1
WHERE salary > (SELECT AVG(salary) FROM employees e2 WHERE e2.dept_id = e1.dept_id);
```

Коррелирующий вариант выше переписывается через оконную функцию и
выполняется одним проходом:

```sql
SELECT * FROM (
  SELECT *, AVG(salary) OVER (PARTITION BY dept_id) AS avg_dept
  FROM employees
) t WHERE salary > avg_dept;
```

Не полагайтесь на «оптимизатор разберётся» — проверяйте
[`EXPLAIN`](indexes.md#9-как-проверять).

## Пагинация: OFFSET против keyset

```sql
-- ❌ OFFSET: прочитает 2100 строк и выбросит 2000
SELECT * FROM movies ORDER BY title LIMIT 100 OFFSET 2000;

-- ✅ keyset (seek method): спуск по индексу сразу в нужную точку
SELECT * FROM movies WHERE title > 'ABC' ORDER BY title LIMIT 100;
```

`OFFSET` линейно деградирует: чем дальше страница, тем дороже. На
странице 1000 запрос читает 100 000 строк ради сотни.

Keyset запоминает последнее значение с предыдущей страницы и стартует
с него. Стоимость одинакова для любой страницы.

Что учесть:

- Колонка сортировки должна быть **проиндексирована**, иначе смысла нет.
- Если значения не уникальны, нужен тайбрейкер, иначе строки на границе
  страниц потеряются или задвоятся:
  ```sql
  WHERE (title, id) > ('ABC', 500) ORDER BY title, id LIMIT 100;
  ```
- Keyset умеет только «следующая/предыдущая», прыжок на произвольную
  страницу — нет. Для бесконечной прокрутки идеально, для нумерованной
  пагинации — нет.

## Подсчёт строк

```sql
-- точно, но полный проход по таблице
SELECT COUNT(*) FROM movies;
```

В InnoDB и в PostgreSQL нет счётчика строк (из-за MVCC у каждой
транзакции своя видимость), поэтому `COUNT(*)` всегда сканирует.
В MyISAM счётчик есть и `COUNT(*)` мгновенный.

Если хватает приблизительной оценки — брать из статистики:

```sql
-- MySQL
SELECT table_rows FROM information_schema.tables
WHERE table_schema = 'database_name' AND table_name = 'table_name';

-- PostgreSQL
SELECT reltuples::bigint FROM pg_class WHERE relname = 'movies';
```

⚠️ Это оценка, обновляемая при `ANALYZE`/сборе статистики. Погрешность
может достигать десятков процентов. Годится для «примерно 2 млн записей»
в интерфейсе, не годится для бизнес-логики.

## Удаление данных

`TRUNCATE` намного быстрее `DELETE`: он не удаляет строки по одной, а
пересоздаёт файл таблицы.

В MySQL и Oracle `TRUNCATE` — DDL с **неявным коммитом**: он завершает
текущую транзакцию, откатить его нельзя, и изоляция нарушается.
В PostgreSQL `TRUNCATE` транзакционный и откатывается.

Полное сравнение `DELETE` / `TRUNCATE` / `DROP` —
[`theory.md`, раздел 1](theory.md#1-ddl-объекты-базы).

## EXPLAIN

Единственный способ узнать, что БД делает на самом деле, вместо догадок.

```sql
EXPLAIN            SELECT …;   -- план и оценки, запрос НЕ выполняется
EXPLAIN ANALYZE    SELECT …;   -- реально выполняет и показывает факт
EXPLAIN (ANALYZE, BUFFERS) …;  -- + сколько страниц прочитано и откуда
```

⚠️ `EXPLAIN ANALYZE` **выполняет** запрос. С `UPDATE`/`DELETE` запускать
только внутри транзакции с `ROLLBACK`.

### Как читать план

План — дерево. Читается **снизу вверх и изнутри наружу**: самые
вложенные узлы выполняются первыми, каждый передаёт строки родителю.

```
Limit  (cost=0.43..8.46 rows=20 width=16) (actual time=0.021..0.089 rows=20 loops=1)
  ->  Index Scan using idx_orders_lookup on orders
        (cost=0.43..402.11 rows=1000 width=16) (actual time=0.019..0.081 rows=20 loops=1)
        Index Cond: (customer_id = 42)
        Filter: (amount > 100)
        Rows Removed by Filter: 340
```

Что здесь важно:

| Поле | Смысл |
|---|---|
| `cost=0.43..402.11` | оценка в условных единицах: **старт..полная**. Сравнивать планы между собой, не считать миллисекундами |
| `rows=1000` | **оценка** числа строк |
| `actual … rows=20` | сколько получилось **на самом деле** |
| `loops=N` | узел выполнялся N раз; `actual time` указан **на один проход**, умножайте |
| `Index Cond` | условие отработало индексом — хорошо |
| `Filter` + `Rows Removed by Filter` | строки прочитали и выбросили — индекс не покрывает условие |

**Главный сигнал: расхождение `rows` и `actual rows` на порядок.**
Планировщик ошибся в оценке и, скорее всего, выбрал неверный алгоритм.
Лечится `ANALYZE table`, расширенной статистикой или переписыванием
запроса.

### Основные узлы

| Узел | Что значит |
|---|---|
| `Seq Scan` | полный проход по таблице |
| `Index Scan` | спуск по индексу + чтение строк из таблицы |
| `Index Only Scan` | всё нужное есть в индексе, в таблицу не ходим |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | строк много: собирается битовая карта страниц, потом читаются они |
| `Nested Loop` | для каждой строки слева — поиск справа. Хорош, когда слева мало строк |
| `Hash Join` | строит хеш-таблицу по меньшей стороне. Универсальный вариант для больших объёмов |
| `Merge Join` | обе стороны отсортированы, идут параллельно. Хорош, когда сортировка уже есть из индекса |
| `Sort` | явная сортировка. `external merge Disk` в `ANALYZE` = не хватило `work_mem` |
| `Materialize` | результат узла сохранён в памяти для повторного использования |

Типичная проблема: `Nested Loop` с большим `loops=` на внутренней
стороне — значит планировщик недооценил левую сторону.

### MySQL

```sql
EXPLAIN SELECT …;
EXPLAIN ANALYZE SELECT …;   -- 8.0.18+
EXPLAIN FORMAT=JSON …;      -- подробности, включая стоимость
```

Ключевые колонки:

| Колонка | На что смотреть |
|---|---|
| `type` | способ доступа. От лучшего к худшему: `const` → `eq_ref` → `ref` → `range` → `index` → **`ALL`** (полный скан) |
| `key` | какой индекс выбран, `NULL` = никакой |
| `key_len` | сколько байт составного индекса задействовано — прямой ответ на «сколько колонок сработало» |
| `rows` | оценка просмотренных строк |
| `Extra` | `Using index` = покрывающий индекс (хорошо), `Using filesort` и `Using temporary` = сортировка/временная таблица (плохо на больших объёмах) |

Диагностика индексов конкретно — [`indexes.md` §9](indexes.md#9-как-проверять).
