# Решение

## Проблемы

1. **Гонка данных**: глобальные `users` и `nextID` изменяются из хендлеров,
   каждый из которых выполняется в своей горутине → `concurrent map writes`.
   Нужен `sync.RWMutex` (или `atomic` для счётчика), лучше — вынести в тип-хранилище.
2. **Все ошибки игнорируются**: `io.ReadAll`, `json.Unmarshal`, `Encode`,
   `ListenAndServe`, `Sscanf`. Нужны проверки и корректные коды ответа (400/404/500).
3. **Нет проверки существования пользователя**: `users[id]` для отсутствующего ключа
   вернёт нулевой `User` и отдаст его с кодом 200 вместо 404.
4. **`io.ReadAll` + `json.Unmarshal`** — лишняя аллокация всего тела; лучше
   `json.NewDecoder(r.Body).Decode(&user)`; плюс ограничить размер тела
   (`http.MaxBytesReader`) — иначе DoS.
5. **Разбор пути через `fmt.Sscanf`** — хрупко; использовать роутер
   (`chi`, `gorilla/mux`) или `http.ServeMux` с шаблонами (Go 1.22+).
6. **Нет обработки неподдерживаемых методов** → должен быть `405 Method Not Allowed`.
7. **Не выставляется `Content-Type: application/json`**.
8. **Нет тегов `json`** у структуры — поля уезжают с заглавной буквы;
   `ID` клиента при создании не должен приниматься извне.
9. **Нет валидации входных данных** (пустое имя, некорректный email, отрицательный возраст).
10. **`http.ListenAndServe` без таймаутов** и без graceful shutdown —
    нужен `&http.Server{ReadHeaderTimeout: ..., WriteTimeout: ...}`.
11. Использование глобального `http.DefaultServeMux` — небезопасно
    (сторонние пакеты могут регистрировать свои хендлеры, например `net/http/pprof`).
