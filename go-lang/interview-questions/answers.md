## 1. Лайв-кодинг

### Сделать воркер-пул

Три полных реализации одной задачи — ровно то, как она разворачивается на собеседовании
от «напиши пул» до «а что в проде».

| Уровень | Код | Что есть |
| --- | --- | --- |
| junior | [pool.go](examples/live_coding/workerpool/junior/pool.go) · [тест на баг](examples/live_coding/workerpool/junior/pool_test.go) | канал задач + `WaitGroup`, ~40 строк, пять багов |
| middle | [pool.go](examples/live_coding/workerpool/middle/pool.go) · [config](examples/live_coding/workerpool/middle/config.go) · [ошибки](examples/live_coding/workerpool/middle/errors.go) | `Submit(ctx, fn) error`, recover, graceful shutdown с дедлайном, канал ошибок |
| senior | [pool.go](examples/live_coding/workerpool/senior/pool.go) · [config](examples/live_coding/workerpool/senior/config.go) | политика при полной очереди, `Resize` на ходу, счетчики дропов, `worker_id` в контексте |

Скелет, который надо уметь писать на доске не задумываясь (это junior-уровень, но без его багов):

```go
jobs := make(chan Job)       // задания
results := make(chan Result) // результаты

var wg sync.WaitGroup
wg.Add(workers)              // Add ДО запуска горутин
for i := 0; i < workers; i++ {
    go func() {
        defer wg.Done()      // defer — уцелеет при панике
        for j := range jobs {            // выйдет сам, когда jobs закроют
            select {
            case results <- work(ctx, j):
            case <-ctx.Done():           // читатель ушел — не виснем на записи
                return
            }
        }
    }()
}
go func() { wg.Wait(); close(results) }() // закрывает писатель, ОДИН раз
```

Базовые вещи, которые проверяют сразу:

- `wg.Add` до `go`, а не внутри горутины;
- канал заданий закрывает тот, кто в него пишет; канал результатов — отдельная горутина после `Wait`;
- есть выход по контексту, иначе при раннем выходе читателя горутины утекут;
- порядок результатов не сохраняется — если он нужен, см. [следующий вопрос](#распараллелить-обработку-данных);
- число воркеров — параметр, а не константа: CPU-bound → `GOMAXPROCS`, IO-bound → больше.

#### Junior: пять багов, которые нельзя нести в прод

Помечены прямо в коде, воспроизводятся тестом
([pool.go](examples/live_coding/workerpool/junior/pool.go), [pool_test.go](examples/live_coding/workerpool/junior/pool_test.go)):

1. **`send on closed channel`.** `AddTask` пишет в тот же канал, который закрывает `Close`.
   Это TOCTOU между `mu.Unlock()` и отправкой, а при полной очереди — детерминированная паника:
   `Close` закрывает канал под уже заблокированным отправителем.
   `go test -race ./workerpool/junior` показывает гонку явно (тест падает намеренно).
2. **Нет `recover`.** Паника в задаче убивает воркера, пул молча деградирует до нуля воркеров.
3. **Нет контекста.** Задача — `func()`: отменить нельзя, результат неизвестен;
   `Close` висит столько, сколько идет самая долгая задача.
4. **Задачи теряются молча.** После закрытия `AddTask` просто делает `return`.
5. **Мьютекс рядом с каналом.** Две модели синхронизации на одно состояние + магическая `100` в буфере.

#### Middle: смена модели, а не заплатки

- канал задач **не закрывается никогда** → `send on closed` невозможен в принципе;
  воркеры выходят по сигнальным каналам `stop` (доесть очередь) и `done` (бросить все);
- `recover` стоит на **каждой задаче** (отдельная функция `runTask`), паника едет
  потребителю как `*PanicError` со стеком;
- `Submit(ctx, fn(ctx)) error` — задача отменяема и возвращает ошибку, `Submit` умеет отказать;
- `Shutdown(ctx)` = graceful drain с дедлайном и force-stop’ом;
- параметры вынесены в `Config`, невалидный конфиг паникует на старте.

Что в middle **осталось** сломанным — об этом лучше сказать самому, это плюс на собеседовании:

- гонка `Submit`/`Shutdown`: если `close(stop)` происходит, когда `Submit` уже внутри `select`,
  готовы обе ветви и выбор случайный — задача может лечь в буфер после начала остановки.
  Обычно ее подберет drain, но при срабатывании дедлайна она потеряется молча.
  Лечится только линеаризацией (refcount in-flight отправителей) ценой синхронизации на горячем пути;
- **хвост очереди при force-stop дропается без следа** — нужен лог и метрика `len(tasks)`;
- ошибки, не влезшие в `Errors()`, уходят в счетчик `DroppedErrors` — без мониторинга их не видно;
- канал ошибок **нельзя закрывать**: задача, начатая до `Shutdown`, еще может в него писать
  (в демо `main.go` закрытие сделано только чтобы выйти из `range`, и уже после `wg.Wait`).

#### Senior: то, что делает пул эксплуатируемым

- `Config.OnFull`: `Block` (ждать слот) / `FailFast` (`ErrQueueFull` сразу) /
  `DropNewest` (тихо выбросить, `nil` наружу, `DroppedTasks++`). Ловушка последней —
  вызывающий думает, что все хорошо; без алерта на счетчик деградация невидима;
- `Resize(n)` через небуферизованный канал `quitOne`: **K отправок = K выходов**;
  `close` здесь нельзя — это broadcast, вышли бы все воркеры;
- `Resize` синхронный под мьютексом, иначе два параллельных вызова прочитают одно и то же
  `current` и оба применят свою дельту;
- `worker_id` в контексте задачи (ключ — неэкспортируемый тип) для structured-логов.

### Распараллелить обработку данных

[parallel_processing](examples/live_coding/parallel_processing/main.go)

Ключевая мысль: **если каждая горутина пишет в свой индекс заранее выделенного среза,
синхронизация не нужна вообще** — это разные адреса, общего состояния нет.

```go
out := make([]R, len(in))     // длина известна заранее
idx := make(chan int)          // раздаем индексы, а не данные
// N воркеров: for i := range idx { out[i] = f(in[i]) }
wg.Wait()                      // без Wait можно прочитать недозаполненный out
```

Уточняющие вопросы, которые последуют:

- «а если порядок не важен?» → обычный воркер-пул с каналом результатов;
- «а если нужны ошибки?» → `[]Result{Val, Err}` или отмена по первой ошибке (`errgroup`);
- «а нужно ли это вообще?» → только если `f` реально долгая: на дешевой функции
  накладные расходы планировщика съедят выигрыш.

### Правильно синхронизировать выполнение нескольких горутин

[sync_goroutines](examples/live_coding/sync_goroutines/main.go) — четыре способа в одном файле.

| Надо | Инструмент |
| --- | --- |
| дождаться всех | `sync.WaitGroup` |
| дождаться N результатов и собрать их | канал с буфером N, ровно N чтений |
| первая ошибка отменяет остальных | `errgroup.Group` (в примере — своя реализация на `Once` + `context`) |
| выполнить ровно один раз | `sync.Once`, `OnceFunc`, `OnceValue`, `OnceValues` |
| защитить общее поле | `sync.Mutex` / `RWMutex` |
| счетчик | `atomic.Int64` |

Чего делать нельзя: `time.Sleep` вместо синхронизации, `wg.Add` внутри горутины,
копирование `WaitGroup`/`Mutex`, закрытие канала со стороны читателя.

## 2. Теория

### Как работают горутины

[scheduler](examples/runtime/scheduler/main.go)

Горутина — это функция, выполняемая рантаймом Go поверх потоков ОС, со своим
стеком и контекстом. Планировщик работает по модели **G-M-P**:

- **G** — горутина: стек (от 2 КБ, растет копированием) + сохраненные регистры;
- **M** — поток ОС;
- **P** — «право исполнять Go-код», количество = `GOMAXPROCS` (по умолчанию число ядер).

Чтобы выполнять G, потоку M нужен P. У каждого P своя локальная очередь на 256 горутин
плюс глобальная очередь; простаивающий P **ворует половину очереди** у соседа (work stealing).

Почему это дешево: создание горутины — это выделение маленького стека в куче, а не
системный вызов; переключение делает рантайм в user space, без перехода в ядро.
В примере 100 000 горутин занимают около 600 байт каждая.

Когда происходит переключение:

- блокирующая операция: канал, мьютекс, `time.Sleep`, сеть;
- системный вызов: M блокируется вместе с G, но **P отдается другому M**, поэтому
  остальные горутины продолжают работать;
- сетевой ввод-вывод не блокирует M вообще: netpoller (epoll/kqueue) паркует G
  и будит ее, когда сокет готов;
- с Go 1.14 планировщик **вытесняющий**: рантайм шлет потоку сигнал примерно
  раз в 10 мс, поэтому даже бесконечный цикл без вызовов функций не вешает программу;
- `runtime.Gosched()` — уступить явно (нужно редко).

### Чем отличаются буферизированный и небуферизированный каналы

[buffered_vs_unbuffered](examples/theory/buffered_vs_unbuffered/main.go)

**Небуферизованный** — рандеву: отправка завершается только тогда, когда другая
горутина забрала значение. Это одновременно передача данных и синхронизация
(гарантия «получено», happens-before между горутинами).

**Буферизованный** — очередь на N элементов: отправка возвращается сразу, пока есть
место, отправитель не знает, прочитали ли его.

| | `make(chan T)` | `make(chan T, n)` |
| --- | --- | --- |
| отправка | ждет получателя | мгновенна, пока есть место |
| чтение | ждет отправителя | мгновенно, пока буфер не пуст |
| `len`/`cap` | 0 / 0 | занято / n |
| дает | синхронизацию | развязку по времени |

Когда буфер оправдан: известно точное число результатов; канал как семафор (буфер = лимит);
буфер 1, чтобы горутина отдала результат и завершилась, даже если по таймауту ее уже никто не ждет.
Большой буфер систему не ускоряет — он прячет то, что потребитель не успевает, и растит задержку.

Что паникует: запись в закрытый канал, повторный `close`, `close(nil)`.
Что не паникует: чтение из закрытого (отдает буфер, потом нулевые значения с `ok == false`).
Операции с nil-каналом блокируются навсегда — этим отключают ветвь `select`.

### Что происходит при копировании мьютекса

[mutex_copy](examples/problems/mutex_copy/main.go)

Копируется **состояние**. `sync.Mutex` — обычная структура `{state int32; sema uint32}`,
поэтому копия компилируется молча и становится **отдельной блокировкой**:
горутины начинают защищать разные мьютексы, взаимного исключения больше нет.
Если скопировать залоченный мьютекс, копия навсегда останется залоченной,
и первый же `Lock` на ней повиснет.

Как это выглядит в реальном коде: метод с приемником по значению у структуры,
которая содержит мьютекс, или передача такой структуры параметром/возврат по значению.

Ловится `go vet` (анализатор copylocks): `passes lock by value`, `assignment copies lock value`.
`go vet` входит в `go test`, так что обычно проблема всплывает сама.

Правило: `Mutex`, `RWMutex`, `WaitGroup`, `Once`, `atomic.*` и все структуры, которые их
содержат, живут только по указателю. Проверить демонстрацию:
`go vet -tags copylocks ./problems/mutex_copy`.

### Как устроен сборщик мусора

[gc](examples/runtime/gc/main.go)

Конкурентный **трехцветный mark-and-sweep с барьером записи**. Не перемещающий
(адреса стабильны, поэтому указатели можно отдавать в C), не поколенческий,
настроен на минимальную паузу, а не на пропускную способность.

Цикл:

1. **sweep termination** — короткий stop-the-world, включается барьер записи;
2. **mark** — конкурентно с программой обходим граф достижимости от корней
   (стеки всех горутин + глобальные переменные); барьер записи перехватывает
   изменения указателей во время обхода, иначе живой объект можно было бы потерять;
3. **mark termination** — второй короткий STW, барьер выключается;
4. **sweep** — освобождение идет конкурентно, по мере новых аллокаций.

Пауз мира две, обе микросекундные (цель — до 500 мкс, на практике десятки).
Основная стоимость GC не в паузах, а в CPU: примерно четверть времени,
включая ассист — горутина, которая много аллоцирует, сама помогает маркировать.

Настройки:

- `GOGC` (по умолчанию 100) — следующая сборка, когда куча вырастет вдвое
  относительно живых данных; больше значение → реже сборки, больше памяти;
- `GOMEMLIMIT` — мягкий лимит всей памяти рантайма: у границы GC начинает частить.
  Типовая связка для контейнера: `GOGC=off` + `GOMEMLIMIT` чуть ниже лимита пода;
- посмотреть вживую: `GODEBUG=gctrace=1`.

Что уменьшает нагрузку на GC: меньше указателей (GC обходит именно их), преаллокация
срезов и map, переиспользование буферов, значения вместо указателей в срезах.
Финализаторы (`runtime.SetFinalizer`) есть, но полагаться на них нельзя — порядок и
время вызова не гарантированы; ресурсы освобождают через `defer`/`Close`.

## 3. Примитивы языка

Подробный разбор с примерами — в [конспекте](../idiomatic-go/conspect.md#3-составные-типы).
Здесь только то, что реально спрашивают.

### Срезы и массивы

Массив — значение фиксированного размера, **размер входит в тип** (`[3]int` и `[4]int` — разные типы),
копируется целиком. Срез — дескриптор из трех полей: указатель на массив, длина, емкость.

- `append` при `len == cap` выделяет новый массив (до 256 элементов рост ×2, дальше ~×1.25)
  и копирует данные — поэтому `make([]T, 0, n)`, когда размер известен;
- подсрез **разделяет память** с родителем: `append` в него затирает элементы родителя,
  пока хватает cap → [confusing_slices](../idiomatic-go/examples/02_composite/confusing_slices/main.go);
  лечится full slice expression `x[low:high:max]`;
- срез из 10 элементов, взятый от массива на 10 млн, **держит весь массив** — классическая
  «утечка без утечки», лечится `copy` → [memory](examples/problems/memory/main.go);
- сравнивать `==` нельзя (только с nil), для сравнения — `slices.Equal`;
- `nil`-срез и пустой срез: у обоих `len == 0`, но `nil` удобнее по умолчанию, а `[]T{}` —
  когда важен JSON (`[]` вместо `null`);
- передача в функцию копирует дескриптор: изменения элементов видны, `append` — нет.

### Словари

[map_internals](examples/theory/map_internals/main.go)

Хеш-таблица из бакетов по 8 пар; старшие 8 бит хеша (tophash) быстро отсеивают несовпадения,
младшие выбирают бакет. При ~6.5 элементов на бакет таблица растет вдвое,
перехеширование **инкрементальное** — по паре бакетов на операцию.

Отсюда все ответы:

- **порядок обхода случайный** и специально рандомизирован (защита от Hash DoS);
- **адрес элемента взять нельзя** (`&m[k]` и `m[k].Field++` не компилируются) — при росте
  элементы переезжают; для изменяемых значений держат `map[K]*V`;
- запись в nil-map — паника, чтение — нулевое значение;
- **конкурентная запись — fatal error** «concurrent map writes», его нельзя перехватить
  `recover`; защита — `RWMutex` или `sync.Map` (последняя оправдана только для
  «записали один раз, читаем много» и непересекающихся наборов ключей);
- `delete` не отдает память: бакеты остаются за map, полное освобождение — только пересоздание;
- ключ обязан быть сравнимым: срез, map и функция ключом быть не могут;
  структура-ключ с полем-срезом — тоже нет.

### Строки

Строка — неизменяемая пара `{указатель на байты, длина}`, всегда UTF-8.

- индексация и срез идут **в байтах**: `s[0]` — это `byte`, а срез может разрезать руну пополам;
- `for i, r := range s` идет по **рунам**, индекс прыгает на 1–4 байта;
- `len(s)` — байты, число символов — `utf8.RuneCountInString`;
- `[]byte(s)` и `[]rune(s)` копируют данные (конвертация не бесплатна);
- конкатенация в цикле — квадратичная: каждая `+` создает новую строку,
  для сборки нужен `strings.Builder` (или `bytes.Buffer`);
- подстрока держит **весь исходный буфер** — `strings.Clone` копирует нужный кусок;
- сравнение строк — побайтовое, `==` работает.

### Структуры данных

- структура сравнима, если сравнимы все поля; наличие среза/map/функции делает ее несравнимой;
- пустая структура `struct{}` не занимает памяти — отсюда `map[T]struct{}` как множество
  и `chan struct{}` как сигнал;
- порядок полей влияет на размер из-за выравнивания: `bool,int64,bool` — 24 байта,
  `bool,bool,int64` — 16 → [unsafe_sizeof_offsetof](../idiomatic-go/examples/14_reflect_unsafe/unsafe_sizeof_offsetof/main.go);
- встраивание — это композиция, а не наследование: динамической диспетчеризации нет,
  метод встроенного типа не видит переопределение во внешнем
  → [no_dynamic_dispatch](../idiomatic-go/examples/06_interfaces/no_dynamic_dispatch/main.go);
- теги полей — просто строки, их читает рефлексия (`encoding/json`, ORM).

### Интерфейсы

Интерфейс внутри — **пара указателей: тип и значение**. Отсюда главные вопросы:

- **типизированный nil**: `var p *T = nil; var i I = p; i != nil` — тип задан, значит интерфейс не nil
  → [interface_nil](../idiomatic-go/examples/06_interfaces/interface_nil/main.go);
- **набор методов**: у `*T` — методы с обоими видами приемников, у `T` — только со значением,
  поэтому значение не реализует интерфейс с указательными методами
  → [method_set](../idiomatic-go/examples/06_interfaces/method_set/main.go);
- реализуются **неявно**, поэтому интерфейс объявляют на стороне потребителя, а не рядом с реализацией;
- «принимай интерфейсы, возвращай структуры»: добавление метода в интерфейс ломает всех, кто его реализует;
- сравнение интерфейсов через `==` **паникует**, если внутри несравнимый тип (срез, map);
- значение, положенное в интерфейс, обычно уезжает в кучу — это цена абстракции;
- пустой интерфейс `any` нужен на границе (JSON, БД), в бизнес-логике это запах.

### Деферы

[defer_pitfalls](examples/theory/defer_pitfalls/main.go)

- выполняется при выходе из функции, **после** вычисления `return`, порядок LIFO;
- **аргументы вычисляются в момент объявления**, тело — потом;
- `defer` в цикле копит ресурсы до конца функции — тело цикла выносят в отдельную функцию;
- `defer` + **именованный результат** — единственный способ подменить возвращаемое значение:
  на этом держатся обертывание ошибок и `recover`;
- с Go 1.14 обычный defer инлайнится и стоит единицы наносекунд, но в горячем цикле его
  все равно заменяют явным вызовом.

### Паники

- паника раскручивает стек, выполняя `defer`; неперехваченная паника **в любой горутине**
  роняет весь процесс — `recover` в main не спасет от паники в другой горутине;
- `recover()` работает **только внутри `defer`** и только в той же горутине;
- в библиотеке паника наружу выходить не должна — конвертируй в `error`;
- в сервисе паникой обычно не пользуются, но обработчик HTTP оборачивают recover-middleware,
  чтобы один запрос не убил процесс;
- **fatal error — это не паника** и не перехватывается: `concurrent map writes`,
  `all goroutines are asleep - deadlock!`, out of memory, переполнение стека.

## 4. Конкурентность

### Горутины

См. [«Как работают горутины»](#как-работают-горутины). Что добавить на этом вопросе:

- запуская горутину, сразу отвечай, **как она завершится** — иначе утечка;
- значение переменной цикла с Go 1.22 создается заново на каждой итерации,
  до этого требовалось передавать параметром
  → [loop_var_capture](../idiomatic-go/examples/10_concurrency/loop_var_capture/main.go);
- `main` не ждет горутины: выход из `main` завершает процесс;
- горутина не имеет ни ID, ни приоритета, ее нельзя убить снаружи —
  только попросить завершиться через контекст или канал.

### Каналы

См. [«Буферизированный и небуферизированный»](#чем-отличаются-буферизированный-и-небуферизированный-каналы).
Что еще спрашивают:

- значение читает **ровно одна** горутина — канал не broadcast;
  рассылка всем делается закрытием канала (`close(done)` будит всех);
- закрывает **писатель**; если писателей несколько — отдельная горутина после `WaitGroup`;
- `for v := range ch` завершается только при закрытии канала;
- `select` из готовых ветвей выбирает **случайную** — поэтому голодания не бывает;
  `default` делает операцию неблокирующей;
- присвоение `ch = nil` отключает ветвь select навсегда
  → [select_disable_case](../idiomatic-go/examples/10_concurrency/select_disable_case/main.go);
- каналы дают happens-before: отправка происходит раньше завершения соответствующего чтения,
  закрытие — раньше чтения нулевого значения.

### Примитивы синхронизации

| Примитив | Для чего |
| --- | --- |
| `sync.Mutex` | взаимное исключение, критическая секция |
| `sync.RWMutex` | много читателей или один писатель; выгоден при «часто читаем, редко пишем» |
| `sync.WaitGroup` | дождаться завершения N горутин |
| `sync.Once` / `OnceValue` | ленивая инициализация ровно один раз |
| `sync.Cond` | ждать условия (в Go почти всегда заменяется каналом) |
| `sync.Pool` | переиспользование дорогих объектов, чистка через `Reset` |
| `sync/atomic` | счетчики и флаги без блокировок |
| `errgroup` | группа горутин с отменой по первой ошибке |

Правила: всегда `defer Unlock` сразу после `Lock`; мьютексы **не реентерабельны**;
не звать чужой код под блокировкой; не копировать примитивы; при нескольких замках —
единый порядок захвата. Каналы — когда данные передаются между горутинами,
мьютекс — когда защищается поле структуры.

### Контексты

- один интерфейс: `Done()`, `Err()`, `Deadline()`, `Value()`; передается **первым параметром**,
  в структурах не хранится;
- `Background()` / `TODO()` — корни; `WithCancel`, `WithTimeout`, `WithDeadline` (+ варианты `...Cause`)
  порождают дочерние; отмена идет только **вниз** по дереву;
- `cancel` вызывать всегда (`defer cancel()`), иначе утекут таймер и дочерние горутины;
- контекст **сам ничего не прерывает** — он закрывает `Done()`, а реагировать должен твой код
  → [own_cancellation](../idiomatic-go/examples/12_context/own_cancellation/main.go);
- `WithValue` — только для сквозных данных запроса (trace id, пользователь), ключ —
  неэкспортируемый тип, а не строка; обязательные аргументы через контекст не передают;
- в HTTP: `r.Context()` отменяется при разрыве соединения клиентом; дедлайн на запрос удобно
  ставить middleware → [timeout_middleware](../idiomatic-go/examples/12_context/timeout_middleware/main.go).

## 5. Runtime

### Как работает планировщик

[scheduler](examples/runtime/scheduler/main.go) — модель G-M-P разобрана
в разделе [«Как работают горутины»](#как-работают-горутины). Что важно добавить именно про планировщик:

- **work stealing**: простаивающий P забирает половину локальной очереди у соседнего P,
  а если очередей нет — берет из глобальной и из netpoller;
- локальная очередь на 256 горутин, при переполнении половина уезжает в глобальную;
- новорожденная горутина попадает в **runnext** — слот «выполнить следующей» у текущего P,
  поэтому только что созданная горутина стартует быстро;
- **sysmon** — служебный поток без P: отбирает P у горутин, которые работают дольше 10 мс,
  забирает P у M, зависших в системном вызове, и запускает GC;
- вытеснение асинхронное (с Go 1.14, через сигнал), поэтому счетный цикл не блокирует остальных;
- `GOMAXPROCS` = число P = сколько горутин исполняется **параллельно**; в контейнере
  рантайм видит ядра хоста, а не лимит cgroup — отсюда `automaxprocs` или явная установка;
- посмотреть: `GODEBUG=schedtrace=1000` (+`scheddetail=1`), трассировка — `runtime/trace` и `go tool trace`.

### Как устроены горутины

- структура `g` в рантайме: указатель на стек, статус, ссылка на M/P, поле для паники,
  ссылка на родителя (для трассировок);
- стек начинается с **2 КБ** и растет: при нехватке рантайм выделяет вдвое больший кусок
  и **копирует** старый, поправляя указатели (поэтому GC не перемещает объекты, а стеки — да);
- максимальный размер стека по умолчанию 1 ГБ (`debug.SetMaxStack`), при превышении —
  fatal error «stack overflow»;
- в примере 100 000 живых горутин занимают порядка 600 байт каждая: столько остается
  после первичного сжатия стека, если горутина ничего не делает;
- состояния: `_Grunnable` (в очереди), `_Grunning`, `_Gwaiting` (канал, мьютекс, сеть),
  `_Gsyscall`, `_Gdead` (лежит в пуле для переиспользования);
- у горутины нет ID и приоритета — специально, чтобы никто не строил на них логику.

### Как устроен сборщик мусора

См. [«Как устроен сборщик мусора»](#как-устроен-сборщик-мусора) — там полный ответ
и [пример с замерами](examples/runtime/gc/main.go).

### Как происходят аллокации памяти

[memory](examples/problems/memory/main.go)

Сначала решается, **где** размещать: это делает **escape analysis** на этапе компиляции.
В стек попадает то, что не переживает кадр функции и имеет известный размер;
в кучу — если указатель возвращается наружу, значение кладут в интерфейс,
размер неизвестен на этапе компиляции или объект слишком велик.
Посмотреть решения компилятора: `go build -gcflags='-m'`.

Стек дешев: выделение — сдвиг указателя, освобождение — возврат кадра, GC не участвует.

Куча: аллокатор в стиле **tcmalloc**, три уровня:

- **mcache** — кэш у каждого P, без блокировок; отсюда берутся мелкие объекты;
- **mcentral** — общий список спанов на каждый размерный класс (~70 классов, до 32 КБ);
- **mheap** — арены по 64 МБ у ОС; объекты больше 32 КБ выделяются напрямую в mheap.

Объекты округляются до ближайшего размерного класса (запрос 17 байт → блок 24 байта),
отсюда внутренняя фрагментация. Освобожденная память сначала возвращается в mcentral/mheap
и лишь потом отдается ОС (`MADV_FREE`/`MADV_DONTNEED`), поэтому RSS падает не сразу.

Что уменьшает число аллокаций: `make` с нужным cap, переиспользование буферов,
`sync.Pool`, значения вместо указателей, `strings.Builder` вместо конкатенации.
Измерять — `go test -bench=. -benchmem` (`B/op`, `allocs/op`) и `pprof -alloc_space`.

## 6. Задачи

### 1) Есть несколько источников данных — как их объединишь?

[fan_in](examples/live_coding/fan_in/main.go)

Fan-in: по горутине на источник, все пишут в один общий канал; общий канал закрывает
**одна** горутина после `wg.Wait()`.

```go
var wg sync.WaitGroup
wg.Add(len(chans))
for _, ch := range chans {
    go func(ch <-chan T) {
        defer wg.Done()
        for v := range ch {
            select {
            case out <- v:
            case <-ctx.Done(): return   // читатель ушел — не виснем
            }
        }
    }(ch)
}
go func() { wg.Wait(); close(out) }()   // единственное место close
```

Продолжения, которые последуют:

- «порядок важен?» — fan-in его не сохраняет, нужен — нумеруй элементы или собирай в срез по индексу;
- «один источник завис?» — `context.WithTimeout` на весь сбор;
- «нужен только первый ответ?» — `select` по каналам + `cancel()` остальным (паттерн «первый выигравший»);
- «источников тысячи?» — ограничить параллелизм семафором (следующая задача);
- «нужны ошибки?» — передавай `struct{Val T; Err error}` или используй `errgroup`.

### 2) Как ограничить количество параллельных запросов?

[limit_concurrency](examples/live_coding/limit_concurrency/main.go)

Семафор на буферизованном канале, буфер = лимит:

```go
sem := make(chan struct{}, limit)
sem <- struct{}{}          // занять слот (заблокируется, если слотов нет)
defer func() { <-sem }()   // освободить
```

Два принципиально разных поведения при исчерпании лимита:

1. **ждать** свободный слот — обычная очередь (пример выше);
2. **сразу отказать** — противодавление: `select` с `default` → ошибка/HTTP 429.
   Так система не копит очередь, которую все равно не разгребет.

Смежные варианты: `errgroup.Group.SetLimit(n)`; ограничение по скорости, а не по параллелизму
(`time.Ticker`, `golang.org/x/time/rate` — N запросов в секунду);
для HTTP-клиента — `http.Transport{MaxConnsPerHost: n}`.

## 7. Data race, утечки, блокировки, память

### Data race

[data_race](examples/problems/data_race/main.go)

Гонка — это когда две горутины обращаются к одной переменной, **хотя бы одна пишет**,
и между обращениями нет отношения happens-before. Это неопределенное поведение,
а не просто «неверное число»: `counter++` — три операции (чтение, инкремент, запись),
плюс компилятор и процессор вправе переупорядочить доступы.

Как чинить, от простого к сложному:

1. не делить состояние вообще — у каждой горутины свой кусок, потом слияние (шардирование);
2. `atomic` для одиночных счетчиков и флагов;
3. `Mutex`/`RWMutex` для составного состояния;
4. канал, если данные логично **передавать**, а не защищать.

Ловится `-race` (`go test -race`, `go run -race`): детектор видит только те гонки, которые
реально произошли на этом прогоне, замедляет программу в 2–20 раз, в прод не идет —
поэтому его включают на тестах в CI.

### Утечки

[goroutine_leak](examples/problems/goroutine_leak/main.go)

Заблокированная навсегда горутина держит стек и все, на что ссылается; GC ее не соберет,
потому что работающая горутина — это корень.

Четыре типовых источника:

- писатель заблокирован на отправке, потому что читатель ушел раньше (лечение — `select` с `ctx.Done()`);
- забытый `time.Ticker` без `Stop` (у `time.Tick` его вообще нет);
- незакрытое `resp.Body` — соединение не возвращается в пул;
- ожидание на канале, в который уже никто не напишет.

Как обнаруживать: `runtime.NumGoroutine()` как метрика (монотонный рост = утечка),
`net/http/pprof` → `/debug/pprof/goroutine?debug=1` покажет стеки и место блокировки,
в тестах — сравнение числа горутин до и после (`go.uber.org/goleak`).

Утечки бывают не только горутин: незакрытые файлы и соединения, растущие глобальные map,
подписки без отписки, `time.AfterFunc` без `Stop`.

### Блокировки

[deadlock](examples/problems/deadlock/main.go)

Типовые сценарии вечного ожидания:

- **повторный `Lock`** в той же горутине — мьютексы в Go не реентерабельны;
  частный случай: публичный метод под замком вызывает другой публичный метод
  (решение — пара `f` / `fLocked`);
- **разный порядок захвата** двух мьютексов в двух горутинах;
- запись в небуферизованный канал без читателя, чтение из канала, куда никто не пишет;
- `RLock` → `Lock` в одной горутине: «повысить» read-lock до write-lock нельзя;
- взаимное ожидание горутин через каналы (лечится `select`).

Если **все** горутины заснули, рантайм печатает `fatal error: all goroutines are asleep - deadlock!`
со стеками. Но в реальном сервисе живой HTTP-сервер этому помешает — зависание будет выглядеть
как «часть ручек перестала отвечать», диагноз ставится по `/debug/pprof/goroutine`.

Профилактика: держать критическую секцию короткой, всегда `defer Unlock`,
не вызывать под блокировкой чужой код (колбэки, интерфейсы, HTTP), единый порядок захвата.

### Проблемы с памятью

[memory](examples/problems/memory/main.go)

- **лишние аллокации**: рост среза без `cap`, конкатенация строк в цикле, `[]byte(s)` в горячем пути;
- **удержание памяти**: подсрез или подстрока держат весь исходный буфер (лечение — `copy`,
  `strings.Clone`); растущая глобальная map без вытеснения; элементы, оставшиеся в срезе после
  «удаления» через `s = s[:0]` (указатели надо занулять);
- **escape analysis**: указатель на локальную структуру уводит ее в кучу — `go build -gcflags='-m'`;
- **фрагментация**: объекты округляются до размерного класса, освобожденное не сразу отдается ОС,
  поэтому RSS падает с задержкой;
- **sync.Pool** помогает только для дорогих долгоживущих объектов и обязательно с `Reset`;
  пул чистится при каждом GC, так что кэшем он не является;
- измерять: `go test -bench=. -benchmem`, `pprof -inuse_space` (что занято сейчас)
  и `-alloc_space` (сколько выделено суммарно), `GODEBUG=gctrace=1` для общей картины.
