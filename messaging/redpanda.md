# Redpanda

[README](README.md) · [Kafka](kafka.md) · [RabbitMQ](rabbitmq.md) · **Redpanda**

Коротко: **Redpanda — это Kafka, переписанная на C++**. Тот же протокол,
те же клиенты, та же модель данных (топики, партиции, offset, consumer
groups) — но один бинарник вместо JVM + ZooKeeper.

Встречается заметно реже Kafka, поэтому на собеседовании обычно
достаточно понимать: что это, чем отличается и когда имеет смысл.
Вся [модель данных Kafka](kafka.md#1-модель-данных) применима к Redpanda
без изменений, повторять её здесь не нужно.

---

## В чём идея

Kafka создавалась в 2011 году под железо того времени: медленные диски,
JVM, вынесенные метаданные в ZooKeeper. Redpanda (2019) написана под
современные NVMe и многоядерные процессоры с нуля:

| | Kafka | Redpanda |
|---|---|---|
| Язык / рантайм | Scala/Java, JVM | C++ (фреймворк Seastar), без GC |
| Метаданные | KRaft (раньше ZooKeeper) | Raft, встроен изначально |
| Развёртывание | брокеры + (исторически) ZK | **один бинарник**, без зависимостей |
| Работа с диском | через page cache ОС | своя подсистема, прямой доступ (DMA) |
| Модель потоков | пулы потоков, блокировки | **thread-per-core**: ядро = shard, без общей памяти |
| Репликация | ISR + контроллер | Raft на каждую партицию |
| Настройка | сотни параметров | автотюнинг под железо (`rpk redpanda tune`) |
| Лицензия | Apache 2.0 | BSL (source available) + Enterprise-фичи |

Практический выигрыш — не столько «больше сообщений в секунду», сколько
**предсказуемые хвостовые задержки** (p99 без пауз GC) и **меньше узлов и
настройки** на ту же нагрузку.

### Совместимость

Redpanda реализует **протокол Kafka**, а не просто похожий API. Значит:

- работают существующие клиенты (`franz-go`, `sarama`, `confluent-kafka`,
  Spring Kafka) — меняется только адрес брокера;
- работают Kafka Connect, Kafka Streams, Flink, Debezium, ksqlDB;
- Schema Registry и HTTP-прокси (REST) встроены, отдельно ставить не надо;
- `rpk` — единый CLI вместо набора `kafka-*.sh` скриптов.

Чего может не хватать: точечные вещи вроде отдельных admin-API, некоторых
метрик JMX, поведения на уровне внутренностей брокера. Для обычного
приложения миграция — это правка адреса подключения.

## Что есть сверх Kafka

- **Tiered storage** — старые сегменты уезжают в S3/GCS, локальный диск
  держит только горячее. В Kafka это появилось позже и в open source
  ограниченнее.
- **Data transforms** — WASM-функции прямо в брокере: фильтрация,
  маскирование, преобразование топика в топик без отдельного сервиса
  потоковой обработки.
- **Iceberg topics** — топик автоматически материализуется в таблицу
  Apache Iceberg, читается аналитическими движками без ETL.
- **Один процесс** — Schema Registry, REST-прокси и брокер в одном
  бинарнике. В Docker поднимается одной командой, что заметно упрощает
  локальную разработку и CI.

## Когда её берут

**Есть смысл:**

- Нужна семантика Kafka, но нет людей на эксплуатацию Kafka. Маленькая
  команда без выделенного платформенного инженера.
- Важны низкие и стабильные задержки: финтех, торговля, real-time
  антифрод, где p99 в 50 мс — это уже проблема.
- Хочется меньше железа: типично те же объёмы на меньшем числе узлов.
- Edge / on-premise / IoT: один бинарник без JVM ставится куда угодно,
  вплоть до маленьких серверов на объекте.
- Локальная разработка и тесты: контейнер стартует за секунды, не
  требует ZooKeeper.

**Скорее не стоит:**

- Уже есть работающая Kafka и команда, которая её знает. Миграция ради
  миграции не окупается.
- Используется managed-решение (MSK, Confluent Cloud, Яндекс/Cloud
  Managed Kafka) — эксплуатация и так не ваша забота.
- Нужна максимально большая экосистема, куча готовых рецептов,
  специалистов на рынке и опыт эксплуатации у сотен компаний.
- Лицензия имеет значение: Redpanda под BSL (source available, не OSI
  open source), часть возможностей — только в Enterprise. Kafka — Apache 2.0.
- Нужны вещи, которых нет ни у Kafka, ни у Redpanda: маршрутизация,
  приоритеты, отложенная доставка, per-message ack. Это к
  [RabbitMQ](rabbitmq.md).

## Что важно не перепутать

Redpanda **не** является альтернативой RabbitMQ. Она решает те же задачи,
что Kafka, и имеет ровно те же ограничения:

- порядок только внутри партиции;
- параллелизм ограничен числом партиций;
- нет роутинга, приоритетов и отложенной доставки;
- ретраи и DLQ строятся приложением
  ([retry-топики](kafka.md#8-ретраи-и-dlq));
- exactly-once — только внутри кластера.

Выбор «Kafka или Redpanda» — про эксплуатацию и задержки. Выбор
«Kafka/Redpanda или RabbitMQ» — про модель данных, и он гораздо важнее.

## Для собеседования

- **Что это:** Kafka-совместимый стриминговый брокер на C++, один бинарник,
  без JVM и ZooKeeper, репликация через Raft.
- **Зачем:** ниже хвостовые задержки (нет GC), проще эксплуатация, меньше
  узлов на ту же нагрузку.
- **Совместимость:** протокол Kafka — существующие клиенты, Connect,
  Streams, Debezium работают; Schema Registry и REST-прокси встроены.
- **Сверх Kafka:** tiered storage в S3, WASM-трансформации, Iceberg-топики.
- **Ограничения:** лицензия BSL, меньше экосистема и сообщество, часть
  фич — Enterprise.
- **Когда:** нужна Kafka без её операционной сложности, важна latency,
  edge/on-premise, локальная разработка. Не когда Kafka уже работает или
  используется managed-сервис.
