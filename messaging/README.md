# Брокеры сообщений

Конспекты по обмену сообщениями между сервисами: как устроены, чем
отличаются и что где применяют.

| Файл | О чём |
|---|---|
| [Kafka](kafka.md) | Распределённый лог: партиции, offset, consumer groups, гарантии, retention |
| [RabbitMQ](rabbitmq.md) | Классический брокер AMQP: exchange, маршрутизация, ack, DLX, quorum queues |
| [Redpanda](redpanda.md) | Kafka-совместимая альтернатива на C++: чем отличается и когда нужна |

Смежное: [Transactional Outbox](../patterns/outbox.md) — как атомарно
записать в БД и опубликовать событие (проблема dual write актуальна для
любого брокера).

---

## Главное различие

Всё остальное вытекает из одного: **что происходит с сообщением после
прочтения**.

```
RabbitMQ                              Kafka
──────────                            ─────
очередь = список заданий              топик = журнал записей

  [msg][msg][msg]                       [0][1][2][3][4][5]...
        │                                     ▲     ▲
   consumer ack                          group A   group B
        │                                offset=2  offset=4
   ✗ удалено                             данные остаются
```

- RabbitMQ: сообщение **доставляется и исчезает**. Это задание, которое
  надо выполнить. Брокер помнит состояние каждого сообщения.
- Kafka: сообщение **записывается в лог** и лежит там до истечения
  retention. Это факт, который произошёл. Брокер помнит только позицию
  каждой группы.

## Сравнение

| | [RabbitMQ](rabbitmq.md) | [Kafka](kafka.md) | [Redpanda](redpanda.md) |
|---|---|---|---|
| Модель | очередь заданий | распределённый лог | то же, что Kafka |
| После чтения | удаляется | остаётся до retention | остаётся до retention |
| Перечитать историю | нет (кроме streams) | да, с любого offset | да |
| Маршрутизация | богатая (direct/fanout/topic/headers) | нет: топик и ключ | нет |
| Доставка | push + prefetch | pull | pull |
| Подтверждение | на каждое сообщение, можно отклонить | commit offset (позиция) | commit offset |
| Порядок | FIFO в очереди, ломается при N потребителях | строгий внутри партиции | внутри партиции |
| Параллелизм | сколько угодно потребителей на очередь | не больше числа партиций | не больше числа партиций |
| Ретраи и DLQ | встроены (DLX, TTL, `x-delivery-limit`) | руками: retry-топики + DLT | руками |
| Отложенная доставка | да (TTL+DLX, плагин) | нет | нет |
| Приоритеты | да (classic) | нет | нет |
| Пропускная способность | десятки тысяч сообщений/с | миллионы/с | миллионы/с, ниже p99 |
| Хранение | оперативное, очередь должна разгребаться | дни и недели, терабайты | + tiered storage в S3 |
| Протоколы | AMQP, MQTT, STOMP | свой | Kafka-протокол |
| Эксплуатация | средняя | сложная (JVM, партиции, ребалансы) | проще Kafka |

## Что выбрать

**RabbitMQ**, когда сообщение — это **команда «сделай»**:

- фоновые задачи: письма, отчёты, обработка файлов;
- сложные правила маршрутизации между сервисами;
- нужны приоритеты, отложенная доставка, ретраи с задержкой;
- умеренный поток, важна простота и гибкость.

**Kafka**, когда сообщение — это **факт «произошло»**:

- поток событий, который читают несколько независимых потребителей;
- нужен replay: новый сервис должен прочитать историю;
- большие объёмы: логи, метрики, кликстрим, CDC;
- потоковая обработка и аналитика.

**Redpanda** — когда подходит модель Kafka, но не хочется её
эксплуатировать: маленькая команда, важны стабильные задержки, edge или
on-premise.

Совмещать нормально и распространено: Kafka как шина событий между
доменами, RabbitMQ внутри домена под задачи воркеров.

## Вопрос-ловушка

> «Kafka же быстрее — зачем вообще RabbitMQ?»

Скорость — не тот критерий. RabbitMQ умеет то, чего у Kafka нет
конструктивно: отклонить **одно** сообщение из середины, доставить
через 30 минут, разложить один поток по десятку получателей разными
правилами, поднять приоритет, ответить в RPC-стиле.

И наоборот: Kafka даёт то, чего нет у RabbitMQ — историю, которую можно
перечитать сколько угодно раз сколь угодно многим потребителям, и
линейное масштабирование по партициям.

Правильный ответ на собеседовании: не «что быстрее», а **«сообщение здесь
— задание или событие?»**
