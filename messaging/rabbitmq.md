# RabbitMQ

[README](README.md) · [Kafka](kafka.md) · **RabbitMQ** · [Redpanda](redpanda.md)

RabbitMQ — классический **брокер сообщений** с умной маршрутизацией.
Реализует протокол AMQP 0-9-1 (плюс MQTT, STOMP, AMQP 1.0 через
плагины/нативно в 4.x).

Главное отличие от [Kafka](kafka.md): здесь сообщение — **задание**, а не
запись в журнале. Оно кладётся в очередь, доставляется потребителю, тот
подтверждает — и сообщение **исчезает**. Вся сила RabbitMQ в том, что
происходит *до* очереди: гибкая маршрутизация через exchange.

## 1. Модель AMQP

```
producer ──publish──► ┌──────────┐ ──binding──► ┌────────┐ ──push──► consumer
   (routing key)      │ exchange │              │ queue  │ ◄──ack────
                      └──────────┘ ──binding──► └────────┘
                                                ┌────────┐
                                   ──binding──► │ queue  │
                                                └────────┘
```

| Понятие | Что это |
|---|---|
| **Exchange** | Точка приёма. Сам ничего не хранит, только решает, в какие очереди положить копию |
| **Queue** | Собственно хранилище сообщений. FIFO |
| **Binding** | Связь exchange → queue, обычно с шаблоном routing key |
| **Routing key** | Строка, которую продюсер вешает на сообщение: `order.created.eu` |
| **Vhost** | Логическая изоляция: свои exchange/queue/права. Аналог namespace |
| **Channel** | Логическое соединение внутри одного TCP. Работать надо через каналы, а не плодить соединения |

Ключевой момент: **продюсер не знает про очереди**. Он публикует в
exchange с routing key. Кто это получит — определяется биндингами,
которые настраивает потребитель. Добавить нового получателя = навесить
новый биндинг, продюсер не меняется.

> В [Kafka](kafka.md) этого слоя нет вообще: продюсер пишет в конкретный
> топик, а «кому надо» решают потребители, читая топик со своим offset.
> Гибкость маршрутизации — за RabbitMQ, гибкость перечитывания — за Kafka.

Если сообщение не подошло ни одному биндингу — оно **молча пропадает**
(если не выставлен флаг `mandatory` с обработкой возврата или не задан
alternate exchange). Классическая ошибка новичка.

## 2. Типы exchange

### direct — точное совпадение routing key

```
                   ┌── "payment" ──► queue: payments
exchange (direct) ─┤
                   └── "email"   ──► queue: emails
```

Ровно один ключ — ровно один набор очередей. Основа обычной очереди
заданий.

### fanout — всем подряд, routing key игнорируется

```
                   ┌──► queue: audit
exchange (fanout) ─┼──► queue: cache-invalidate
                   └──► queue: search-index
```

Broadcast. Каждая очередь получает **свою копию** сообщения.

### topic — шаблоны

Routing key — слова через точку: `order.created.eu`. Шаблон биндинга:

| Символ | Значение |
|---|---|
| `*` | ровно одно слово |
| `#` | ноль или больше слов |

```
"order.created.eu" попадёт в очереди с биндингами:
  order.created.eu   ✓ точное совпадение
  order.*.eu         ✓ одно слово вместо *
  order.#            ✓ # покрывает "created.eu"
  #                  ✓ всё
  order.*            ✗ "*" — одно слово, а осталось два
  *.created.us       ✗ регион не тот
```

Самый используемый тип. Позволяет одному потребителю подписаться на
`order.#`, другому — только на `order.created.*`.

### headers — по заголовкам

Матчинг не по ключу, а по словарю заголовков с `x-match: all|any`.
Медленнее, применяется редко — когда критериев несколько и они не
укладываются в иерархию.

### Default exchange

Безымянный exchange (`""`) типа direct, к которому автоматически
привязана каждая очередь по своему имени. `publish("", "my-queue", body)`
кладёт напрямую в `my-queue`. Удобно для «просто очереди», но в проде
лучше явный exchange — иначе продюсер жёстко привязан к имени очереди.

## 3. Доставка: ack и prefetch

RabbitMQ — **push-модель**: брокер сам проталкивает сообщения
подписавшемуся потребителю. (В Kafka
[наоборот — pull](kafka.md#4-consumer-и-группы).)

Отсюда необходимость в тормозе — **prefetch (QoS)**:

```
channel.Qos(prefetchCount=1)   // не давать новое, пока не подтверждено предыдущее
```

`prefetch_count` — сколько неподтверждённых сообщений брокер может
держать у потребителя. Без ограничения (`0` = без лимита) брокер зальёт
быстрому потребителю всю очередь в память, а остальные будут простаивать.

| prefetch | Когда |
|---|---|
| `1` | долгие неравномерные задачи: честное распределение, никто не копит |
| `10-100` | быстрая обработка, важна пропускная способность |
| `0` (без лимита) | почти всегда ошибка |

### Подтверждения

```go
msgs, _ := ch.Consume(q.Name, "", false /* autoAck = false */, false, false, false, nil)

for d := range msgs {
    if err := handle(d.Body); err != nil {
        // requeue=false → в DLX; true → обратно в очередь (риск вечного цикла)
        d.Nack(false /* multiple */, false /* requeue */)
        continue
    }
    d.Ack(false)
}
```

| Действие | Что происходит |
|---|---|
| `ack` | сообщение удалено из очереди навсегда |
| `nack(requeue=true)` / `reject(requeue=true)` | вернуть в очередь (обычно в голову) — повторится |
| `nack(requeue=false)` | в dead-letter exchange, если настроен; иначе удалить |
| соединение оборвалось | все неподтверждённые сообщения возвращаются в очередь автоматически |
| `autoAck=true` | считается доставленным в момент отправки — потеря при падении потребителя |

Последняя строка — главное отличие от Kafka на уровне модели: здесь
подтверждение **на каждое сообщение**, и его можно отклонить. В Kafka
подтверждается только позиция (offset), отклонить одно сообщение из
середины нельзя — отсюда и
[head-of-line blocking](kafka.md#8-ретраи-и-dlq).

## 4. Надёжность публикации

Три независимые настройки, нужны все три:

```go
// 1. durable queue — переживёт рестарт брокера
ch.QueueDeclare("orders", true /* durable */, false, false, false, nil)

// 2. persistent message — запишется на диск
ch.PublishWithContext(ctx, "orders-ex", "order.created", false, false,
    amqp.Publishing{
        DeliveryMode: amqp.Persistent,   // = 2
        Body:         payload,
    })

// 3. publisher confirms — брокер подтвердил приём
ch.Confirm(false)
confirms := ch.NotifyPublish(make(chan amqp.Confirmation, 1))
// ... publish ...
if c := <-confirms; !c.Ack {
    // брокер не принял — повторить
}
```

| Забыли | Последствие |
|---|---|
| `durable` | очередь исчезнет при рестарте вместе с содержимым |
| `persistent` | очередь останется, сообщения — нет |
| publisher confirms | продюсер думает, что отправил; брокер не получил. Тихая потеря |

Флаг `mandatory=true` + `NotifyReturn` ловит случай «сообщение никуда не
смаршрутизировалось» — тоже тихая потеря по умолчанию.

Важно: даже с persistent запись может быть асинхронной, и окно потери
между приёмом и fsync существует. Настоящая гарантия «записали и
подтвердили» — это publisher confirms **на quorum-очереди**, где
подтверждение приходит после репликации на большинство узлов.

И общее с Kafka: атомарности «БД + брокер» тут тоже нет — та же проблема
dual write решается [Transactional Outbox](../patterns/outbox.md).

## 5. Типы очередей

| Тип | Репликация | Когда |
|---|---|---|
| **Classic** | нет (живёт на одном узле) | нереплицируемые задачи, временные очереди, максимальная скорость |
| **Quorum** | Raft, большинство узлов | по умолчанию для всего важного (с 3.8) |
| **Stream** | Raft, лог | когда нужно перечитывание и много потребителей |

### Quorum queues

Реплицированная очередь на Raft: лидер + фолловеры, запись подтверждается
после записи большинством. Переживает падение узла без потери
подтверждённых сообщений.

Цена: больше диска и сети, чуть выше задержка, не поддерживают
приоритеты. Зато умеют то, чего нет у classic: **`x-delivery-limit`** —
счётчик доставок, после превышения сообщение уходит в DLX. Это
встроенная защита от «ядовитых» сообщений.

> Старые **mirrored classic queues** (`ha-mode`) считались решением HA,
> но были источником сплит-брейнов и потерь. Объявлены устаревшими и
> **удалены в RabbitMQ 4.0**. Если на собеседовании спрашивают про HA —
> правильный ответ сегодня «quorum queues».

### Streams

Append-only лог с offset и **неразрушающим чтением** — то есть
по сути [модель Kafka](kafka.md#1-модель-данных) внутри RabbitMQ. Данные
не удаляются при чтении, потребители читают с любого offset, retention
по времени/размеру. Есть свой бинарный протокол, заметно быстрее AMQP.

Когда: нужен fan-out на много потребителей, перечитывание истории или
большой поток, но менять брокер не хочется. Полноценной заменой Kafka не
является — нет consumer groups с автоматическим распределением партиций,
экосистемы (Connect, Streams, Schema Registry) и того же масштаба.

## 6. TTL, DLX и ретраи

То, что в Kafka приходится строить руками, здесь встроено.

### TTL

```
x-message-ttl : 60000     — сообщение живёт в очереди 60 с, потом удаляется/в DLX
x-expires     : 1800000   — сама очередь удалится после 30 мин без использования
x-max-length  : 10000     — максимум сообщений; при переполнении drop-head или reject-publish
expiration    : "5000"    — TTL конкретного сообщения при публикации
```

### Dead Letter Exchange

Сообщение уходит в DLX, если:

- отклонено с `requeue=false`;
- истёк TTL;
- очередь переполнена (`x-max-length`);
- превышен `x-delivery-limit` (quorum).

```
        ┌──────────────┐  reject / TTL   ┌──────────────┐
        │ orders.queue │ ──────────────► │  dlx (topic) │
        └──────────────┘                 └──────┬───────┘
                                                ▼
                                        ┌───────────────┐
                                        │ orders.failed │ ← ручной разбор
                                        └───────────────┘
```

### Retry с задержкой

Классический трюк: очередь-«отстойник» с TTL, у которой DLX указывает
обратно на рабочий exchange.

```
orders.queue ──reject──► orders.retry (x-message-ttl=30000,
                                       x-dead-letter-exchange=orders-ex)
                              │
                         через 30 с TTL истёк
                              ▼
                         orders.queue    ← повтор
```

Счётчик попыток держат в заголовке (`x-death` заполняется брокером
автоматически: сколько раз и откуда сообщение дедлеттерилось). После N —
в `orders.failed`.

Альтернатива — плагин `rabbitmq_delayed_message_exchange` для честной
отложенной доставки («напомнить через 2 часа»). В Kafka такого нет
совсем: там [цепочка retry-топиков](kafka.md#8-ретраи-и-dlq).

### Приоритеты

`x-max-priority: 10` на classic-очереди: сообщения с большим `priority`
обгоняют. Работает в пределах того, что уже в очереди (то, что уже
отправлено потребителю через prefetch, не переупорядочится). У Kafka
приоритетов нет в принципе.

## 7. Типовые паттерны

### Work queue (competing consumers)

```
producer ──► [ task queue ] ──┬──► worker 1
                              ├──► worker 2
                              └──► worker 3
```

Каждое сообщение достаётся **одному** воркеру. Масштабирование —
запустить ещё воркеров, никаких партиций и ребалансировок. Это
существенно проще, чем в Kafka, где параллелизм ограничен
[числом партиций](kafka.md#4-consumer-и-группы).

### Publish/Subscribe

fanout или topic exchange → у каждого подписчика **своя очередь**. Копия
сообщения кладётся в каждую. Отсюда: 10 подписчиков = 10 копий в памяти
и на диске (в Kafka — одна запись в логе на всех).

### RPC

Запрос с заголовками `reply_to` (имя callback-очереди) и
`correlation_id`. Сервер отвечает в `reply_to`, клиент сопоставляет по
`correlation_id`. Kafka для такого не предназначена.

### Routing по признакам

```
logs (topic exchange)
  ├── "*.critical"        ──► pagerduty-queue
  ├── "auth.#"            ──► security-queue
  └── "#"                 ──► archive-queue
```

Один поток событий, разные подписки. Ровно тот случай, ради которого
берут RabbitMQ.

### Claim check

Большие payload'ы (файлы, картинки) не кладут в сообщение — кладут в S3,
а в очередь ссылку. Верно и для Kafka.

## 8. Кластер и HA

Узлы объединяются в кластер, метаданные (exchange, биндинги, пользователи)
реплицируются на все узлы. **Сообщения — нет**: classic-очередь целиком
живёт на одном узле, quorum-очередь реплицируется по Raft.

| Механизм | Для чего |
|---|---|
| **Кластер** | один логический брокер в пределах одного ДЦ, низкие задержки между узлами |
| **Quorum queues** | отказоустойчивость очереди внутри кластера |
| **Federation** | связь между кластерами/ДЦ по WAN: exchange или очередь «протягивается» на другой кластер |
| **Shovel** | простое перекачивание из очереди одного кластера в другой; удобно для миграций |

Кластер **не растягивают через WAN** — Raft и обнаружение отказов
чувствительны к задержкам. Между регионами — federation/shovel.

Для quorum-очередей нужен нечётный размер кластера (3, 5) — иначе
большинство не собирается. Для устойчивости к разделению сети настраивают
`cluster_partition_handling` (`pause_minority` — безопасный вариант).

Масштабирование по объёму: RabbitMQ не шардирует очередь автоматически.
Одна очередь = одна точка (лидер). Если упирается — руками бьют на
несколько очередей по признаку (плагин `rabbitmq_sharding` или
маршрутизация по ключу). Здесь Kafka с её партициями выигрывает
структурно.

## 9. Эксплуатация

| Метрика | О чём говорит |
|---|---|
| `messages_ready` | накопилось необработанного — потребители не справляются |
| `messages_unacknowledged` | висит у потребителей: слишком большой prefetch или зависшая обработка |
| Publish rate vs ack rate | расхождение = очередь растёт |
| Memory / disk alarm | при превышении watermark брокер **блокирует продюсеров** |
| Число соединений и каналов | типичная утечка: канал на каждую операцию |
| Размер DLQ | растёт → системная ошибка обработки |

```bash
rabbitmqctl list_queues name messages messages_ready messages_unacknowledged
rabbitmqctl list_consumers
rabbitmq-diagnostics status
```

Management UI (плагин `rabbitmq_management`, порт 15672) — стандартный
инструмент: очереди, скорости, трассировка.

**Flow control**: при нехватке памяти (`vm_memory_high_watermark`, по
умолчанию 40% RAM) или места на диске RabbitMQ перестаёт принимать
публикации. Продюсер «зависает» на publish. Это не баг, а защита — но
именно так выглядит инцидент «всё встало», когда очередь никто не разбирал.

## 10. Кейсы применения

### 1. Фоновые задачи

Самый частый случай. Отправка писем, генерация PDF, обработка загруженных
изображений, выгрузка отчётов.

```
POST /report ──► "reports" queue ──► N воркеров ──► готовый файл в S3
   (202 Accepted сразу)
```

Почему не Kafka: задачи разнородные, важны retry с задержкой, ack на
каждую задачу и простое горизонтальное масштабирование воркеров.

### 2. Маршрутизация команд между сервисами

Разные типы событий должны попасть разным получателям по правилам:
`payment.eu.*` — в европейский процессинг, `payment.us.*` — в
американский, `*.failed` — дополнительно в мониторинг. Topic exchange
делает это конфигурацией, без кода.

### 3. Интеграция «зоопарка» протоколов

IoT-устройства шлют по MQTT, старый сервис слушает STOMP, новый — AMQP.
RabbitMQ принимает всё это в один брокер и раскладывает по очередям.
Kafka говорит только на своём протоколе.

### 4. Отложенные и запланированные действия

«Отменить неоплаченный заказ через 30 минут», «напомнить о брошенной
корзине через сутки». TTL + DLX или delayed-exchange плагин. Отдельного
шедулера не нужно.

### 5. RPC поверх брокера

Синхронный по смыслу вызов с балансировкой, ретраями и без прямой сетевой
связности между сервисами. Ниша узкая (чаще берут gRPC), но встречается
в интеграциях.

### 6. Сглаживание нагрузки на внешний API

Внешний шлюз держит 100 rps. Складываем вызовы в очередь, воркеры с
`prefetch=1` и ограниченным пулом равномерно расходуют лимит; всплеск
остаётся в очереди.

## 11. Подводные камни

| Проблема | Суть и что делать |
|---|---|
| Очередь не durable / сообщения не persistent | Рестарт брокера — всё пропало. Нужны обе настройки + confirms |
| Публикация без confirms | Продюсер уверен, что отправил. Проверять `NotifyPublish` |
| Сообщение никуда не смаршрутизировалось | Молча исчезает. `mandatory=true` + `NotifyReturn` или alternate-exchange |
| `autoAck=true` | Потребитель упал — сообщение потеряно. Только для метрик/логов |
| Prefetch не задан | Один потребитель забирает всю очередь, остальные простаивают, память течёт |
| `nack(requeue=true)` в цикле | Битое сообщение крутится вечно и жжёт CPU. Лимит попыток → DLX |
| Забыли DLQ | Отклонённые сообщения исчезают бесследно |
| Очередь копится незамеченной | Память → alarm → блокировка продюсеров → «встал весь сервис». Алерт на `messages_ready` |
| Соединение на каждую операцию | TCP-хендшейк дорог. Одно соединение, много каналов; канал не потокобезопасен |
| Ждут, что порядок сохранится | FIFO ломается при нескольких потребителях, requeue и повторах. Строгий порядок — одна очередь, один потребитель |
| Ждут перечитывания истории | Прочитано и подтверждено = удалено. Нужен replay — streams или [Kafka](kafka.md) |
| Mirrored classic queues для HA | Удалены в 4.0. Использовать quorum queues |
| Упёрлись в пропускную способность одной очереди | Очередь не шардируется сама. Разбивать вручную или брать Kafka |
| Огромные сообщения | Раздувают память брокера. Claim check: тело в S3, в очередь ссылка |

## 12. Для собеседования

- **Модель:** producer → exchange → (binding + routing key) → queue →
  consumer. Продюсер не знает про очереди.
- **Типы exchange:** direct (точный ключ), fanout (всем), topic
  (шаблоны `*` = слово, `#` = любое число слов), headers.
- **Доставка:** push с ограничением через prefetch; per-message
  ack/nack/reject; при обрыве соединения неподтверждённое возвращается.
- **Надёжность:** durable queue + persistent message + publisher
  confirms. Любого из трёх недостаточно.
- **HA:** quorum queues на Raft (большинство узлов). Mirrored classic
  queues устарели и удалены в 4.0.
- **Ретраи:** reject → DLX; задержка через очередь с TTL и DLX обратно;
  `x-delivery-limit` у quorum-очередей ограничивает попытки.
- **Умеет то, чего нет у Kafka:** маршрутизация, приоритеты, отложенная
  доставка, отклонение отдельного сообщения, RPC, несколько протоколов.
- **Не умеет:** перечитывание истории (кроме streams), масштаб Kafka,
  автоматический шардинг очереди.
- **Когда брать:** задачи и команды, сложный роутинг, умеренный поток
  (десятки тысяч сообщений/с). Когда поток событий, replay и
  аналитика — [Kafka](kafka.md).
