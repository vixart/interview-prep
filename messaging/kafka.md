# Apache Kafka

[README](README.md) · **Kafka** · [RabbitMQ](rabbitmq.md) · [Redpanda](redpanda.md)

Kafka — это **распределённый журнал (log)**, а не очередь. Ключевое отличие
от классических брокеров: сообщение не удаляется после чтения. Оно лежит
в логе, пока не истечёт retention, а потребитель просто двигает по логу
свой указатель — **offset**.

Из этой одной идеи следует почти всё остальное: и репликация, и
производительность, и то, чего Kafka принципиально не умеет. Где Kafka
ведёт себя иначе, чем RabbitMQ, стоят ссылки на
[`rabbitmq.md`](rabbitmq.md).

## 1. Модель данных

```
topic "orders"
├── partition 0:  [0][1][2][3][4][5] →  append only
├── partition 1:  [0][1][2][3]       →
└── partition 2:  [0][1][2][3][4]    →
                   ▲        ▲
             consumer A   consumer B
             offset=1     offset=4
```

| Понятие | Что это |
|---|---|
| **Topic** | Логическое имя потока: `orders`, `user.events` |
| **Partition** | Физический файл-лог. Топик разбит на N партиций |
| **Offset** | Порядковый номер сообщения **внутри партиции**. Монотонно растёт, не переиспользуется |
| **Record** | `key`, `value`, `timestamp`, `headers`. Ключ определяет партицию |
| **Broker** | Узел кластера, хранит партиции |
| **Consumer group** | Набор потребителей, между которыми делятся партиции |

Три следствия, которые нужно проговаривать на собеседовании:

- **Порядок гарантирован только внутри партиции.** Между партициями
  порядка нет и быть не может — они пишутся независимо.
- **Партиция — единица параллелизма.** Больше потребителей в группе, чем
  партиций, не даст ускорения: лишние будут простаивать.
- **Чтение не разрушает данные.** Десять разных сервисов читают один
  топик независимо, каждый со своим offset. В RabbitMQ для этого нужно
  N очередей и N копий сообщения — см.
  [маршрутизацию](rabbitmq.md#2-типы-exchange).

### Ключ и выбор партиции

```
partition = hash(key) % partitions_count     // ключ задан
partition = round-robin / sticky             // ключ = null
```

Ключ — это **не** идентификатор сообщения, а **ключ упорядочивания**. Все
события с `key = "order-42"` попадут в одну партицию и будут прочитаны
строго по порядку. Именно поэтому в
[Transactional Outbox](../patterns/outbox.md) ключом берут `aggregate_id`.

## 2. Архитектура кластера

```
                     ┌──────────── cluster ────────────┐
producers  ────────► │ broker 1   broker 2   broker 3  │ ◄──────── consumers
                     │ P0(L)      P0(F)      P0(F)     │
                     │ P1(F)      P1(L)      P1(F)     │
                     │ P2(F)      P2(F)      P2(L)     │
                     └─────────────────────────────────┘
                        L = leader, F = follower
```

Каждая партиция реплицируется на `replication.factor` узлов. Один из них —
**лидер**, он обслуживает все чтения и записи этой партиции. Остальные —
фолловеры, они просто тянут данные с лидера.

### ISR и min.insync.replicas

**ISR** (in-sync replicas) — реплики, которые не отстали от лидера дольше
`replica.lag.time.max.ms` (по умолчанию 30 с). Если лидер падает, новый
выбирается **только из ISR**.

`min.insync.replicas` — сколько реплик в ISR должно быть, чтобы запись
с `acks=all` считалась успешной. Классическая безопасная конфигурация:

```
replication.factor    = 3
min.insync.replicas   = 2
acks                  = all
```

Смысл: пишем, пока живы минимум 2 из 3. Потеря одного узла не
останавливает запись, потеря двух — останавливает (producer получает
`NotEnoughReplicasException`), но данные не теряются. Комбинация
`replication.factor=3, min.insync.replicas=3` выглядит надёжнее, но любой
упавший узел останавливает запись целиком — так почти никогда не делают.

> `unclean.leader.election.enable=true` разрешает выбрать лидером реплику
> вне ISR. Это доступность ценой **молчаливой потери данных**. По
> умолчанию выключено, включать осознанно.

### KRaft вместо ZooKeeper

Исторически метаданные кластера (кто лидер, какие топики есть) хранились
в ZooKeeper — отдельном кластере, который надо было эксплуатировать. С
Kafka 3.3 стабилен **KRaft**: метаданные живут в самой Kafka, в
служебном логе, консенсус — по Raft. В Kafka 4.0 ZooKeeper удалён
полностью.

Практический смысл: меньше движущихся частей, быстрее failover и старт,
кластер поднимает десятки тысяч партиций вместо тысяч. Именно
«без ZooKeeper» с самого начала строился и [Redpanda](redpanda.md).

## 3. Producer

Producer не отправляет сообщения по одному. Он **накапливает батч** на
партицию и отсылает, когда набралось `batch.size` или истекло
`linger.ms`. Это основной источник пропускной способности.

```go
w := &kafka.Writer{
    Addr:         kafka.TCP("kafka-1:9092", "kafka-2:9092"),
    Topic:        "orders",
    Balancer:     &kafka.Hash{},        // partition = hash(key)
    RequiredAcks: kafka.RequireAll,     // acks=all
    BatchTimeout: 10 * time.Millisecond, // linger.ms
    BatchSize:    100,
    Compression:  kafka.Lz4,
}

err := w.WriteMessages(ctx, kafka.Message{
    Key:   []byte(order.ID),           // ключ упорядочивания
    Value: payload,
    Headers: []kafka.Header{
        {Key: "event_type", Value: []byte("order.created")},
    },
})
```

### acks

| `acks` | Когда подтверждается | Риск |
|---|---|---|
| `0` | сразу после отправки в сокет | потеря без следа; максимальная скорость |
| `1` | лидер записал к себе | лидер упал до репликации — сообщение потеряно |
| `all` (`-1`) | записали все реплики из ISR | потери нет при живых `min.insync.replicas` |

Ретрай при `acks=1` может привести и к дублю, и к потере; при `acks=all`
и включённой идемпотентности — только к корректному повтору.

### Идемпотентный producer

Проблема: producer отправил батч, ответ потерялся в сети, producer
повторил — в логе два одинаковых сообщения.

Решение: `enable.idempotence=true` (по умолчанию с Kafka 3.0). Producer
получает **PID** и нумерует сообщения последовательностью на партицию.
Брокер помнит последний номер и молча отбрасывает повтор.

Что важно понимать: это дедупликация **на стороне брокера, в рамках
сессии producer'а и одной партиции**. Она не спасает от дубля, если
приложение само дважды сформировало событие (например, перезапустилось
между записью в БД и отправкой) — от этого спасает
[Outbox](../patterns/outbox.md).

### Транзакции

Транзакции дают атомарность **записи в несколько партиций/топиков**
и связки «прочитал → обработал → записал» (read-process-write).

```
producer.InitTransactions()
producer.BeginTransaction()
    → пишем в topic-A
    → пишем в topic-B
    → фиксируем offset потребителя в той же транзакции
producer.CommitTransaction()
```

Механика: транзакционный координатор, служебный топик
`__transaction_state`, в партиции пишутся **control-маркеры** commit/abort.
Потребитель с `isolation.level=read_committed` не видит сообщений
незакоммиченных транзакций.

Ограничение, о котором спрашивают: **это exactly-once только внутри
Kafka**. Если обработка пишет в PostgreSQL или дёргает внешний API, Kafka-
транзакция их не покрывает — нужна идемпотентность на стороне приёмника.

## 4. Consumer и группы

Kafka — **pull-модель**: потребитель сам ходит за данными
(`fetch.min.bytes`, `fetch.max.wait.ms`), брокер ничего не проталкивает.
Отсюда естественный backpressure: медленный потребитель просто реже
запрашивает. В RabbitMQ модель обратная — push с ограничением через
prefetch, см. [`rabbitmq.md`](rabbitmq.md#3-доставка-ack-и-prefetch).

### Распределение партиций

```
topic: 4 партиции

group "billing" c 2 потребителями      group "billing" c 5 потребителями
  c1: P0, P1                             c1: P0   c2: P1   c3: P2
  c2: P2, P3                             c4: P3   c5: — простаивает
```

Правило: **одна партиция в один момент времени принадлежит ровно одному
потребителю группы**. Разные группы читают независимо и не мешают друг
другу.

### Commit offset

Позиция группы хранится в служебном топике `__consumer_offsets`.

```go
r := kafka.NewReader(kafka.ReaderConfig{
    Brokers: []string{"kafka-1:9092"},
    Topic:   "orders",
    GroupID: "billing",           // ← группа, иначе partition assignment вручную
})

for {
    m, err := r.FetchMessage(ctx)   // читаем, но НЕ коммитим
    if err != nil {
        return err
    }
    if err := handle(ctx, m); err != nil {
        continue                    // не коммитим — перечитаем после ребаланса
    }
    if err := r.CommitMessages(ctx, m); err != nil {  // ← коммит после обработки
        return err
    }
}
```

- Коммит **после** обработки → at-least-once (возможен дубль).
- Коммит **до** обработки → at-most-once (возможна потеря).
- Автокоммит (`enable.auto.commit=true`) коммитит по таймеру, независимо
  от того, обработалось ли сообщение. Для критичной логики его выключают.

### Ребалансировка

Происходит при входе/выходе потребителя, падении, изменении числа
партиций. Больная точка эксплуатации.

| Стратегия | Поведение |
|---|---|
| **Eager** (range, roundrobin) | stop-the-world: все отпускают все партиции, потом переназначение. Пауза на всю группу |
| **Cooperative** (`CooperativeStickyAssignor`) | инкрементально: переезжают только те партиции, которые действительно меняют владельца |
| **Static membership** (`group.instance.id`) | при рестарте пода в пределах `session.timeout.ms` ребаланса вообще не происходит |

Частая причина «группа постоянно ребалансится»: обработка одного батча
дольше `max.poll.interval.ms` (по умолчанию 5 минут). Брокер считает
потребителя мёртвым и выкидывает из группы. Лечится уменьшением
`max.poll.records` или выносом долгой работы в отдельный пул.

## 5. Гарантии доставки

| Гарантия | Как получить | Цена |
|---|---|---|
| **At-most-once** | коммит offset до обработки | теряем при падении |
| **At-least-once** | `acks=all` + коммит после обработки | дубли; нужна идемпотентность потребителя |
| **Exactly-once** | идемпотентный producer + транзакции + `read_committed` | только внутри Kafka, ~20-30% пропускной способности, сложность |

Практический вывод: в 90% систем строят **at-least-once + идемпотентный
потребитель** (дедупликация по `event_id`, `UPSERT`, Inbox-таблица —
см. [Outbox](../patterns/outbox.md#дубли-и-идемпотентность)). Это проще и
надёжнее, чем тянуть EOS через границу Kafka.

## 6. Хранение: retention и compaction

Данные лежат в **сегментах** — файлах фиксированного размера
(`log.segment.bytes`, по умолчанию 1 ГБ) с индексом offset → позиция в
файле. Удаляется всегда сегмент целиком, не отдельное сообщение.

### cleanup.policy=delete (по умолчанию)

```
log.retention.hours = 168        # 7 дней
log.retention.bytes = -1         # или по размеру
```

Сегмент удаляется, когда он **весь** старше retention. Отсюда: реальный
объём на диске всегда чуть больше расчётного, а «удалить одно сообщение»
(GDPR) нельзя — только через compaction с tombstone.

### cleanup.policy=compact

Compaction оставляет **последнее значение для каждого ключа**:

```
до:   (k1,v1) (k2,v2) (k1,v3) (k3,v4) (k2,v5)
после: k1→v3   k3→v4   k2→v5
```

Получается снимок текущего состояния в виде лога. Это основа для:

- топиков состояния (`user.profile.changed` — последний профиль по `user_id`);
- `__consumer_offsets` (сам Kafka так и хранит offsets);
- change data capture и восстановления кэшей/read-моделей с нуля.

Удаление ключа — **tombstone**: сообщение с тем же ключом и `value=null`.
После `delete.retention.ms` compaction убирает и его.

> Retention — это **не** очередь с TTL. Сообщение не «протухает» для
> конкретного потребителя: если потребитель отстал сильнее retention, он
> просто получит `OffsetOutOfRange` и потеряет непрочитанное. В RabbitMQ
> TTL относится к сообщению в очереди — совсем другая семантика,
> см. [`rabbitmq.md`](rabbitmq.md#6-ttl-dlx-и-ретраи).

## 7. Почему быстро

Вопрос «почему Kafka держит миллионы сообщений в секунду» — стандартный.
Четыре причины:

1. **Последовательная запись на диск.** Append-only лог. Линейная запись
   на HDD быстрее случайной записи в память по количеству IOPS. Никаких
   B-tree, никакого поиска места.
2. **Page cache вместо своего кэша.** Kafka пишет через файловую систему
   и полагается на кэш ОС. Свежие данные читаются из памяти, а JVM-heap
   не раздувается и не собирается GC.
3. **Zero-copy.** Отдача данных потребителю идёт через `sendfile(2)`:
   из page cache сразу в сокет, минуя пользовательское пространство.
   *(Ломается при включённом TLS или если брокеру нужно перепаковать
   батч — это одна из причин просадки при шифровании.)*
4. **Батчинг и сжатие.** Producer жмёт **батч целиком** (lz4/zstd) и
   брокер хранит его сжатым, не распаковывая. Сжатие однотипных JSON'ов
   пачкой даёт в разы больше, чем по одному.

Плюс отсутствие per-message состояния: брокер не хранит, кто что
прочитал, — только offset группы. Нет очереди «в памяти», нет
подтверждений на сообщение, нет сложного роутинга —
[роутинг здесь вообще отсутствует](rabbitmq.md#2-типы-exchange).

## 8. Ретраи и DLQ

В Kafka **нет** встроенного механизма повторов и dead-letter — это
принципиально. Брокер не знает, обработалось сообщение или нет, у него
есть только offset.

Что происходит при ошибке обработки:

```
не закоммитили offset → после рестарта/ребаланса читаем то же сообщение
                      → снова ошибка → бесконечный цикл
                      → партиция стоит, лаг растёт  ← head-of-line blocking
```

Одно «ядовитое» сообщение блокирует **всю партицию**. Стандартное
решение — паттерн retry-топиков:

```
orders ──ошибка──► orders.retry.5s ──ошибка──► orders.retry.1m ──►  orders.DLT
   ▲                     │                          │
   └── успех после паузы ┘──────────────────────────┘
```

Потребитель retry-топика ждёт нужную задержку перед обработкой (либо
топик читается отдельным сервисом с паузой). После N попыток —
в dead-letter topic, оттуда разбор вручную. В Spring Kafka это
`@RetryableTopic`/`DeadLetterPublishingRecoverer`, в Go пишется руками.

Сравните с RabbitMQ, где DLX и лимит доставок — часть брокера:
[`rabbitmq.md`](rabbitmq.md#6-ttl-dlx-и-ретраи). Это, пожалуй, самое
заметное различие в повседневной разработке.

## 9. Эксплуатация

**Consumer lag** — главная метрика. Разница между последним offset в
партиции и закоммиченным offset группы. Растёт → потребители не
справляются.

```bash
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group billing
# TOPIC  PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID
```

| Что смотреть | Симптом |
|---|---|
| Consumer lag по партициям | перекос → «горячий» ключ, неравномерное распределение |
| Under-replicated partitions | реплика выпала из ISR: диск/сеть/узел |
| Offline partitions | нет живого лидера — часть топика недоступна |
| Rebalance rate | частые ребалансы → таймауты обработки |
| Request latency (p99) | упирается в диск или в GC на брокере |

**Число партиций.** Планируется заранее: увеличить можно, уменьшить —
нет. При увеличении `hash(key) % N` меняется, и ключи начинают попадать
в другие партиции — **порядок по ключу на границе изменения ломается**.
Отправная точка: целевая пропускная способность ÷ пропускная способность
одного потребителя, с запасом ×2-3 на рост.

**Schema Registry** (Confluent/Redpanda) — реестр схем Avro/Protobuf/JSON
с проверкой совместимости. Без него эволюция формата событий в топике,
который читают пять команд, превращается в переговоры.

## 10. Кейсы применения

### 1. Event streaming между сервисами

Каноническое применение. Сервис заказов публикует `order.created`, его
читают склад, биллинг, уведомления, аналитика — независимо, каждый со
своим offset и своей скоростью.

```
order-service ──► topic "orders" ──┬──► warehouse   (group: wh)
                                   ├──► billing     (group: billing)
                                   ├──► notifier    (group: notify)
                                   └──► analytics   (group: dwh)
```

Новый потребитель добавляется без изменения продюсера и может **прочитать
историю с начала** — этого RabbitMQ (кроме streams) не умеет в принципе.

### 2. Сбор логов, метрик, кликстрима

Огромный поток, потеря отдельных записей терпима, нужна пропускная
способность и буферизация. Kafka — буфер между источниками (тысячи
инстансов) и хранилищем (ClickHouse, S3, Elasticsearch). Пик нагрузки
гасится retention'ом: приёмник читает в своём темпе.

### 3. Change Data Capture

Debezium читает WAL PostgreSQL и пишет изменения строк в топики. На той
стороне — репликация в аналитическое хранилище, обновление поисковых
индексов, наполнение кэшей. Compaction по первичному ключу даёт всегда
актуальный снимок таблицы.

Связка с [Outbox](../patterns/outbox.md): CDC — второй способ вычитывать
outbox-таблицу вместо поллинга.

### 4. Event sourcing и пересчёт состояния

Лог — источник истины. Состояние — результат свёртки лога. Можно
пересобрать read-модель с нуля, прочитав топик с offset 0, или
проиграть события на новой версии логики.

### 5. Потоковая обработка

Kafka Streams / Flink: агрегации в окнах, джойны потоков, детекция
паттернов. Антифрод «больше 5 платежей за минуту с одной карты» — типовая
задача. Промежуточное состояние тоже живёт в Kafka (compacted changelog).

### 6. Разгрузка пиков

Чёрная пятница: фронт кладёт заказы в топик за миллисекунды, обработчики
разгребают в своём темпе. База не видит пика, клиент не видит таймаута.

## 11. Подводные камни

| Проблема | Суть и что делать |
|---|---|
| Порядок «сломался» | Порядок только внутри партиции. Нужен порядок — общий ключ. Ключ `null` → round-robin, порядка нет |
| Перекос партиций | Один «горячий» ключ (крупный клиент) грузит одну партицию. Пересмотреть ключ: добавить суффикс, сменить измерение |
| Head-of-line blocking | Одно битое сообщение стопорит партицию. Retry-топики + DLT, лимит попыток |
| Больше потребителей, чем партиций | Лишние простаивают. Параллелизм ограничен числом партиций |
| Частые ребалансы | Обработка дольше `max.poll.interval.ms`. Уменьшить `max.poll.records`, static membership, cooperative assignor |
| Потребитель отстал сильнее retention | `OffsetOutOfRange`, данные уже удалены. Мониторить lag, не ставить retention в пару часов |
| Ждут отложенной доставки | «Через 30 минут» Kafka не умеет: нет per-message TTL и планировщика. Нужны retry-топики или [RabbitMQ](rabbitmq.md#6-ttl-dlx-и-ретраи) |
| Ждут приоритетов | Приоритетов нет вообще. Только разные топики и разные потребители |
| Много мелких топиков/партиций | Каждая партиция — файлы и метаданные. Десятки тысяч партиций на брокер — деградация |
| `acks=1` в проде | «Быстрее» ценой тихой потери при падении лидера. Для бизнес-событий — `acks=all` |
| Exactly-once «включили и всё» | EOS работает только Kafka→Kafka. Внешние системы — идемпотентность руками |
| Большие сообщения | Дефолт `max.message.bytes` ~1 МБ. Файлы — в S3, в топик ссылку (claim check) |

## 12. Для собеседования

- **Что это:** распределённый упорядоченный лог с репликацией. Не очередь:
  чтение не удаляет данные, потребитель двигает свой offset.
- **Единица параллелизма и порядка:** партиция. Порядок — только внутри
  партиции, определяется ключом.
- **Consumer group:** партиция принадлежит одному потребителю группы;
  разные группы читают независимо. Больше потребителей, чем партиций —
  бессмысленно.
- **Надёжность записи:** `acks=all` + `replication.factor=3` +
  `min.insync.replicas=2`. Лидер выбирается из ISR.
- **Гарантии:** по умолчанию at-least-once. Exactly-once — идемпотентный
  producer + транзакции + `read_committed`, и только внутри Kafka.
- **Почему быстро:** последовательный append, page cache, zero-copy,
  батчинг со сжатием.
- **Retention vs compaction:** удаление по времени/размеру сегментами либо
  хранение последнего значения на ключ (снимок состояния, tombstone для
  удаления).
- **Чего нет:** роутинга, приоритетов, отложенной доставки, per-message
  ack, встроенных ретраев и DLQ — всё это делается приложением.
- **KRaft:** метаданные в самой Kafka вместо ZooKeeper, с 4.0 ZK удалён.
- **Когда не Kafka:** сложная маршрутизация, RPC-стиль, задачи с
  приоритетами и задержками, небольшой поток команд —
  [RabbitMQ](rabbitmq.md) проще и уместнее.
