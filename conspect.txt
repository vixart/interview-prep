##Срезы
Срез - это последовательность значений.
Элементам среза выделяются последовательные ячейки в памяти.
Каждый срез обладает определенной емкостью(зарезервированные ячейки).
Когда длина среза становится больше емкости, среда Go увеличивает срез.
Если емкость до 256 элементов, то она увеличивается в 2 раза, потом действует по формуле.
Выделение большей емкости - тяжелая операция. 
Выделение памяти -> копирование среза -> очистка старой памяти при помощи сборщика мусора.
Длина среза не является составной частью его типа.
Срезы можно увеличивать по мере необходимости.
Можно писать функцию для работы со срезами любого размера.
Срезы нельзя сравнивать через == и != между собой, но можно с nil.
Срез формируется только с помощью []
Срезы можно сравнивать при помощи библиотеки slices.
slices.Equal принимает два среза сравнивает длину и значения.
slices.EqualFunc принимает функцию для сравнения срезов третим аргументом.
len для среза равного nil вернет 0.
var x = []int{10, 20, 30} // не нужно указывать размер
var x = []int{1, 5: 4, 6, 10: 100, 15} // срез на 12 элементов
var x [][]int // многомерный срез
var x []int // указатель на nil срез, x == nil

x[0] = 10 // запись по индексу
fmt.Println(x[2]) // чтение по индексу
x = append(x, 10) // используется для увеличения среза
x = append(x, 1, 2, 3)  // добавляем сразу несколько элементов
len(x) // длина среза
cap(x) // емкость среза

##Функция make

x := make([]int, 5) // длина и емкость равны 5, [0, 0, 0, 0, 0]
x := make([]int, 5, 10) // длина 5, емкость 10
x := make([]int, 0, 10) // длина 0, емкость 10
clear(x) // устанавливает нулевое значение для всех его элементов
Всегда стоит делать так, чтобы срез как можно реже приходилось увеличивать.
var x []int // nil срез
var x = []int{} // срез нулевой длины и емкости, удобно если нужно преобразовывать в JSON
[]int{} - это называют литералом среза

##Срезание срезов
При срезании срезов, копии не создается.
Создается дополнительная переменная, использующая ту же область памяти
x := []string{"a", "b", "c", "d"}
y := x[:2] // [a b]
z := x[1:] // [b c d]
d := x[1:3] // [b c]
e := x[:] // [a b c d]

При использованни append на подсрезе x от среза y, элемент добавляется в подсрез x
и добавляет или перезатирает элемент на родительском срезе y
Full slice expression - x[low : high : max]

Когда мы подсрез превышает cap, то происходит перевыделение среза в памяти
и подсрез становится срезом со своей собственной памятью независимым от родительского среза

##Функция copy
Копирует элементы из второго аргумента в первый. Меняет первый аргумент.
Будет скопировано количество элементов равное длине первого аргумента.
Возвращает количество скопированных элементов.
x := []int{1, 2, 3, 4}
y := make([]int, 4)
num := copy(y, x)
fmt.Println(y, num) // y - [1, 2, 3, 4], num - 4

num := copy(x[:3], x[1:]) // можно копировать подсрез в подсрез
fmt.Println(x, num)

Точно также можно копировать из массива и в массив.

Данные компируются в массив, память раздельная!!!

Можно использовать общю память через преобразование среза в указатель на массив
xArrayPointer := (*[4]int)(xSlice) // общая память

##Отображения

var nilMap map[string]int // будет присвоено нулевое значение - nil, имеет нулевую длину.
totalWins := map[string]int{} // объявление при помощи литерала отображения.
teams := map[string][]string{
    "Oliers": []string{"Semenko", "Pittsburg", "Lemieux"},
    "Iggles": []string{"Yzerman", "Gretzky", "Kurri"},
    "Flames": []string{"Jagr", "Sidney", "Gretzky"},
}

ages := make(map[int][]string, 10) // имеет нулевую длину, но выделена емкость равная 10

Можно узнать сколько пар "ключ - значение" содержит отображение используя функцию len
Нельзя сравнивать два отображения через == или !=
Если обратиться по ключу, которому не было присвоено значение, то результатом будет нулевой значение того типа,
к которому относятся значения отображения.

Идиома "запятая-ok"
Чтобы проверить есть ли в отображении ключ можно применить такую конструкцию
v, ok := teams["Oliers"] // v содержит значение, ok содержит boolean, true - ключ существует, false - ключ отсутствует.

Чтобы удалить значение из отображения, нужно применить функцию delete:
delete(teams, "Iggles") // удаляет "ключ - значение" по ключу, функция идемпотентна

Очистка отображения
clear(teams) // получим отображение с нулевой длиной и без элементов

Сравнение отображений происходит через пакет maps
maps.Equal и maps.EqualFunc аналогичны функциям slices.Equal и slices.EqualFunc
maps.Equal(map1, map2), maps.EqualFunc(map1, map2, func)

В языке Go нет множеств (set), их можно имитировать через отображения(map)
intSet := map[int]bool{}
if intSet[100] {
    fmt.Println("100 in in the set")
}
Для более оптимизированного по памяти множества можно использовать структуры в качестве значения
intSet := map[int]struct{}{}
if _, ok := intSet[100]; ok {
    fmt.Println("100 in in the set")
}

##Анонимные структуры
Переменная реализует структурный тип без имени
var john struct {
    name string
    age int
    pet string
}
john.name = "John"
john.age = 30
john.pet = "dog"

pet := struct {
    name string
    kind string
}{
    name: "Fido",
    kind: "dog"
}

Анонимные структуры применяются в двух случая: 
1) Преобразование внешних данных в структуры или, наоборот, структуры во внешние данные,
например данные в формате JSON или буферы протоколов. Эти виды преобразований называют
маршалингом и демаршалингом соответственно.
2) Написание тестов. Срез анонимных структур используется при написании табличных тестов.

##Сравнение и преобразование структур
Если все поля структуры являются сравнимыми, то и сама структура является сравнимой.
Если некоторые поля - это срезы или отображения, или функции и каналы, то такая структура является несравнимой.
Нельзя сравнивать структуры разных типов.
Можно преобразовывать одну структуру в другую. Если поля обеих структур имеют одинаковые поля и типы и расположены в одинаковом порядке.

type firstPerson struct {
    name string
    age int
}

type secondPerson struct {
    name string
    age int
}

type thirdPerson struct {
    age int
    name string
}

type fourthPerson struct {
    firstName string
    age int
}

type fifthPerson struct {
    name string
    age int
    favoriteColor string
}

firstPerson и secondPerson можно преобразовывать друг в друга, но сравнивать нельзя.
thirdPerson и fourthPerson нельзя преобразовать ни в кого, разный порядок полей и разные названия полей.
fifthPerson нельзя преобразовать в нее, так как имеет дополнительное поле.

Анонимные структуры можно сравнивать с именованными без преобразования,
если поля обеих структур имеют одинаковые имена и типы и расположены в одинаковом порядке.
Также можно выполнять присвоение между переменными именованного и анонимного типов, при том же условии.

Затеняющая переменная меняет значение лишь внутри своего блока, значение во внешнем блоке остается неизменным.
Затенить можно и имя пакета, например создав переменную fmt := "oops"

var total int
for i := 0; i <= 10; i++ {
    total := total + 1 // total справа от = всегда берет внешнюю переменную.

}

Они называются предопределенными идентификаторами в всеообщем блоке(universe block), включающем в себя все остальные блоки.

##Оператор for
Это единственный способ организации цикла
Четыре разновидности оператора for: 
1) Полная форма
2) Использующий толко условие
3) Бесконечный
4) for-range

Обязательно использует := для инициализации переменных
for i := 0; i < 10; i++ {
    fmt.Println(i)
}

Можно опустить одну или несколько из трех частей оператора for
for ; i < 10; i++  { ... }
for i := 0; i < 10; { ... }
for i < 10 { ... }
for { ... } // бесконечный цикл

break позволяет немедленно выйти из цикла.
continue позволяет закончить текущюу итерацию в цикле.

For-range цикл:
Идиомы: для ключа используется i(от слова index - массивы, срезы или строки) или k(от слова key - отображения).
Если тело цикла содержит большое количество логики лучше использовать более описательные имена, вместе i/k и v.
Если не планируете использовать ключи, вставьте вместо i/k символ нижнего подчеркивания (_)
Если не планируете использовать значения, просто опустите вторую переменную v
evenVals := []int{2, 4, 6, 8, 10, 12}
for i, v := range evenVals {
    fmt.Println(i, v)
}

В Go в отображениях порядок ключей и значений при обходе будет меняться, иногда повторяясь.
Это сделано из соображений безопасности. Если отображение всегда хэширует элементы в одни и те же значения,
то можно добиться реального замедления работы сервера с помощью Ddos-атаки на основе хеш-коллизий (Hash Dos),
Отправив серверу специально подготовленные данные, все ключи которых хешируются в одно и то же ведро.

Хеш-алгоритм для отображений генерирует случайное число при каждом создании переменной отображения.
При обходе отображеня при помощи for-range порядок обхода меняется.

Однако функции форматирования, такие как fmt.Println, всегда выводят отображения в порядке возрастания ключей.

for-range при обходе строк перебирает РУНЫ, а не БАЙТЫ.
Из-за того что одна руна может достигать 4 байт, индексы могут пропускать до 3х значений.
Индекс всегда будет увеличиваться на то количество байтов, которое содержит руна(от 1 до 4)
Индекс всегда содержит количество байтов от начала строки.

При обходе любого составного типа цикл for-range копирует значение из этого составного типа.

##Оператор defer
В Go код для очистки ресурсов добавляется в функцию с помощью ключевого слова defer
func main() [
    if len(os.Args) < 2 {
        log.Fatal("no file specified")
    }
    f, err := os.Open(os.Args[1])
    if err != nill {
        log.Fatal(err)
    }
    defer f.Close() // гарантирует запуск кода в случае выхода из функции.
    data := make([]byte, 2048)
    for {
        count, err := f.Read(data)
        os.Stdout.Write(data[:count])
        if err != nil {
            if err != io.EOF {
                log.Fatal(err)
            }
            break
        }
    }
]
Можно использовать defer несколько раз, код будет выполнен по принципу LIFO (last in - first out)
То есть оператор defer, указанный последним, выполнится первым.
Код defer выполняется после оператора возврата (return).
В оператор defer можно указать функцию с некоторыми входными параметрами. Входные параметры вычисляются незамедлительно,
а их значения сохраняются до тех пор, пока функция е будет запущена.
func deferExample() int {
    a := 10
    defer func(val int) {
        fmt.Println("first:", val) // Выведется третьим
    }(a)
    a = 20
    defer func(val int) {
        fmt.Println("second:", val) // Выведется вторым
    }(a)
    a = 30
    fmt.Println("exiting:", a) // Выведется первым
    return a
}
В операторе defer можно указать функцию с возвращаемыми значениями, но вы не сможете их прочитать.

Возможность отложенных фунций читать и модифицировать возвращаемые значения фунцкии,
которая ее содержит, - это одна из главных причин использования именованных возвращаемых значений.

Пример использования оператора defer для высвобождения транзакций базы данных
func DoSomeInsers(ctx context.Context, db *sql.DB, value1, value2 string) (err error) {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer func() {
        if err == nil { // проверяем именованное возвращаемое значение
            err = tx.Commit() // обновляем именованное возвращаемое значение
        }
        if err != nil {
            tx.Rollback()
        }
    }()
    _, err = tx.ExecContext(ctx, "INSERT INTO FOO(val) values $1", value1)
    if err != nil {
        return err
    }
    // здесь можно выполнить еще ряд операций вставки, используя tx
    return nil
}

В Go широко используется следующий паттерн: функция, которая выделяет некоторый ресурс,
также возвращает замыкание, которое высвобождает этот ресурс.
func getFile(name stirng) (*os.File, func(), error) {
    file, err := os.Open(name)

        retunr nill, nill, err
    }

        file.Close()

    log.Fatal(err)
}

срезы передаются тоже по дескриптору, но если во внутренней функции будет увеличен размер среза(длина), то в этот момент создастся копия

##Указатели
Указатель - это переменная, содержащая адрес ячейки памяти, в которой размещено значение.
Нулевое значение - nil
var pointer *string // pointer содержит nil, но при компиляции указывает на нулевой адрес(указывает никуда)
Срезы, отображения, функции, каналы и интерфейсы реализованы при помощи указателей.

Символом & обозначается оператор взятия адреса.
Символом * обозначается оператор разыменования. Возвращает значение по адресу.
x := 10
pointerToX := &x // возвращает адрес ячейки, в которой находится значение.
fmt.Println(pointerToX) // ввыведет адрес в памяти
fmt.Println(*pointerToX) // выведет 10

var x *int
fmt.Println(x == nil) // true
fmt.Println(*x) // попытка разыменовать нулевой указатель выдаст панику

var x = new(int)
fmt.Println(x == nil) // false
fmt.Println(*x) // выведет 0

x := &Foo{} // указатель на структуру
var y string
z := &y // указатель на строку

Функция, которая возвращает указатель на переданное значение
func makePointer[T any](t T) *T {
    return &t
}
Указатели служат признаком изменяемых параметров.
Если функция применяет указатель, значит она скорее всего попытается изменить значение по этому указателю.
Применение указателей может затруднять анализ потоков данных и увеличивать объем работы, выполняемой сбощиком мусора.
Не используйте функции для заполнения структуры по указателю.

Использовать парамтер ссылочного типа для изменния переменной следует лишь в том случае,
когда функция принимает интерфейс.
f := struct {
    Name string `json:"name"`
    Age int `json:"age"`
}{}
err := json.Unmarshal([]byte(`{"name": "Bob", "age": 30}`), &f)
Функция Unmarshal принимет срез байтов и параметр типа any.
Параметр типа any должен передаваться по указателю, иначе ошибка.
Передача данных по указателю медленнее, если данные не превышают 1 Мбайт.
Передача данных по указателю быстрее, если данные превышают 1 Мбайт.

Срезы применяются для чтения данных из файлов без указателей
data := make([]byte, 100)
for {
    count, err := file.Read(data)
    process(data[:count])
}

Указатели применяются для отсуствия значения
func findUser(id int) *User {
    if notFound {
        return nil // только так мы можем показать пустой результат, а для этого нужен указатель.
    }
    return &user

Отображения переданные в функцию передаются по значению указателя, изменения влияют на оригинал

Срез передается тоже как структура из 3х полей (указатель, длина, емкость).
Все изменения значений в срезе БЕЗ ИЗМЕНЕНИЯ ДЛИНЫ - отобразятся в исходном срезе.
Если длина изменится, исходный срез ну увидит новых значений.
Если емкость изменится, то в этот момент срез скопируется в новую область,
и все последующие изменения не повлияют на исходный срез.

В Go подразумевается исключение ненужного распределения памяти. Вместо того
чтобы выделять новую память при выполнении каждой операции чтения из источника
данных, необходимо один раз создать срез байтов и использовать его в качестве
буфера для четния из источника.
Это уменьшает объем работы, выполняемой сборщиком мусора.
Под мусором в программировании понимаются данные, на которые не указывает ни один указатель.

Стек и куча
Стек - это непрерывный блок памяти, который используется всеми вызовами функций в потоке выполнения.
Указатель стека указывает на то место, где память выделялась в последний раз, и дополнительная память
добавляется путем смещения указателя стека.
В стеке хранятся локальные переменные и передаваемые функции параметры.
При этом каждая новая переменная смещает укзатель стека на длину, равную своему значению.
Когда функция завершает работу, возвращаемые ею значения копируются обратно в вызывающую функцию
с помощью стека и указатель стека возвращается в начало кадра стека для закончившей работу функции.
Особождается память в стеке, которая была занята локальными переменными и параметрами этой функции.

Чтобы сохранить что-либо в стеке, необходимо точно знать его размер на этапе компиляции.
Все типы значений в языке Go(простые типы, массивы и структуры) занимают строго определенный
объем памяти, известный на этапе копиляции.
Имена поэтому размер считается частью типа массива.
Стек в го может увеличиваться во время выполнения программы
Плюсы: в Go стек изначеально имеет небольшой размер
Минусы: при увеличении стека, нужно полностью копировать его в новое место.
В худшем случае можно написать код, который попеременно будет увеличивать и уменьшать стек.

Данные, на которые указывает указатель, могут размещаться в стеке если
1) Это локальная переменная с определенным размером на этапе компиляции
2) Указатель не должен быть возвращен из функции.
3) Если компилятор Go увидит, что из функции возвращается указатель, указывающий
на локальную переменную функции, то он разместит ее в куче.

Куча - это память, управление которой осуществляется сборщиком мусора.
Размещенные в куче данные остаются корректными до тех пор, пока их можно проследить
до размещенной в стеке переменной ссылочного типа.
Когда не остается указателей, указывающих на эти данные, эти данные становятся мусором,
которы должен быть удален сборщиком мусора.

Основная проблема кучи - производство мусора, который надо убирать сборщиком мусора.
На это тратится ресурсы вычислительного устройства и время работы программы.
Алгоритмы сборки мусора делятся на 2 категории:
1) Алгоритмы, призванные обеспечить максиальную пропскную способность(то есть выявление
максимального количества мусора за одно сканирование)
2) Алгоритмы, призванные обеспечить минимальную задержку (то есть максимально быстрое
сканирование на наличие мусора)
В статье The Tail at Scail 2013 года рекомендуется использовать алгоритмы с минимальной задержкой(2).
В Go используется алгоритм с минимальной задержкой. Каждый цикл занимает не более 500 мкс.
Болле подробно о реализации сборщика мусора в Go можно узнать из доклада
Rick Hudson на международно симпозиуме по управлению памятью 
International Symposium on Memeory Management, ISMM в 2018 году

Еще одна проблема кучи - это разброс данных по памяти.
Вычислительному устройству удобнее читать память последовательно, как в стеке.
В случае с указателями данные разбросаны по всей памяти - это замедляет чтение.
Скорость может падать на 2 порядка (в 100 раз)

Такой подход к разработке программного обеспечения с учетом особенностей аппаратного обеспечения,
предназначенного ля его запуска, называется механической симпатией. 
Механическая симпатия - термин из мира автомобильных гонок, где он означает, что водитель, который
понимает, как работает его автомобиль, сможет выжать из него максимум скорости.
Применяя рекомендуемые методы работы в Go, вы обеспечите соблюдение этого принципа автоматически.

##Настройки сборщика мусора
GOGC - переменная окружения. Собрщик мусора определяет размер кучи в конце цикла сборки мусора
по формуле CURRENT_HEAP_SIZE + CURRENT_HEAP_SIZE * GOGC / 100, который должен быть дотигнут для
запуска следующего цикла сборки мусора
GOGC по умолчанию 100. Если увеличить, то сборщик мусора будет запускаться реже, если уменьшить - чаще.
GOGC раный off - отключает сборку мусора.

GOMEMLIMIT - задает ограничение на общий объем памяти, который разрещено использовать программе.
По умолчанию он отключен (технически ему присвоено значение math.MaxInt64)
Значение указывается в байтах, но есть возможность использовать суффиксы B, KiB, MiB, GiB, TiB.

Имя приемника идиоматически сокращается до одной буквы.
Методы можно объявлять только на уровне блока пакета, функции - внутри любого блока.
Методы нельзя перегружать.

Если метод вносит изменения в приемник, необходимо использовать указательный тип.
Если метод можт вызываться для экземляров с нулевым значением, необходимо применять указатель.
Если метод не вносит изменений в приемник, то можно использовть значимый тип.

Если хотя бы один из методов принимает приемник по указателю, то для единообразия рекомендуется
принимать приемник по указателю во всех методах, включая те, которые не изменяют приемник. 

Go автоматически разыменует/возьмет указатель для метода, неважно какой приемник использует метода,
по указателю или по значению. 

Приемник по значению - это копия, все изменения не повлияют на оригинал.

Доступ к полям типов рекомендуется выполнять напрямую.

Метод может использовать приемник со значением nil. Если приемник передается по значению, то будет паника.
Если приемник передается по указателю, то все зависит от внутренней реализации.

Принимайте интерфейсы и возвращайте структуры.
Это означает, что выполняемая функциями бизнес-логика должна вызываться посредством интерфейсов,
а результаты функции должны представлять собой конкретные типы.
Когда функция возвращает конкретный тип, вы можете добавлять в него новые методы и поля,
не нарушая работу существующего кода. Но это не относится к интерфейсам. После добавления нового метода
в интерфейс придется обновить все существующие его реализации, иначе работа вашего кода нарушится.
Изменение конкретного типа сохраняет обратную совместимость с прошлой версией программы.
Изменение интерфейса обратная совместимость нарушается.
Возврат структуры позволяет обойтись без выделения памяти в куче, что снижает работу сборщика мусора.
Но вызов функции с параметрами интерейсного типа каждый из них размещается в куче.
Если программа работает медленно, постарайтесь переписать функции так, чтобы они принимали конкретный тип.
Если в функцию передается несколько реализаций интерфейса, попробуйте создать несколько функций
с повторяющейся логикой.

Интерфейсы и значение nil
В среде выполнения Go интерфейсы реализованы как структура с двумя полями-указателями: один служит
ссылкой на значение, а другой - на тип значения.
Пока поле типа не равно nil, интерфейс не равен nil.(Поскольку переменная всегда имеет определенный тип,
если ссылка на значение не равна nil, то и ссылка на тип не будет равна nil.)

Интерфейс считается равным nil в том случае, когда оба указателя, ссылающиеся на значение и тип, равны nil.
var pointerCounter *Counter // конкретный ссылочный тип на структуру, без значения
fmt.Println(pointerCounter == nil) // true
var incrementer Incrementer // интерфейс, type = nil, value = nil
fmt.Println(incrementer == nil) // true
incrementer = pointerCounter // type = *Counter, value = nil - это типизированный nil
fmt.Println(incrementer == nil) // false

Пакет database/sql/driver в стандартной библиотеке объявляет набор интерфейсов, которые описывают,
что должен предоставлять драйвер базы данных. Из функций там возвращаются интерфейсы.
Существующие интерфейсы не будут расширяться и дополняться новыми функциями, вместо этого
разработчики языка Go будут выпускать новые интерфейсы для параллельной реализации со старыми.

##Интерфейсы можно сравнивать
Объекты, реализующие один и тот же интерфейс, можно сравнивать
Указатели на объекты сравнимых типов можно сравнивать, true будет если и тип и указатель равны
Указатели на объекты несравнимых типов нельзя сравнивать, например срезы вызовут панику
В случае отображений, ключи отображений должны иметь сравнимый тип.

Пустой интерфейс сообщает, что переменная может содержать любое значение, тип которого реализует

##Утверждение типа
Утверждение типа определяет конкретный тип, реализующий данный интерфейс, или другой интерфейс, который
также реализуется базовым конкретным типом итерфейса, значение которого хранится в исследуемой переменной.

type MyInt int

func main() {
    var i any
    var mine MyInt = 20
    i = mine
    i2 := i.(MyInt) // Утверждаем тип (закрепляем его)
    fmt.Println(i2 + 1)
    i2 := i.(string) // Сгенерирует панику
    // panic: interface conversion: interface {} is main.MyInt, not string
    // чтобы избежать паники, возмпользуемся идиомой "запятая-ok"
    i2, ok := i.(int)
    if !ok {
        return fmt.Errorf("unexpected type for %v", i)
    }
    fmt.Println(i2 + 1)
}

Операции преобразования типа могут применяться и к конкретным типам, и к интерфейсам, проверяются на этапе компиляции.
Операции утверждения типа могут применяться только к интерфейсным типам и проверяются на этапе выполнения программы.
При утверждении типа лучше всегда пользоваться идиомой запятая-ok, потому что неизвестно, как ваша программа изменится спустя время.

Если тип точно неизвестен, его можно раскрыть, для этого используется переключатель типа
func doThings(i any) {
    switch j := i.(type) { // идиоматический подход - i := i.(type)
    case nil:
        // переменная i равна nil, переменная j имеет тип any
    case int:
        // переменная j имеет тип int
    case bool, rune
        // переменная i имеет тип bool или rune, j имеет тип any
    default:
        // неизвестно, что содержит переменная i, j имеет тип any
    }
}

Лучше как можно реже использовать утверждение типа и переключатель типа.
Обычно утверждение типа используется, чтобы проверить реализует ли переменная интерфейс,
Если базовый тип неизвестен, применяйте рефлексию.

Если есть конкретный тип, который реализует интерфейс A и интерфейс B. Мы обернули этот тип в декоратор,
который реализует только интерфейс A. Утверждение типа B на декораторе не получится.
В случае с ошибками можно исопльзовать errors.Is - для определения ошибки или errors.As - для преобразования ошибки в нужный тип.

После преобразования в тип http.HandlerFunc любая функция с сигнатурой func(http.ResponseWriter, *http.Request)

Функции в Со являются полноценными объектами и часто передаются другим функциям в качестве параметров.
Go поощряет использование небольших интерфейсов, и интерфейс, имеющий единственный метод, может заменить

Если речь идет о случае, когда одна функция может зависеть от многих других функций или другого состояния,

Именно так сделано в пакете http, где Handler может быть лишь точкой входа в цепочку вызовов.
Однако если речь идет о простой функции, например sort.Slice, лучше задействовать параметр функционального типа.

##Обобщенные типы (дженерики)
Обобщенные типы уменьшают количество повторяющегося кода и повышают типобезопасность.
Реализация стека на основе обобщенных типов:
type Stack[T any] struct { // T - имя, any - ограничение типа
    vals []T
}
func (s *Stack[T]) Push(val T) {
    s.vals = append(s.vals, val)
}
func (s *Stack[T]) Pop() (T, bool) {
    if len(s.vals) == 0 {
        var zero T // идиоматический способ вернуть нулевое значение для значимого типа
        return zero, false
    }
    top := s.vals[len(s.vals)-1]
    s.vals = s.vals[:len(s.vals)-1]
    return top, true
}
func main() {
    var initStack Stack[int]
    initStack.Push(10)
    initStack.Push(20)
    v, ok := initStack.Pop()
}

Чтобы иметь возможность сравнивать надо использовать тип comparable
type Stack[T comparable] struct {
    vals []T
}
func (s Stack[T]) Contains(val T) bool {
    for _, v := range s.vals {
        if v == val { // без comparable это не скомпилируется
            return true
        }
    }
    return false
}

##Обобщенные функции

// Функция Мар преобразует срез типа []Т1 в срез типа []Т2, используя
// отображающую функцию. Эта функция принимает два параметра типа, Т1 и Т2. 
// Ее можно применять для срезов любого типа.
func Map[T1, T2 any] (s []T1, f func(T1) T2) []T2 {
    r := make([]Т2, len(s))
    for i, v := range s {
        r[i] = f(v)
    }
    return r
}

// Функция Reduce редуцирует срез типа []Т1 до одного значения,
// используя редуцирующую функцию.
func Reduce[T1, T2 any](
    s []T1,
    initializer T2,
    f func(T2, Т1) T2
) T2 {
    r := initializer
    for _, v := range s {
        r = f(r, v)
        return r
    }
}

// Функция Filter фильтрует значения среза, используя функцию фильтрации.
// Она возвращает новый срез, содержащий только те элементы среза s,
// для которых функция f возвращает значение true.
func Filter[T any](s []T, f func(T) bool) []T {
    var r []T
    for _, v := range s {
        if f(v) {
            r = append(r, v)
        }
    }
    return r
}

words := []string{"One", "Potato", "Two", "Potato"}
filtered := Filter(words, func(s string) bool {
    return s != "Potato"
})
lengths := Map(filtered, func(s string) int {
    return len(s)
})
sum := Reduce(lengths, 0, func(acc int, val int) int {
    return acc + val
})

Теперь можно объявить функцию с обобщенным ограниченным типом
func FindCloser[T Differ[T]]FindCloser(pair1, pair2 Pair[T]) Pair[T] {
    d1 := pair1.Val1.Diff(pair1.Val2)
    d2 := pair2.Val2.Diff(pair2.Val2)
    if d1 < d2 {
        return pair1
    }
    return pair2
}

##Списки типов для определения операторов
type Integer interface { // такой интерфейс может использоваться только, как ограничитель типа

func Sum[T int | int64 | float64](nums ...T) T // ok
Sum(1, 2, 3) // ok
Sum(1.0, 2.0, 3.0) // ok
Sum(1. 2.0) // ошибка, разные типы

В Go нет и не будет специализации, каррирования(currying), метапрограммирования.

##Ошибки
Обработка ошибок в Go сводится к возврату значения типа error в качестве последнего возвращаемого значения функции.
Это общепринятое соглашение и его никогда не следует нарушать.
Если программа выолняется ожидаемым образом, то в качестве параметра ошибки возвращается значение nil.
При возврате ошибки остальным возвращаемым значениям следует присвоить соответствующие нулевые значения.

func calcRemainderAndMod(numerator, denominator int) (int, int, error) {
    if denominator == 0 {
        return 0, 0, errors.New("denominator is 0") // новая ошибка создается через New из пакета errors
                                                    // нулевые значения присвоены всем остальным параметрам
    }
    return numerator / denominator, numerator % denominator, nil
}

func main() {
	numerator := 20
	denominator := 3
	remainder, mod, err := calcRemainderAndMod(numerator, denominator)
	if err != nil { // используем if чтобы проверить наличие ошибки
		fmt.Println(err)
		os.Exit(1)
	}
	fmt.Println(remainder, mod)
}

Тип error - это встроенный интерфейс, который определяет метод:
type error interface {
    Error() string
}

Есть 2 способа создать ошибку
errors.New("Message") // создает ошибку, которую впоследствии можно получить вызвав метод Error()
fmt.ErrorF("%d isn't an even number", i) // создает ошибку с отформатированной строкой

Сигнальные ошибки
Определить можно так
var ErrInvalidID = errors.New("invalid ID")

Сигнальные ошибки обычно используют, чтобы показать, что дальнейшая обработка невозможна.
func main() {
	data := []byte("This is not a zip file")
	notAZipFile := bytes.NewReader(data)
	_, err := zip.NewReader(notAZipFile, int64(len(data)))
	if err == zip.ErrFormat { // сигнальная ошибка из пакета archive/zip
		fmt.Println("Told you so")
	}
}

Можно определить собственные ошибки:
type Status int
const (
    InvalidLogin Status = iota + 1
    NotFound
)
type StatusErr struct {
    Status Status
    Message string
}
func (se StatusErr) Error() string {
    return se.Message
}
Теперь этот код можно исопльзовать для возврата ошибок со статусом:
if err != nil {
    return nil, StatusErr{
        Status: InvalidLogin,
        Message: fmt.Sprintf("invalid credentials for user %s", uid)
    }
}
Даже если вы определяете собственные пользовательские типы ошибок, всегда применяйте
тип error в качестве типа возвращаемой ошибки. Это позволит возвращать из функци разные
типы ошибок, а вызывающая сторона при этом не будет зависеть от конкретного типа ошибок.

Всегда возвращайте инициализированный экземпляр пользовательских ошибок, иначе неинициализированная
ошибка, вернувшаяся из функции не будут равны nil
var genErr error // без инициализации базовый тип error не будет равен nil

Обертывание ошибок
Когда ошибка передается в коде в обратном направлении, часто в нее требуется внести дополнительный контекст.
Этим контекстом может быть имя функции, в которой произошла ошибка, или сведения о том, какую операцию она
пыталась при этом выполнить. Если при добавлении информации исходная ошибка сохраняется, это называют
обертыванием ошибки. Последовательность обернутых ошибок называется цепью ошибок.

Функция для обертывания ошибок - fmt.Errorf, поддерживает специальный глагол %w для создания уточненного сообщения
об ошибке. Согласно общепринятому соглашению в конце форматированной строки ошибки следует записать :%w чтобы обернуть ошибку,
переданную функции fmt.Errorf в последнем параметре.

Стандартная библиотека также предоставляет функцию для извлечения обернутых ошибок — это функция Unwrap из пакета errors.
Она принимает ошибку и возвращает обернутую ошибку, если такая существует, иначе nil


func fileChecker (name string) error {
    f, err := os.Open(name)
    if err != nil {
        return fmt.Errorf("in fileChecker: %w", err)
    }
    f.Close()
    return nil
}
func main() {
    err := fileChecker ("not_here.txt")
    if err != nil {
        fmt.Println(err)
        if wrappedErr := errors.Unwrap(err); wrappedErr != nil {
            fmt.Println(wrappedErr)
        }
    }
}
Запустив эту программу, вы получите следующий результат:
in fileChecker: open not_here.txt: no such file or directory
open not_here.txt: no such file or directory

Функция errors.Unwrap обычно не вызывается напрямую. Для поиска конкретной обернутой ошибки лучше воспользоваться функциями
errors.Is и errors.As

Если вы хотите обернуть ошибку в свой пользовательский тип, ваш тип ошибки должен реализовывать метод Unwrap() error
type StatusErr struct {
    Status Status
    Message string
    Err error
}
func (se StatusErr) Error() string {
    return se.Message
}
func (se StatusErr) Unwrap() error {
    return se.err
}

Если вы хотите создать новую ошибку, которая содержала бы сообщение из другой ошибки, не обертывая ее при этом используйте fmt.Errorf:
if err != nil {
    return fmt.Errorf("internal failure: %v", err)
}

Обертывание сразу нескольких ошибок, например при валидации полей используйте errors.Join:
package main

import (
	"errors"
	"fmt"
)

type Person struct {
	FirstName string
	LastName  string
	Age       int
}

func ValidatePerson(p Person) error {
	var errs []error
	if len(p.FirstName) == 0 {
		errs = append(errs, errors.New("field FirstName cannot be empty"))
	}
	if len(p.LastName) == 0 {
		errs = append(errs, errors.New("field LastName cannot be empty"))
	}
	if p.Age < 0 {
		errs = append(errs, errors.New("field Age cannot be negative"))
	}
	if len(errs) > 0 {
		return errors.Join(errs...)
	}
	return nil
}

func main() {
	err := ValidatePerson(Person{
		FirstName: "",
		LastName:  "",
		Age:       -1,
	})
	fmt.Println(err)
}

Можно объединить несколько ошибок через fmt.Errorf:
err1 := errors.New("first error")
err2 := errors.New("second error")
err3 := errors.New("third error")
err := fmt.Errorf("first: %w, second: %w, third: %w", err1, err2, err3)

Можно создать свой тип
type MyError struct {
    Code int
    Errors []error
}
type (m MyError) Error() string {
    return errors.Join(m.Errors...).Error()
}

Если приходится обрабатывать ошибки, которые могут содержать ноль, одну или несколько ошибок,
то используйте этот код в качестве основы:
var err error
err = funcThatReturnsAnError()
switch err := err.(type) {
case interface{ Unwrap() error }:
    // handle single error
    innerErr := err.Unwrap()
    // process innerErr
    fmt.Println(innerErr)
case interface{ Unwrap() []error }:
    //handle multiple wrapped errors
    innerErrs := err.Unwrap()
    for _, innerErr := range innerErrs {
        // process each innerErr
        fmt.Println(innerErr)
    }
default:
    // handle no wrapped error
}

Функции Is и As
Чтобы проверить, не совпадает ли возвращаемая ошибка или какая-либо из завернутых в нее ошибок с определенным
экземляром сигнальной ошибки, следует использовать функцию errors.Is
errors.Is(err, os.ErrNotExist) // вернет либо true, либо false

Is сравнивает ошибки через ==, если это не подходит для вашего пользовательского типа ошибки
определите собственную реализацию Is для пользовательского типа ошибки
type MyErr struc {
    Codes []int // несравнимый тип среза делает структуру несравнимым типом
}
func (me MyErr) Is(target error) bool {
    if me2, ok := target.(MyErr); ok {
        return slices.Equal(me.Codes, me2.Codes)
    }
    return false
}

Иногда требуется сравнить ошибки по маске указав фильтрующий экзамляр, выявляющий совпадение по некоторым полям.
Если требуется, чтобы два экземпляра ошибки ResourceErr считались совпадающими при совпадении хотя бы одного из полей,
это можно сделать, определив свой метод Is:
package main

import (
	"errors"
	"fmt"
)

func main() {
	err := ResourceErr{"Database", 123}

	// errors.Is вызывает наш метод Is(...)
	// Здесь мы проверяем: совпадает ли только Resource
	if errors.Is(err, ResourceErr{Resource: "Database"}) {
		fmt.Println("match by resource")
	}

	// Здесь проверяем: совпадает ли только Code
	if errors.Is(err, ResourceErr{Code: 123}) {
		fmt.Println("match by code")
	}

	// Здесь проверяем совпадение обоих полей
	if errors.Is(err, ResourceErr{"Database", 123}) {
		fmt.Println("match by both")
	}
}

// Наша кастомная ошибка
type ResourceErr struct {
	Resource string
	Code     int
}

func (e ResourceErr) Error() string {
	return fmt.Sprintf("%s:%d", e.Resource, e.Code)
}

// Этот метод автоматически используется errors.Is(...)
func (e ResourceErr) Is(target error) bool {

	// Проверяем, что target тоже ResourceErr
	t, ok := target.(ResourceErr)
	if !ok {
		return false
	}

	// Если поле в target = zero-value,
	// считаем его "неважным" (wildcard)
	matchResource := t.Resource == "" || t.Resource == e.Resource
	matchCode := t.Code == 0 || t.Code == e.Code

	// Совпадение, если оба условия выполняются
	return matchResource && matchCode
}

Функция errors.As позволяет проверить совпадение возвращаемой ошибки (или любой ошибки, завернутой в нее) с определенным типом.
Эта функция принимает два параметра: проверяемую ошибку и указатель на переменную искомого типа. Она возвращает значение true
при наличии в цепи ошибок совпадающей ошибки, которая затем присваивается второму параметру. При отсутствии совпадений в цепи
ошибок возвращается значение false.

err := AFunctionThatReturnsAnError()
var myErr MyErr
var coder interface {
    CodeVals() []int
}
if errors.As(err, &myErr) {
    fmt.Println(myErr.code)
}
if errors.As(err, &coder) {
    fmt.Println(coder.CodeVals())
}

Функция errors.As сгенерирует панику, если во втором параметре передать ей не указатель на ошибку или интерфейс, а что-то иное.

По аналогии с функцией errors.Is можно переопределить функцию errors.As.
Переопределение функции errors.As является нетривиальной задачей и требует применения рефлексии.

Применяйте errors.Is, когда требуется выявить определенный экземпляр или определенные значения.
Если нужно выявить определенный тип, применяйте errors.As

##Обертывание ошибок с помощью оператора defer
В некоторых случаях требуется завернуть в одно и то же сообщение несколько ошибок:
func DoSomeThings (val1 int, val2 string) (string, error) {
    val3, err := doThing1 (val1)
    if err != nil {
        return "", fmt.Errorf("in DoSomeThings: %w", err)
    }
    val4, err := doThing2(va12)
    if err != nil {
        return "", fmt.Errorf("in DoSomeThings: %w", err)
    }
    result, err := doThing3 (val3, va14)
    if err != nil {
        return "", fmt.Errorf("in DoSomeThings: %w", err)
    }
    return result, nil
}
Такой код можно упростить с помощью оператора defer:
func DoSomeThings (val1 int, val2 string) (_ string, err error) {
    defer func() {
        if err != nil {
            err = fmt.Errorf("in DoSomeThings: %w", err)
        }
    }()
    val3, err := doThing1 (val1)
    if err != nil {
        return "", err
    }
    val4, err := doThing2(val2)
    if err != nil {
        return "", err
    }
    return doThing3 (val3, va14)
}

##Функции panic и recover
В Go паника генерируется всякий раз, когда среда выполнения оказывается неспособной определить,
что делать дальше. После генерирования паники немедленно прекращается выполнение текущей функции.
Программа завершится, если любая горутина сгенерирует панику и не попытается восстановится после нее.

func doPanic(msg string) {
    panic(msg)
}

Можно перехватить панику.
Для этого нужно внутри оператора defer вызвать функцию recover() и проверить, была ли сгенерирована паника.
Вызов recover() должен производится внутри defer, поскольку при генерировании паники выполняются только отложенные фунции.
func div60(i int) {
    defer func() {
        if v := recover(); v != nil {
            fmt.Println(v)
        }
    }()
    fmt.Println(60 / i)
}

Используйте панику при фатальных ошибках системы. Продолжать работу после паники требуется крайне редко.
Компьютер исчерапал память -> panic -> defer -> recover -> отправка сведений в ПО мониторинга -> прекращение выполнения программы os.Exit(1)

##Модули, пакеты и операции импорта
Управление библиотеками в Go основано на трех концепциях, таких как репозитории, модули и пакеты.
Репозиторий - это место в системе управления версиями, где хранится исходный код проекта.
Модуль - это коплект исходного кода на Go, который хранится в репозитории и распространяется, как единое целое.
Каждый модуль включает один или несколько пакетов.
Пакет - это каталог с исходным кодом, что придает модулю определенную структуру.

Желательно в одном репозитории хранить один модуль. Содержимое модуля версионируется, как единое целое.

Для использования кода пакетов, не входящих в стандартную библиотеку, каждый пакет должен быть объявлен, как модуль,
обладающий глобально уникальным идентификатором.
В качесте идентификатора обычно используется путь к репозиторию.
Репозиторий в GitHub: https://github.com/jonbodner/proteus
Путь к нему имеет вид github.com/jonbodner/proteus

Файл go.mod
Древо каталогов с исходным кодом на языке Go становится модулем в том случае, если в его корневом каталоге имеется корректный
файл go.mod.
go.mod можно создать вручную, но лучше это сделать через команды go.mod
go mod init ПУТЬ_К_МОДУЛЮ создаст файл go.mod в директории

module github.com/author/module_name // уникальный путь к текущему модулю

go 1.25.6 // минимальная совместимая версия языка. Весь код внутри модуля должен быть совместим с этой версией

require (
    github.com/random_author1/module1 v1.3.1 // прямая зависимость
    github.com/random_author2/module2 // прямая зависимость
)

require (
    github.com/random_author3/module3 v2.4.2 // зависимость зависимости
    golang.org/x/sys v0.0.0-223423 // зависимость зависимости
)

Выбор версии Go для сборки кода с помощью директивы go
Если установлен Go 1.20 или более ранняя, а в директиве go будет указана версия языка выше, то директива будет проигнорирована,
и будут доступны возможность только той версии, которая установлена.
Если установлен Go 1.21 или более поздняя, а в директиве go будет указана версия языка выше, то по умолчанию будет загружена
более позняя версия языка и она будет использована для сборки кода.

Управлять этим поведением начиная с Go 1.21 можно при помощи директивы toolchain и переменной окружения GOTOOLCHAIN.
Им можно присвоить следующие значения:
auto - загружает более новые версии Go
local - восстанавливает поведение версий, предшествовавших Go 1.21
можно указать, конкретную версию, например go1.20.4, она будет загружена и использована для сборки программы.

Это можно использовать прямо в момент вызова компилятора:
GOTOOLCHAIN=go1.18 go build 

Напомним, что цикл for-range в версии языка 1.22 содает новые переменные каждую итерацию цилка,
более ранние версии языка копируют значения элементов в одну и ту же переменную.

В директиве require перечислены зависимости модуля и их минимальная версия.
Первая секция require перечисляет зависимости. Вторая секция require перечисляет зависимости зависимостей.
Обычно все строки второй секции require заканчиваются на // indirect.
Хотя строки в первой секции require тоже могут заканчиваться на // indirect, но редко.

Операции импорта и экспорта
Оператор import языка Go позволяет получить доступ к константам, переменным, функция и типам, экспортируемым
другим пакетом.
Если идентификатор внутри пакета начинается с буквы верхнего регистра, он экспортируемый, а если с буквы нижнего
регистра или с символа подчеркивания, то будет доступен только внутри пакета, в котором объявлен.

Создание пакета:
Пример файла ./math/math.go:

package math // спецификатор пакета

func Double(a int) int {
    return a * 2
}

Пример файла ./do-formt/formatter.go

package format

import "fmt"

func Number(num int) string {
    return fmt.Sprintf("The number is %d", num)
}

Корневой файл ./main.go
package main

import (
	"fmt"

	format "github.com/learning-go-book-2e/package_example/do-format"
	"github.com/learning-go-book-2e/package_example/math"
)

func main() {
	num := math.Double(2)
	output := format.Number(num)
	fmt.Println(output)
}

При импортировании пакетов, которые не входят в состав стандратной библиотеки, необходимо указывать путь импорта.
Чтобы получить путь импорта, нужно объединить путь к модулю и путь к пакету внутри модуля.
github.com/learning-go-book-2e/package_example - путь к модулю
/math - путь к пакету внутри модуля

Относительных путей импорта в Go нет.

Имена пакетов находятся в блоке файла.

Каждый Go-файл, расположенный в определенном каталоге, должен обладать идентичным спецификатором пакета.
(Из этого правила есть лишь одно небольшое исключение, которое мы обсудим в подразделе "Тестирование публичного API")

Имя пакета не обязано совпадать с именем каталога. В том числе по причине возможности версионирования пакетов.
В Go не допускается импорт пакета main.

Используйте описательныей названия пакетов и функций
util.ExtractNames и util.FormatNames - плохое название, util не несет никакой информции
extract.Names и format.Names - названия лучше, функционал разбит логически на 2 пакета
names.Extract и names.Format - названия еще лучше. Методы что-то делают, поэтому их имена - глаголы, а имя пакета - существительное.

Можно импортировать пакет используя точку. Так делать не рекомендуется.
import . "fmt" // все экспортируемые имена из пакета становятся доступными без префикса пакета.
Println("Hello") // без fmt.

###Go Doc
// Package mini демонстрирует минимальный пример документации в формате Go Doc.
//
// # Overview
//
// Пакет показывает:
//   - документирование пакета

Пакет internal
Если у нас есть пакет project а в нем пакет internal
package/internal
То импортировать internal могут только те, кто находится в package/*

Go не допускает наличия циклических зависимостей между пакетами.

Если модуль небольшой, весь код следует разместить в одном пакете.

Если модуль предполагается применять только в виде приложения, объявите корневой каталог проекта пакетом main. 
Пакет main должен содержать минимальный объем кода: поместите всю логику в каталог internal, а в функции main
просто вызывайте код из пакета internal. Это даст вам уверенность, что никто не создаст модуль, зависящий от 
реализации вашего приложения.

Если модуль может использоваться в качестве библиотеки, то в его корне должен иметься пакет,
имя которого совпадает с именем репозитория. Это гарантирует совпадение импортируемого имени с именем пакета.
Не применяйте дефис в качестве разделителя слов в имени репозитория, потому что он не может появляться в именах пакетов.

Нередко бывает, что в библиотечные модули включаются одно или несколько приложений в качестве утилит.
В таком случае создайте каталог с именем cmd в корневом каталоге модуля. Внутри каталога cmd создайте по одному каталогу
для каждого двоичного файла, получаемого на основе модуля. Например, модуль может включать в себя веб-приложение и инструмент
командной строки для анализа информации, содержащейся в базе данных этого веб-приложения.
В каждом из этих каталогов используйте main в качестве имени пакета.

По возможности не используйте функцию init
registry/registry.go
package registry

var plugins = map[string]func(){}

func Register(name string, fn func()) {
	plugins[name] = fn
}

func Run(name string) {
	if fn, ok := plugins[name]; ok {
		fn()
	}
}

plugin/plugin.go
package plugin

import "app/registry"

func init() {
	registry.Register("hello", func() {
		println("hello from plugin")
	})
}

main.go
package main

import (
	"app/registry"
	_ "app/plugin" // пустой импорт ради init
)

func main() {
	registry.Run("hello")
}

Что здесь плохо?

2) всё магически происходит через init
3) порядок init может стать проблемой
4) невозможно понять поток данных, просто читая main

В Go версии привязаны к модулю, а не к репозиторию: модуль определяется go.mod в конкретной папке.
Каждая major ≥ v2 оформляется с /vX в пути, и Go считает такие версии разными модулями.
Поэтому можно одновременно использовать разные версии одного репозитория в разных местах программы,
импортируя их как отдельные пакеты. Go берет код только из папки модуля, а не весь репозиторий целиком.

replace в Go Modules позволяет подменять один модуль другим — например, локальной копией или другой версией.
Пример в go.mod:
replace example.com/old => ../local/old
replace example.com/old v1.2.0 => example.com/old v1.3.0
Первая строка — используем локальную папку вместо удалённого модуля
Вторая — подменяем конкретную версию на другую
Полезно для локальной разработки или исправления багов без публикации новой версии.

Директива replace также может ссылаться на путь в локальной файловой системе:
replace github.com/jonbodner/proteus => ../projects/proteus
Лучше не применять локальную директиву replace, особенно если вашим модулем пользуются сторонние разработчики.
Так как могут не совпасть локальные пути.

exclude в Go Modules блокирует конкретную версию модуля, чтобы её не использовали (например, из-за багов или несовместимости):
exclude github.com/jonbodner/proteus v0.10.1

Отзыв версии модуля внутри файла go.mod:
retract v1.5.0 // не полностью протестирована
retract [v1.7.0, v.1.8.5] // публикует ваши фотографии в LinkedIn без разрешения

Директива retract запрещает другим использовать определенные версии вашего модуля.
Директива exclude блокирует применение вами версий чужих модулей.

##Использование рабочих пространств (Go Workspaces)
Рабочие пространства в Go позволяют объединять несколько модулей в одну рабочую область и использовать их локальные версии
без публикации в репозитории и без добавления replace в go.mod.

Предположим, структура проекта:
my_workspace/
 ├── workspace_app
 └── workspace_lib

Чтобы модуль workspace_app видел локальную копию workspace_lib, выполняем в каталоге my_workspace:
go work init ./workspace_app
go work use ./workspace_lib

После этого создаётся файл go.work со следующим содержимым:
go 1.20

use (
    ./workspace_app
    ./workspace_lib
)

Что делает go.work:
1) Объединяет несколько модулей в одно рабочее пространство.
2) Заставляет Go использовать локальные директории, а не версии из репозитория.
3) Позволяет тестировать изменения сразу в нескольких модулях.
4) Убирает необходимость в replace.

Файл go.work предназначен только для локальной разработки.
Его не следует добавлять в систему контроля версий (Git), так как он отражает локальную конфигурацию разработчика.

GOWORK=off go build // собирает модуль игнорируя рабочее пространство

Если в будущем вам придется вносить изменения в workspace_lib и вы захотите протестировать их в workspace_app
без отправки изменений на GitHub и создания множества временных версий, то снова загрузите последние версии модулей
в рабочее пространство командой git pull и внесите изменения.

Прокси-серверы модулей в Go

В Go каждый модуль хранится в своём Git-репозитории (например, GitHub), но по умолчанию go get скачивает его через
официальный прокси Google — proxy.golang.org.

Прокси:
1) Кэширует версии модулей.
2) Защищает от удаления версий из репозиториев.

Дополнительно используется база контрольных сумм (sum.golang.org), которая:
1) Хранит хеши версий модулей.
2) Защищает от подмены или изменения уже выпущенных версий.

При скачивании Go:
1) Загружает модуль.
2) Проверяет его хеш.
3) Если хеш не совпадает — установка прерывается.

Настройка
GOPROXY=direct — скачивание напрямую из репозиториев.
Можно использовать собственный прокси (например, корпоративный).

##Конкурентность в Go
Под конкурентностью в теории вычислительных машин понимается разбиение одного процесса на несколько независимых составляющих
и определение для них безопасного способа совместного использования данных.

Модель конкурентности языка Go основана на теории взаимодействующих последовательных процессов (Communicating Sequential Processes, CSP)
Применяйте конкурентность лишь в том случае, когда она делает вашу программу лучше.

Процесс — это экземпляр программы, выполняемой операционной системой компьютера.
Операционная система связывает с процессом такие ресурсы, как память, и следит за тем, чтобы другие процессы не могли их использовать.
Процесс состоит из одного или нескольких потоков.
Поток — это единица выполнения, на работу которой операционная система дает некоторое время.
Потоки одного процесса совместно используют его ресурсы. 

Центральный процессор может выполнять инструкции из одного или нескольких потоков одновременно в зависимости от количества имеющихся у него ядер.
Одной из задач операционной системы является планирование выполнения потоков процессором таким образом,
чтобы были выполнены каждый процесс и каждый его поток.

Горутины — это легковесные потоки, которыми распоряжается среда выполнения языка Go.
При запуске Go-программы среда выполнения языка Go создает для нее несколько потоков и запускает одну горутину.
Горутины - это не потоки ОС. Несколько горутин могут жить в одном потоке. Поток будет выполнять последовательно переключаясь между ними.
// Потоков может быть 8, а горутин 100_000
for i := 0; i < 1_000_000; i++ {
    go work()
}

В качестве горутины можно запустить любую функцию.
func process(val int) int {
    // выполнить некоторые операции с val
}

func processConcurrently(inVals []int) []int {
    // создать каналы
    in := make(chan int, 5)
    out := make(chan int, 5)
    // запустить горутины, выполняющие обработку
    for i := 0; i < 5; i++ {
        go func() {
            for val := range in {
                out <- process(val)
            }
        }()
    }

    // записать данные в канал in для передачи другой горутине
    // прочитать данные из канала out
    // вернуть результат
}

Каналы
Горутины общаются друг с другом посредством каналов.
ch := make(chan int) // небуферизованный канал

Как и отображения, каналы представляют собой ссылочный тип.
Нулевое значение - nil
Передаются по указателю
a := <-ch // читает значение из канала ch и присваивает его переменной a
ch <- b   // записывает значение переменной b в канал ch

Значение, записанное в канал, можно прочитать только один раз.
Если данные из канала читают несколько горутин, то записанное в него значение прочитает только одна из них.
Горутины редко читают данные из одного и того же канала и записывают в один и тот же канал.

Канал только для чтения
func readOnly(ch <-chan int) {
    val := <-ch // читать можно
    fmt.Println(val)
    // ch <- 1 // ❌ ошибка: запись запрещена
}

Канал только для записи
func writeOnly(ch chan<- int) {
    ch <- 42 // писать можно
    // val := <-ch // ❌ ошибка: чтение запрещено
}

По умолчанию каналы являются небуферизованными.
После каждой операции записи в открытый небуферизованный канал пишущая горутина приостанавливается,
пока другая горутина не прочитает данные из этого канала. Тоже самое работает и в обратную сторону.

Go позволяет задействовать и буферизованные каналы, которые буферизуют без блокировки некоторое
ограниченное количество операций записи. Если буфер заполнится до выполнения каких-либо операций
чтения из канала, то следующая операция записи в этот канал приостановит записывающую горутину,
пока не будет произведено чтение из канала. Точно так же попытка чтения из канала с пустым буфером
приостановит читающую горутину.

ch := make(chan int, 10)
cap(ch) // размер буфера
len(ch) // количество элементов в буффере на данный момент

Для небуферизиованного канала len и cap возвращают 0.
В большинстве случаев следует применять небуферизованные каналы.

Для чтения из канала можно задействовать цикл for-range:
for v := range ch {
    fmt.Println(v)
}
Если значения нет в канале, то горутина приостанавливается, пока не появится значение или канал не закроется.
Цикл будет работать пока канал не закроется, не будет встречен оператор break или return.

После завершения записи в канал его следует закрыть вызовом встроенной функции close:
close(ch)

После закрытия канала любые попытки произвести в него запись или закрыть его снова приведут к панике.
Однако, что интересно, попытки чтения из закрытого канала всегда завершаются успехом. Если канал буферизованный
и в буфере остаются непрочитанные значения, то они будут возвращены в том же порядке, в каком были записаны.
Если канал небуферизованный или буферизованный, но с пустым буфером, то операция чтения вернет нулевое значение,
соответствующее типу канала.

Чтобы отличать нулевое значение от закрытого канала, надо использовать идиому "запятая-ok"
v, ok := <-ch
Если переменная ok получит значение true, значит, канал открыт. Если переменная ok получит значение false — закрыт.
Задача закрытия канала возлагается на горутину, которая пишет в канал.

Оператор select

Эта управляющая конструкция, предусмотренная в Go для конкурентности, позволяет изящно решить, какую из двух конкурентных
операций выполнить первой, когда нельзя сделать какую-либо из них более приоритетной, чтобы избежать проблемы невыполнения
некоторых операций. Проблема, когда какие-то операции не выполняются, потому что постоянно предпочтение отдается более
приоритетным операциям, называется голоданием.

Каждая ветвь case оператора select производит чтение из канала или запись в канал. 
select {
case v := <-ch:
    fmt.Println(v)
case v := <-ch2:
    fmt.Println(v)
case ch3 <- x:
    fmt.Println("wrote", x)
case <-ch4:
    fmt.Println("got value on ch4, but ignored it")
}
Оператор select просто выбирает случайным образом одну из ветвей, которые могут быть выполнены, не обращая внимания на порядок их выполнения.
Это полностью исключает вероятность появления проблемы голодания, поскольку все ветви обладают одинаковым приоритетом и проверяются в одно и то же время.

func main() {
    ch1 := make(chan int)
    ch2 := make(chan int)
    go func() {
        inGoroutine := 1
        ch1 <- inGoroutine
        fromMain := <-ch2
        fmt.Println("goroutine:", inGoroutine, fromMain)
    }()
    inMain := 2
    ch2 <- inMain
    fromGoroutine := <-ch1
    fmt.Println("main:", inMain, fromGoroutine)
}
fatal error: all goroutines are asleep - deadlock!
апущенная нами вторая горутина не может продолжить выполнение, пока не будет прочитано значение из канала ch1,
а основная горутина не может продолжить выполнение, пока не будет прочитано значение из канала ch2.

Исключение взаимоблокировок с помощью оператора select (1, 2, 3 - ключевые этапы выполнения по порядку)
func main() {
    ch1 := make(chan int)
    ch2 := make(chan int)
    go func() {
        inGoroutine := 1
        ch1 <- inGoroutine // 1
        fromMain := <-ch2 // зависнет на этом этапе в ожидании значения в ch2
        fmt.Println("goroutine:", inGoroutine, fromMain) // не выполнится
    }()
    inMain := 2
    var fromGoroutine int
    select {
    case ch2 <- inMain: // не выполнится
    case fromGoroutine = <-ch1: // 2
    }
    fmt.Println("main:", inMain, fromGoroutine) // 3
}

select часто оборачивают в бесконечный цикл for. Эту комбинацию называют for-select

Можно использовать default. Если default не будет, то select заблокируется, пока одна из ветвей не станет доступной для выполнения.
select {
case v := <-ch:
    fmt.Println("read from ch:", v)
default: // лучше так не делать без необходимости, иначе цикл будет выполнятся непрерывно и тратить процессорное время
    fmt.Println("no value written to ch")
}

Не используйте каналы и мьютексы в публичном API. Иначе пользователь API будет нести за них ответственность.
У этого правила есть исключения. Каналы могут входить в состав API, если речь идет о библиотеке,
содержащей вспомогательную функцию для работы с конкурентностью.

Лучше всегда явно передавать значения горутине, если ее значение может изменится вне горутины:
a := []int{2, 4, 6, 8, 10}
ch := make(chan int, len(a))
for _, v := range a {
    go func(val int) {
        ch <- val * 2
    }(v)
}

Предусматривая запуск горутин, предусматривайте и их завершение. В отличие от переменных, среда выполнения языка Go не может
проверить, будет ли еще применяться та или иная горутина. Если горутину не закрыть, то планировщик продолжит выделять ей время,
которое она не будет использовать, что негативно скажется на производительности программы. Эта проблема называется утечкой горутин.
Например если горутина заблокировалась на чтение из канала и не была завершена, то планировщик будет тратить на нее время.

func countTo(max int) <-chan int {
    ch := make(chan int)
    go func() {
        for i := 0; i < max; i++ {
            ch <- i
        }
        close(ch)
    }()
    return ch
}

func main() {
    for i := range countTo(10) {
        if i > 5 {
            break // после выполнения этой строчки, горутина заблокируется.
        }
        fmt.Println(i)
    }
}

Использование контекста для завершения горутин
Прием завершения горутин с использованием контекста получил очень широкое распространение.
Он позволяет останавливать горутины на основе любого условия, возникшего в функциях, находящихся выше в стеке вызовов.
func countTo(ctx context.Context, max int) <-chan int {
    ch := make(chan int) 
    go func() { 

        defer close(ch) // При завершении горутины канал будет закрыт.
        for i := 0; i < max; i++ { 
            select { 
            case <-ctx.Done(): 
                // Канал ctx.Done() закрывается, если вызван cancel или истёк дедлайн
                return
            case ch <- i:
            }
        }
    }()
    return ch 
}

func main() { 
    ctx, cancel := context.WithCancel(context.Background()) 
    // Создаём контекст с возможностью ручной отмены.
    // cancel — функция, которая сигнализирует всем,
    // кто слушает ctx.Done(), что пора завершаться.

    defer cancel() // Гарантируем вызов cancel при выходе из main.
    ch := countTo(ctx, 10) 
    for i := range ch {
        if i > 5 { 
            break 
        }
        fmt.Println(i) 
    }
    // После выхода из цикла выполнится defer cancel().
    // Это приведёт к закрытию ctx.Done().
}

Буферизованные каналы отлично работают, когда нужно либо собрать данные из некоторого набора запущенных горутин,
либо ограничить конкурентное использование.
Например, запустили 10 горутин, каждая добавила в буферизованный на 100 значений канал по 10 значений,
далее в цикле мы переносим все значения из канала в срез/массив

Противодавление - это механизм ограничения нагрузки.
Если система перегружена — не принимаем новые задачи.

type PressureGauge struct {
    ch chan struct{} 
    // Буферизированный канал.
    // Его размер = максимальное количество
    // одновременно выполняемых задач.
}

func New(limit int) *PressureGauge {
    return &PressureGauge{
        ch: make(chan struct{}, limit),
        // Создаём канал с буфером limit.
        // Это и есть "ёмкость системы".
    }
}

func (pg *PressureGauge) Process(f func()) error {

    select {
    case pg.ch <- struct{}{}:
        // Пытаемся занять "слот".
        // Если в буфере есть место — запись проходит.
        // Если буфер заполнен — этот case не выбирается.

        f() 
        // Выполняем переданную функцию.

        <-pg.ch 
        // Освобождаем слот.
        // Теперь другая задача может стартовать.

        return nil

    default:
        // Если буфер заполнен —
        // значит уже выполняется limit задач.

        // Мы НЕ ждём освобождения.
        // Вместо этого сразу возвращаем ошибку.
        return errors.New("no more capacity")
    }
}

Ошибка при default - это и есть противодавление. Мы не ждем блокирующий канал, а сразу разворачиваем(мест нет).

Отключение ветвей оператора select
Если какая-то из ветвей оператора select будет читать из закрытого канала, то эта операция всегда будет успешно выполняться,
возвращая нулевое значение. 

// in и in2 — это каналы

for count := 0; count < 2; {
    select {
    case v, ok := <-in: // даже если канал закрыт, будет потрачено процессорное время на проверку закрытости
        if !ok {
            in = nil // Эта ветвь больше не будет успешно выполняться!
            count++
            continue
        }
        // Обработка значения переменной v, прочитанного из канала in
    case v, ok := <-in2:
        if !ok {
            in2 = nil // Эта ветвь больше не будет успешно выполняться!
            count++
            continue
        }
        // Обработка значения переменной v, прочитанного из канала in2
    }
}

Как установить тайм-аут для кода

// timeLimit запускает worker в отдельной горутине
// и либо возвращает его результат,
// либо ошибку, если превышен лимит времени.
func timeLimit[T any](worker func() T, limit time.Duration) (T, error) {

    // Буферизированный канал на 1 элемент.
    // ВАЖНО: буфер = 1 нужен, чтобы если таймаут сработал раньше,
    // горутина смогла всё равно записать результат и НЕ заблокировалась.
    // Если сделать без буфера — возможна утечка горутины.
    out := make(chan T, 1)

    // Создаём контекст с таймаутом.
    // Через limit времени ctx.Done() закроется автоматически.
    ctx, cancel := context.WithTimeout(context.Background(), limit)

    // defer гарантирует освобождение ресурсов таймера.
    // Даже если worker завершился раньше — таймер надо остановить.
    defer cancel()

    // Запускаем worker в отдельной горутине,
    // чтобы основной поток мог ждать либо результат, либо таймаут.
    go func() {
        // Если select уже выбрал ветку таймаута —
        // запись всё равно пройдёт благодаря буферу 1.
        out <- worker()
    }()

    // Ждём одно из двух событий:
    select {

    // Если worker завершился первым —
    // получаем результат и возвращаем его.
    case result := <-out:
        return result, nil

    // Если сработал таймаут —
    // ctx.Done() закроется и эта ветка выполнится.
    case <-ctx.Done():

        // Возвращаем zero-value для T.
        // Так как T — дженерик, мы не знаем его тип,
        // поэтому создаём "пустое" значение.
        var zero T

        return zero, errors.New("work timed out")
    }
}

Использование типа WaitGroup

func main() {
    // WaitGroup — примитив синхронизации.
    // Его задача — подождать, пока завершатся N горутин.
    var wg sync.WaitGroup

    // Сообщаем wg, что будем ждать 3 завершения.
    // ВАЖНО: Add вызывается ДО запуска горутин,
    // иначе возможна гонка.
    wg.Add(3)

    go func() {
        // Done уменьшает внутренний счётчик на 1.
        // defer гарантирует, что даже при panic
        // счётчик уменьшится.
        defer wg.Done()
        doThing1()
    }()

    go func() {
        defer wg.Done()
        doThing2()
    }()

    go func() {
        defer wg.Done()
        doThing3()
    }()

    // Блокируем main-горутины,
    // пока внутренний счётчик не станет 0.
    // Когда все три Done() будут вызваны —
    // Wait() разблокируется.
    wg.Wait()
}

func processAndGather[T, R any](
    in <-chan T,                 // входной канал (только чтение)
    processor func(T) R,         // функция обработки
    num int,                     // количество воркеров
) []R {
    // Канал для результатов.
    // Буфер равен числу воркеров — это уменьшает блокировки.
    out := make(chan R, num)

    var wg sync.WaitGroup
    wg.Add(num) // будем ждать num горутин

    // Запускаем num воркеров
    for i := 0; i < num; i++ {
        go func() {
            defer wg.Done()

            // Каждый воркер читает из одного и того же канала.
            // range завершится, когда канал in будет закрыт.
            for v := range in {
                // Обрабатываем значение
                // и отправляем результат в канал out.
                out <- processor(v)
            }
        }()
    }

    // Следящая горутина закрывает out,
    // когда все воркеры завершатся.
    go func() {
        wg.Wait()
        close(out)
    }()

    var result []R

    // Собираем все результаты.
    // Цикл завершится, когда out будет закрыт.
    for v := range out {
        result = append(result, v)
    }

    return result
}

Однократное выполнение кода

type SlowComplicatedParser interface {
    Parse(string) string
}

func initParser() SlowComplicatedParser {
    // здесь выполняются различные операции настройки и загрузки
}

var parser SlowComplicatedParser // глобальный объект
var once sync.Once               // гарантирует однократное выполнение

func Parse(dataToParse string) string {
    // Выполнится РОВНО ОДИН раз,
    // даже при конкурентных вызовах из разных горутин.
    once.Do(func() {
        parser = initParser() // дорогая инициализация (lazy init)
    })

    // После первого вызова parser уже инициализирован.
    return parser.Parse(dataToParse)
}
Объявление экземпляра типа sync.Once внутри функции обычно является плохой идеей,
поскольку при каждом вызове функции будет создаваться новый экземпляр,
ничего не знающий о предыдущих вызовах.

initOnce := sync.OnceFunc(func() {
    fmt.Println("init")
})
initOnce() // выполнится только один раз

getConfig := sync.OnceValue(func() Config {
    return loadConfig()
})
cfg := getConfig() // вычислится один раз

getDB := sync.OnceValues(func() (*DB, error) {
    return connect()
})
db, err := getDB() // вычислит несколько значений один раз

Когда вместо каналов следует использовать мьютексы.
mutex, от mutual exclusion — «взаимное исключение»

Мьютексы усложняют понимание движения данных: при shared memory нельзя ясно увидеть, кто и когда обращается к значению.
Каналы делают поток данных очевидным — значение передаётся между горутинами и обрабатывается последовательно.
Принцип Go:
«Не делитесь памятью — общайтесь через каналы».

Mutex
Методы: Lock() / Unlock()
Lock() - приостанавливает горутину, если критическая секция занята, иначе берёт блокировку
Unlock() — освобождает блокировку
Использовать defer Unlock() для безопасного освобождения

RWMutex
Методы: Lock()/Unlock() для записи, RLock()/RUnlock() для чтения
Правила блокировок:
Lock() (write lock) → только одна горутина, блокирует всех (чтение и запись)
RLock() (read lock) → несколько горутин читают одновременно, но write lock ждёт

RWMutex полезен, когда часто читают, но редко пишут.

Всегда освобождай блокировку через defer сразу после Lock/RLock:
mu.Lock()
defer mu.Unlock()
или
mu.RLock()
defer mu.RUnlock()

• Если нужно координировать горутины или отслеживать значение по мере его преобразования с помощью нескольких горутин, используйте каналы.
• Если нужно обеспечить совместный доступ к полю структуры, применяйте мьютексы.
• Если вы выявили критическую проблему производительности при использовании каналов и не можете найти других способов ее решения, задействуйте вместо каналов мьютексы.

Если горутина попытается установить одну и ту же блокировку дважды, это приведет к зависанию, потому что она приостановится в ожидании высвобождения ранее установленной ею блокировки.

Мьютексы в Go не являются повторно входимыми.
• Не ставьте Lock() внутри рекурсивных функций.
• Снимайте блокировку перед вызовом рекурсивной функции.
• Вообще старайтесь не вызывать другие функции с установленным Lock — неизвестно, какие блокировки они используют, это может привести к зависанию.

Мьютексы, как sync.WaitGroup и sync.Once, нельзя копировать.
• Передавайте мьютекс в функции или в структуры по указателю, иначе совместное использование блокировки не гарантировано.

Всегда защищайте переменные, к которым обращаются несколько горутин.
• Доступ без Lock может вызвать трудноуловимые ошибки (data race).
• Для выявления проблем используйте detector состояния гонки (-race).

type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}

func countLetters(r io.Reader) (map[string]int, error) {
    // Буфер, в который будем читать данные из Reader
    buf := make([]byte, 2048)

    // Карта для подсчёта букв
    out := map[string]int{}

    for {
        // Read может вернуть:
        // 1) n > 0 и err == nil
        // 2) n > 0 и err == io.EOF
        // 3) n == 0 и err != nil
        n, err := r.Read(buf)

        // СНАЧАЛА обрабатываем прочитанные данные.
        // Даже если err == io.EOF, Reader может вернуть
        // последние байты вместе с этой ошибкой.
        // Поэтому игнорировать buf[:n] нельзя.
        for _, b := range buf[:n] {

            if (b >= 'A' && b <= 'Z') || (b >= 'a' && b <= 'z') {
                out[string(b)]++
            }

        }

        // EOF означает: данных больше не будет.
        // Но последние n байт уже обработаны выше.
        if err == io.EOF {
            return out, nil
        }

        // Любая другая ошибка чтения
        if err != nil {
            return nil, err
        }
    }
}

Read организован так по этим причинам:
1. Мы выделяем буфер единожды и пишем в него, не выделяя память в куче несколько раз.
2. Возвращаемое значение n показывает сколько байтов было прочитано в буфер
3. Сигналом завершения чтения служит возврат оибки io.EOF

s := "The quick brown fox jumped over the lazy dog"
sr := strings.NewReader(s) // sr теперь реализует io.Reader

r, err := os.Open(fileName) // r реализует io.Reader
gr, err := gzip.NewReader(r) // gr реализует io.Reader, используется декоратор

Используйте их, чтобы четче выразить свои намеренья в коде.

Если есть тип, который реализует io.Reader, но не реализует io.Closer (например strings.Reader),
а функция ожидает io.ReadCloser, можно использовать io.NopCloser.
io.NopCloser оборачивает Reader и добавляет пустой метод Close(), который ничего не делает.

Идея реализации:

type nopCloser struct {
    io.Reader
}

func (nopCloser) Close() error { return nil }

func NopCloser(r io.Reader) io.ReadCloser {
    return nopCloser{r}
}

io.NopCloser — адаптер, который превращает io.Reader → io.ReadCloser.

Функция io.NopCloser нарушает общее правило, согласно которому вы не должны возвращать интерфейс из функции,
но это простой адаптер интерфейса, который гарантированно останется неизменным, поскольку является составной
частью стандартной библиотеки.

Функции os.ReadFile и os.WriteFile читают файл в срез байтов и записывают срез байтов в файл соответственно.
Эти функции (и io.ReadAll) хороши только при работе с небольшими объемами данных.
Для работы с объемными источниками данных задействуйте функции Create, NewFile, Open и OpenFile в пакете os.
Они возвращают экземпляр *os.File, реализующий интерфейсы io.Reader и io.Writer. Благодаря этому вы сможете
использовать экземпляр *os.File с типом Scanner из пакета bufio.
bufio.Scanner — инструмент для последовательного чтения io.Reader и разбиения данных на токены (обычно строки).

Промежуточный слой.
Позволяет выполнять общий код для нескольких handlers.
Типичные задачи:
- авторизация
- логирование
- измерение времени запроса
- проверка заголовков
- rate limiting
- работа с контекстом

Основная идея
Middleware — это функция вида:
func(http.Handler) http.Handler
Она:
1) принимает handler
2) возвращает новый handler
3) оборачивает его дополнительной логикой

Пример задач middleware
1) Таймер запроса
   - сохраняем start time
   - вызываем handler
   - считаем duration
   - логируем результат
2) Проверка доступа
   - проверяем заголовок X-Secret-Password
   - если пароль неверный → 401 Unauthorized
   - handler не вызывается

##Контекст

Контекст — это экземпляр, который соответствует интерфейсу Context, определенному в пакете context.
В Go имеется и соглашение о том, что контекст должен передаваться явно в первом параметре.

func logic(ctx context.Context, info string) (string, error) {
    // здесь производятся определенные действия
    return "", nil
}

Когда у вас еще нет контекста, как, например, в точке входа в консольную программу, необходимо создать
пустой исходный контекст с помощью функции context.Background. Она возвращает переменную типа context.Context.

Чтобы привести возвращаемое значение к подходящему типу, используйте идиому «запятая-ok»:
ctx := context.Background()
if myVal, ok := ctx.Value(myKey).(int); !ok {
    fmt.Println("no value")
} else {
    fmt.Println("value:", myVal)
}

Ключи для контекста лучше делать через перечисления
type userKey int
const (
    _ userKey = iota
    key
)

Или через структуры
type userKey struct{}

Запись и чтение из контекста
func ContextWithUser(ctx context.Context, user string) context.Context {
    return context.WithValue(ctx, userKey{}, user)
}

func UserFromContext(ctx context.Context) (string, bool) {
    user, ok := ctx.Value(userKey{}).(string)
    return user, ok
}

| ----------------------------- | ------------------------- |
| `context.Background()`        | корневой context          |
| `context.TODO()`              | placeholder context       |
| `context.WithCancel()`        | ручная отмена             |
| `context.WithCancelCause()`   | отмена с причиной         |
| `context.WithDeadline()`      | отмена в конкретное время |
| `context.WithDeadlineCause()` | deadline + причина        |
| `context.WithTimeout()`       | отмена через duration     |
| `context.WithTimeoutCause()`  | timeout + причина         |
| `context.WithValue()`         | хранение данных           |

Тесты распологаются в той же директории, что и код.
go test - команда запускает выполнение тестов.

func addNumbers(x, y int) int {
    return x + x
}
func Test_addNumbers(t *testing.T) {
    result := addNumbers(2,3)
    if result != 5 {
        t.Error("incorrect result: expected 5, got", result)
    }
}

// Устанавливает начальное состояние для файла с тестами, запускается 1 раз на пакет
// Если файлов в пакете много и на каждый файл есть свой файл с тестами, то функцию
// могут вынести в отдельный файл, например main_test.go или testmain_test.go
func TestMain(m *testing.M) {
    fmt.Println("Set up stuff for tests here")
    testTime = time.Now()
    exitVal := m.Run()
    fmt.Println("Clean up stuff after tests here")
    os.Exit(exitVal)
}

Функция TestMain может быть полезной в следующих двух распространенных случаях.
• Когда требуется настроить данные в некотором внешнем хранилище, например в базе данных.
• Когда тестируемый код зависит от переменных уровня пакета, которые нужно инициализировать.

Для высвобождения временных ресурсов, выделенных для отдельного теста, следует вызвать метод Cleanup экземпляра типа *testing.T.
Этот метод принимает функцию без входных параметров и возвращаемых значений, которая выполняется по завершении теста.
func createFile(t *testing.T) (_ string, err error) {
    // ....
    t.Cleanup(func() {
        os.Remove(f.Name())
    })
}

Фаззинг
Фаззинг (fuzzing) — это метод генерации случайных данных и передачи их в код, чтобы увидеть, правильно ли обрабатываются неожиданные
входные данные. Разработчик может предоставить начальный набор заведомо корректных данных, а фаззер на его основе попытается сгенерировать
некорректные входные данные.

1. Что это:
Fuzz-тест = автоматическая генерация входных данных для поиска багов.

2. Как написать:
func FuzzXxx(f *testing.F) {
    f.Fuzz(func(t *testing.T, input string) {
        YourFunc(input)
    })
}

3. Как запустить:
go test -fuzz=FuzzXxx

4. Что делает Go:
- генерирует случайные данные
- подставляет в функцию
- ищет падения (panic/ошибки)

5. При падении:
Go сохраняет входные данные в:
testdata/fuzz/ИмяТеста/

6. Что сохраняется:
ФАЙЛ с входом (не .go код)

7. Дальше:
go test автоматически:
- читает эти файлы
- запускает их как тесты

8. Зачем:
это регрессионные тесты
(проверяют, что баг не вернулся)

9. Полный цикл:
- написал fuzz
- запустил
- найден баг
- вход сохранён
- исправил код
- go test проверяет фикс

10. Главное:
Fuzz создаёт не тесты в коде,
а входные данные, которые становятся тестами.

Имитации и заглушки
Под словами «имитация» (mock) и «заглушка» (stub) часто понимается одно и то же, но в действительности это разные концепции. Мартин Фаулер (Martin Fowler), авторитетный эксперт во всем, что касается разработки ПО, посвятил имитациям одну из своих статей (https://oreil.ly/nDkF5), где, помимо прочего, коснулся разницы между имитацией и заглушкой. Если в двух словах, то заглушка возвращает готовое значение для определенных входных данных, а имитация позволяет убедиться, что некоторый набор вызовов производится в ожидаемом порядке с ожидаемыми входными данными.
В приведенных ранее примерах использовались заглушки, возвращающие готовые значения для определенных данных. Вы также можете вручную написать собственные имитации или сгенерировать их с помощью одной из сторонних библиотек. Наиболее популярными из них являются библиотека gomock от компании Google (https://oreil.ly/_EjoS) и библиотека testify от компании Stretchr (https://oreil.ly/AfDGD).

Интеграционные тесты и теги сборки
Несмотря на то что пакет httptest позволяет провести тестирование без использования внешних сервисов, все равно старайтесь писать интеграционные тесты — автоматизированные тесты, производящие подключение к другим сервисам. Они позволят убедиться, что вы имеете верное представление об API применяемого сервиса. Здесь важно правильно сгруппировать автоматизированные тесты, поскольку интеграционные тесты должны запускаться только при наличии необходимой вспомогательной среды. Кроме того, интеграционные тесты обычно выполняются реже, поскольку их выполнение, как правило, занимает больше времени, чем выполнение модульных тестов.
В разделе «Использование тегов сборки» главы 11 я рассказывал о тегах сборки, указывающих, когда следует компилировать код. Первоначально теги сборки планировалось задействовать для компилирования разного кода для разных платформ или версий Go, но, как оказалось, пользовательские теги сборки можно применять для управления компиляцией и выполнения интеграционных тестов.

Попробуем использовать эту возможность в нашем проекте по решению математических задач. Задействуйте Docker (https://oreil.ly/5FWcb), чтобы скачать реализацию сервера, выполнив команду docker pull jonbodner/math-server, а затем запустите сервер локально на порте 8080 командой docker run -p 8080:8080 jonbodner/math-server.
Если у вас не установлена платформа Docker или вы хотите скомпилировать этот код самостоятельно, то сможете найти его на сайте GitHub (https://oreil.ly/yjMzc).
Мы должны написать интеграционный тест, чтобы убедиться, что наш метод Resolve должным образом взаимодействует с сервером математических вычислений. Соответствующая функция тестирования TestRemoteSolver_ResolveIntegration определена в файле sample_code/solver/remote_solver_integration_test.go в репозитории (https://oreil.ly/PNRJx). Данный тест выглядит точно так же, как любой из табличных тестов, написанных нами ранее. Интерес представляет лишь первая строка в этом файле, отделенная от объявления пакета пустой строкой:
//go:build integration
Чтобы запустить этот интеграционный тест вместе с остальными тестами, нужно выполнить следующую команду:
$ go test -tags integration -v ./...

Выявление проблем конкурентности с помощью детектора состояний гонки
Даже при использовании встроенной поддержки конкурентности языка Go вы иногда будете допускать ошибки. Так, например, вы можете ненамеренно обратиться к одной и той же переменной в двух разных горутинах без установки блокировки. В терминах компьютерных технологий это называется состоянием гонки. Для облегчения поиска таких ошибок в комплект поставки языка Go включен детектор состояний гонки. Он не гарантирует выявления абсолютно всех имеющихся состояний гонки, но, когда находит такое состояние, вы должны обеспечить установку в этом месте надлежащей блокировки.

Рассмотрим простой пример кода в файле sample_code/race/race.go в репозитории (https://oreil.ly/PNRJx):

func getCounter() int {

    var counter int

    var wg sync.WaitGroup

    wg.Add(5)

    for i := 0; i < 5; i++ {

        go func() {

            for i := 0; i < 1000; i++ {

                counter++

            }

            wg.Done()

        }()

    }

    wg.Wait()
Использование флага -short

Еще один подход — использовать команду go test с флагом -short. Если иногда может понадобиться пропустить долго выполняющиеся тесты, пометьте их, поместив в начало функции тестирования следующий код:

if testing.Short() {

    t.Skip("skipping test in short mode.")

}

Когда понадобится запустить только короткие тесты, используйте команду go test с флагом -short.

У данного подхода есть несколько недостатков. При использовании флага -short вы имеете только два уровня тестирования: выполнение коротких тестов и выполнение всех тестов. Теги сборки, напротив, позволяют сгруппировать интеграционные тесты, указав, какой сервис требуется для их выполнения. Второй аргумент против применения флага -short для выделения интеграционных тестов носит философский характер. Если теги сборки определяют зависимость, то флаг -short лишь указывает, что не должны запускаться долго выполняющиеся тесты. Первое и второе — совершенно разные концепции. Нако­нец, на мой взгляд, в использовании флага -short нет логики. Короткие тесты нужно выполнять всегда, и было бы логичнее задействовать флаг, позволяющий не исключить, а включить долго выполняющиеся тесты в число выполняемых.

Выявление проблем конкурентности с помощью детектора состояний гонки
Даже при использовании встроенной поддержки конкурентности языка Go вы иногда будете допускать ошибки. Так, например, вы можете ненамеренно обратиться к одной и той же переменной в двух разных горутинах без установки блокировки. В терминах компьютерных технологий это называется состоянием гонки. Для облегчения поиска таких ошибок в комплект поставки языка Go включен детектор состояний гонки. Он не гарантирует выявления абсолютно всех имеющихся состояний гонки, но, когда находит такое состояние, вы должны обеспечить установку в этом месте надлежащей блокировки.

Рассмотрим простой пример кода в файле sample_code/race/race.go в репозитории (https://oreil.ly/PNRJx):

func getCounter() int {

    var counter int

    var wg sync.WaitGroup

    wg.Add(5)

    for i := 0; i < 5; i++ {

        go func() {

            for i := 0; i < 1000; i++ {

                counter++

            }

            wg.Done()

        }()

    }

    wg.Wait()

    return counter

}

Этот код запускает пять горутин и ждет, пока каждая из них 1000 раз обновит общую переменную counter, а затем возвращает результат. По завершении эта переменная должна содержать значение 5000. Давайте проверим это, использовав модульный тест в файле sample_code/race/race_test.go:

func TestGetCounter(t *testing.T) {

    counter := getCounter()

    if counter != 5000 {

        t.Error("unexpected counter:", counter)

    }

}

Выполнив команду go test несколько раз, вы увидите, что иногда тест выполняется успешно, но чаще выдает отрицательный результат с сообщением об ошибке следующего вида:

unexpected counter: 3673

Причина этой проблемы в состоянии гонки. В столь простой программе легко понять, чем это вызвано: несколько горутин пытаются обновлять переменную counter одновременно, и часть этих обновлений теряется. В более сложных программах выявление состояний гонки дается труднее. Посмотрим, что в данном случае сделает детектор состояний гонки. Его можно активировать, используя команду go test с флагом -race:

$ go test -race

Рефлексия позволяет работать с типами на этапе выполнения
Одной из наиболее привлекательных особенностей языка Go является статическая типизация. В большинстве случаев объявление переменных, типов и функций в нем не представляет никаких проблем. Когда вам требуется тип, переменная или функция, вы просто определяете их следующим образом:

type Foo struct {
  A int
  B string
}

var x Foo

func DoSomething(f Foo) {
  fmt.Println(f.A, f.B)
}

Типы используются для представления структур данных, о необходимости которых известно на этапе написания программы. Поскольку типы являются неотъемлемой составляющей языка Go, компилятор с их помощью проверяет корректность создаваемого нами кода. Однако порой на этапе компиляции известна не вся информация. Иногда на этапе выполнения может понадобиться работать с переменными, используя информацию, которой не было на момент написания программы. Например, сохранить в переменную данные из файла или сетевого запроса или создать функцию, способную работать с разными типами. 
нам на выручку приходит рефлексия. Она позволяет исследовать типы на этапе выполнения, а также изучать, модифицировать и создавать переменные, функции и структуры на этапе выполнения.

Это подводит нас к вопросу о том, в каких случаях нужна эта функциональность. Общее представление об этом можно получить, заглянув в стандартную библиотеку Go. Области применения рефлексии можно разделить на следующие основные категории.

• Чтение из базы данных и запись в нее. Пакет database/sql использует ре­флексию для того, чтобы отправлять записи в базы данных и, наоборот, читать записи из баз данных.

• Встроенные библиотеки шаблонизации языка Go text/template и html/template используют рефлексию для обработки значений, передаваемых шаблонам.

• Пакет fmt активно задействует рефлексию для определения типа предоставляемых параметров при вызове функции fmt.Println и других подобных функций.

• Пакет errors использует рефлексию для реализации функций errors.Is и errors.As.

• Пакет sort применяет рефлексию для реализации функций сортировки и проверки содержимого срезов любого типа: sort.Slice, sort.SliceStable и sort.SliceIsSorted.

• Последняя основная область применения рефлексии в стандартной библиотеке — преобразование данных в форматы JSON, XML и другие, поддерживаемые различными пакетами encoding, и обратно. Рефлексия используется для доступа к тегам структур (о них мы поговорим чуть позже), а также для чтения и записи соответствующих полей структур.

Типы, разновидности и значения
Теперь, зная, что такое рефлексия и когда она может понадобиться, разберемся с тем, как все это работает. Типы и функции, реализующие рефлексию в Go, определены в пакете reflect стандартной библиотеки. Механизм действия рефлексии опирается на следующие три концепции: типы, разновидности типов и значения.
----

Типы и разновидности

В контексте рефлексии тип является именно тем, что означает это слово. То есть он определяет, какими свойствами обладает переменная, какие значения она может содержать и как с ней можно взаимодействовать. При использовании рефлексии вы можете запросить у типа информацию об этих свойствах с помощью кода.

Получить рефлексивное представление типа переменной можно с помощью функции TypeOf из пакета reflect:

vType := reflect.TypeOf(v)

Функция reflect.TypeOf возвращает значение типа reflect.Type, представляющее тип переданной в эту функцию переменной. Тип reflect.Type обладает рядом методов, возвращающих информацию о типе переменной. Мы не можем рассмотреть здесь все эти методы, поговорим лишь о наиболее важных.

Для вас не должно быть сюрпризом, что метод Name возвращает имя типа. Рассмотрим небольшой пример:

var x int

xt := reflect.TypeOf(x)

fmt.Println(xt.Name())     // возвращает int

f := Foo{}

ft := reflect.TypeOf(f)

fmt.Println(ft.Name())     // возвращает Foo

xpt := reflect.TypeOf(&x)

fmt.Println(xpt.Name())    // возвращает пустую строку

Здесь мы объявляем переменную x типа int. Передаем ее в функцию reflect.TypeOf и получаем обратно экземпляр типа reflect.Type. Для простых типов, таких как int, метод Name() возвращает имя типа — в данном случае строку int для типа int. Для структур этот метод возвращает имя структуры. Некоторые типы, например срезы и указатели, не имеют имени типа, в таком случае метод Name возвращает пустую строку.

Метод Kind типа reflect.Type возвращает значение типа reflect.Kind — константу, которая указывает, на основе чего создан тип: среза, отображения, указателя, структуры, интерфейса, строки, массива, функции, типа int или какого-то другого простого типа. При этом иногда сложно понять, в чем разница между типом и разновидностью типа. Запомните следующее правило: если вы определяете структуру с именем Foo, то она обладает разновидностью reflect.Struct и типом Foo.

Разновидности типов играют очень важную роль. При использовании рефлексии следует помнить о том, что любой код из пакета reflect исходит из предположения, что вы знаете, что делаете. Некоторые из методов типа reflect.Type и других типов пакета reflect имеют смысл только для определенных разновидностей типов. Так, например, у типа reflect.Type есть метод NumIn. Если экземпляр типа reflect.Type представляет функцию, то NumIn вернет количество ее входных параметров. Если экземпляр типа reflect.Type представляет что-то другое, то вызов метода NumIn сгенерирует панику.


Обычно при вызове метода, не имеющего смысла для данной разновидности типа, этот метод генерирует панику. Поэтому не забывайте выяснять, какие методы будут работать, а какие — нет, используя разновидность исследуемого типа.

Еще одним важным методом типа reflect.Type является метод Elem. Некоторые типы в Go содержат ссылки на другие типы, и метод Elem позволяет выяснить, что представляют собой эти вложенные типы. Например, вызовем функцию reflect.TypeOf, передав ей указатель на тип int:
ar x int

xpt := reflect.TypeOf(&x)

fmt.Println(xpt.Name())        // возвращает пустую строку

fmt.Println(xpt.Kind())        // возвращает reflect.Ptr

fmt.Println(xpt.Elem().Name()) // возвращает int
fmt.Println(xpt.Elem().Kind()) // возвращает reflect.Int

В результате мы получим экземпляр типа reflect.Type с пустой строкой вместо имени и разновидностью reflect.Ptr, что подразумевает указатель. Когда экземпляр типа reflect.Type представляет указатель, метод Elem возвращает экземпляр типа reflect.Type, представляющий тот тип, на который указывает этот указатель. В данном случае метод Name возвращает строку int, а метод Kind — разновидность reflect.Int. Метод Elem можно использовать также для срезов, отображений, каналов и массивов.

У типа reflect.Type тоже есть методы для анализа структур. Метод NumField позволяет узнать, сколько полей содержит структура, а метод Field — извлечь поле структуры по индексу. Второй метод возвращает структуру каждого поля, как ее определяет тип reflect.StructField, что включает в себя имя, порядок, тип и имеющиеся в поле теги структур. Рассмотрим небольшой пример, который вы можете запустить в онлайн-песочнице (https://oreil.ly/Ynv_4) или опробовать локально, взяв исходный код из каталога sample_code/struct_tag в папке ch16 репозитория (https://oreil.ly/jAIdQ):

type Foo struct {

    A int    `myTag:"value"`

    B string `myTag:"value2"`

}

 

var f Foo

ft := reflect.TypeOf(f)

for i := 0; i < ft.NumField(); i++ {

    curField := ft.Field(i)

    fmt.Println(curField.Name, curField.Type.Name(),

        curField.Tag.Get("myTag"))

}

Мы создаем экземпляр типа Foo и с помощью функции reflect.TypeOf получаем экземпляр типа reflect.Type, представляющий переменную f. Затем с помощью метода NumField настраиваем цикл for так, чтобы он обошел индексы всех полей в переменной f. Далее с помощью метода Field получаем структуру reflect.StructField, представляющую отдельное поле. После этого мы можем использовать поля структуры reflect.StructField для получения дополнительной информации о поле. Этот код выводит следующий результат:

A int value

B string value2

У типа reflect.Type есть и много других методов, но все они используют тот же паттерн, позволяя получать определенную информацию о типе переменной. Более подробную информацию о типе reflect.Type можно найти в документации к стандартной библиотеке (https://oreil.ly/p4AZ6).

Значения
Рефлексию можно использовать не только для выяснения типов, но и для чтения значений переменных, присваивания им значений и создания с нуля новых значений.

С помощью функции reflect.ValueOf можно создать экземпляр типа reflect.Value, представляющий значение переменной:

vValue := reflect.ValueOf(v)

Поскольку каждая переменная в Go обладает типом, reflect.Value имеет метод Type, который возвращает экземпляр типа reflect.Type для экземпляра типа reflect.Value. Как и у типа reflect.Type, у типа reflect.Value есть метод Kind.
Подобно тому как у типа reflect.Type есть методы для получения информации о типе переменной, у типа reflect.Value есть методы для получения информации о значении переменной. Мы не будем рассматривать здесь их все, но изучим, как можно использовать тип reflect.Value для работы со значениями переменных.

Для начала посмотрим, как читать значения из экземпляров типа reflect.Value. Метод Interface возвращает значение переменной как интерфейс any. При этом теряется информация о типе, поэтому при записи возвращаемого значения в переменную его нужно снова привести к правильному типу с помощью операции утверждения типа:

s := []string{"a", "b", "c"}

sv := reflect.ValueOf(s)        // переменная sv имеет тип reflect.Value

s2 := sv.Interface().([]string) // переменная s2 имеет тип []string

Метод Interface можно вызывать для экземпляров типа reflect.Value, содержащих значения любого типа, однако имеются и специализированные методы для случаев, когда переменная относится к одному из встроенных простых типов: Bool, Complex, Int, Uint, Float и String. Есть также метод Bytes для случая, когда переменная представляет собой байтовый срез. Вызов метода, который не соответствует типу значения, содержащегося в экземпляре типа reflect.Value, сгенерирует панику.

Рефлексию можно использовать также для присвоения значения переменной, однако эта операция выполняется в три этапа. Сначала нужно передать указатель на переменную в функцию reflect.ValueOf, которая вернет экземпляр типа reflect.Value, представляющий этот указатель:

i := 10

iv := reflect.ValueOf(&i)

Затем необходимо добраться непосредственно до значения, которое нужно поменять. Вызвав метод Elem в экземпляре типа reflect.Value, мы можем получить то значение, на которое указывает указатель, переданный в функцию reflect.ValueOf. Подобно тому как метод Elem типа reflect.Type возвращает тип, на который указывает вмещающий тип, метод Elem типа reflect.Value возвращает значение, на которое указывает указатель, или значение, содержащееся в экземпляре интерфейса:

ivv := iv.Elem()

Теперь осталось непосредственно применить метод, используемый для установки значения. Наряду со специализированными методами для чтения простых типов в пакете reflect имеются и специализированные методы для установки значений простых типов: SetBool, SetInt, SetFloat, SetString и SetUint. В своем примере мы можем изменить значение переменной i, выполнив вызов ivv.SetInt(20). Если выведем значение переменной i, то увидим, что теперь оно равно 20:

ivv.SetInt(20)

fmt.Println(i) // выводит 20

В случае всех остальных типов следует использовать метод Set, который принимает переменную типа reflect.Value. При этом присваиваемое значение может не быть указателем, потому что мы просто читаем это значение, не изменяя его. И подобно тому, как метод Interface(), помимо прочего, может применяться для чтения простых типов, метод Set может использоваться для записи простых типов.

Необходимость передачи указателя в функцию reflect.ValueOf для изменения значения входного параметра объясняется тем, что эта функция ведет себя так же, как любая другая функция в языке Go. Как упоминалось в разделе «Указатели служат признаком изменяемых параметров» главы 6, использование параметров указательного типа означает, что функция должна модифицировать значение параметра. Модификация производится путем разыменования указателя и присваивания значения. Например, следующие две функции производят одно и то же действие:

func changeInt(i *int) {

    *i = 20
}

func changeIntReflect(i *int) {
    iv := reflect.ValueOf(i)

    iv.Elem().SetInt(20)
}

Попытка присвоить экземпляру reflect.Value значение неправильного типа приведет к панике.

Если в вызов reflect.ValueOf передать параметр, не являющийся указателем, вы сможете прочитать значение переменной с помощью рефлексии, но любая попытка использовать один из методов, изменяющих значение переменной (что неудивительно), приведет к панике.

Используйте рефлексию для проверки значения интерфейса на равенство nil
Как упоминалось в разделе «Интерфейсы и значение nil» главы 7, если переменную конкретного типа со значением nil присвоить переменной интерфейсного типа, то переменная интерфейсного типа не будет равна nil. Это объясняется тем, что с интерфейсной переменной ассоциируется некоторый тип. Если вам нужно проверить, равно ли значению nil ассоциированное с интерфейсом значение, то это можно сделать с помощью рефлексии и методов IsValid и IsNil:

func hasNoValue(i interface{}) bool {

    iv := reflect.ValueOf(i)

    if !iv.IsValid() {

        return true

    }

    switch iv.Kind() {

    case reflect.Pointer, reflect.Slice, reflect.Map, reflect.Func,

         reflect.Interface:

        return iv.IsNil()

    default:

        return false

    }

}

Создавайте с помощью рефлексии функции для автоматизации повторяющихся задач
Еще одной областью применения рефлексии в Go является создание функций. Мы можем применить рефлексию для обертывания существующих функций с некоторой часто используемой функциональностью без написания повторяющегося кода. Например, вот как может выглядеть фабричная функция, снабжающая любую переданную ей функцию информацией о времени выполнения:

func MakeTimedFunction(f any) any {

    ft := reflect.TypeOf(f)

    fv := reflect.ValueOf(f)

    wrapperF := reflect.MakeFunc(ft, func(in []reflect.Value) []reflect.Value {

        start := time.Now()

        out := fv.Call(in)

        end := time.Now()

        fmt.Println(end.Sub(start))

        return out

    })

    return wrapperF.Interface()

}

Поскольку эта функция должна принимать на входе любую функцию, ее параметр объявлен с типом any. Она передает экземпляр типа reflect.Type, представляющий полученную функцию, в вызов reflect.MakeFunc вместе с замыканием, которое фиксирует начальный момент времени, вызывает исходную функцию с помощью рефлексии, фиксирует конечный момент времени, выводит разницу между началом и концом и возвращает значение, вычисленное исходной функцией. Поскольку reflect.MakeFunc возвращает экземпляр типа reflect.Value, мы вызываем метод Interface этого типа, чтобы получить возвращаемое значение. Использовать эту функцию можно следующим образом:

func timeMe(a int) int {

    time.Sleep(time.Duration(a) * time.Second)

    result := a * 2

    return result
    }

 

func main() {

    timed:= MakeTimedFunction(timeMe).(func(int) int)

    fmt.Println(timed(2))

}

Использовать пакет unsafe небезопасно
Подобно тому как пакет reflect позволяет манипулировать типами и значениями, пакет unsafe позволяет манипулировать памятью. Это очень небольшой и очень странный пакет. Он определяет только три функции и один тип, которые ведут себя совершенно не так, как типы и функции, определенные в других пакетах.

Учитывая, что безопасность управления памятью находится в центре внимания Go, вы можете спросить: зачем вообще был создан пакет unsafe? Подобно пакету reflect, который часто используется для преобразования текстовых данных на границе программы Go и внешнего мира, пакет unsafe применяется для преобразования двоичных данных. Основных причин применения unsafe две. В статье Breaking Type Safety in Go: An Empirical Study on the Usage of the unsafe Package (https://oreil.ly/N_6JX), написанной Диего Элиасом Костой (Diego Elias Costa) с коллегами, представлены результаты исследования 2438 популярных проектов с открытым исходным кодом на Go. Обнаружено следующее:

• в коде 24 % проектов на Go unsafe применяется минимум один раз;

• большинство случаев использования unsafe обусловлено необходимостью интеграции с операционными системами и кодом на C;

• разработчики часто задействуют unsafe, чтобы повысить эффективность кода на Go.

Главное предназначение unsafe — организация взаимодействий между системами. Стандартная библиотека Go использует unsafe для обмена данными с операционной системой. Примеры можно увидеть в пакете syscall в стандартной библиотеке или в пакете sys более высокого уровня (https://oreil.ly/ueHY3). Дополнительную информацию о применении unsafe для взаимодействия с операционной системой вы найдете в замечательной статье (https://oreil.ly/VtE1t), написанной Мэттом Лейхером (Matt Layher).

Тип unsafe.Pointer является особенным в том плане, что он существует лишь для того, чтобы преобразовывать указатели любых типов в тип unsafe.Pointer и обратно. Помимо указателей, в тип unsafe.Pointer или из него можно преобразовывать также значения специального целочисленного типа uintptr. Над значениями этого типа можно производить математические действия, как в случае любого другого целочисленного типа. Это позволяет заходить в экземпляр определенного типа и извлекать отдельные байты. Можно также использовать адресную арифметику, подобную той, что поддерживается в C и C++. Эти байтовые манипуляции ведут к изменению значения переменной.

Существует два основных паттерна применения unsafe. Первый паттерн — преобразование друг в друга значений двух разных типов, которые не поддерживают такое преобразование. Это обеспечивается путем использования цепочки преобразований типа с unsafe.Pointer посередине. Второй паттерн — чтение или запись байтов переменной путем ее преобразования в unsafe.Pointer, затем преобразования unsafe.Pointer в указатель и копирования или модификации байтов содержимого переменной.

Использование Sizeof и Offsetof
Некоторые функции в unsafe помогают узнать, как байты, составляющие значения разных типов, располагаются в памяти. Первая такая функция — Sizeof. Как следует из названия, она возвращает размер в байтах всего, что ей передается.

В то время как размеры для числовых типов довольно очевидны (int16 — это 16 бит, или 2 байта, byte — это 1 байт и т.д.), ситуация с другими типами немного сложнее. Для указателя вы получите объем памяти, необходимый для хранения указателя (обычно 8 байт в 64-битной системе), а не размер данных, на которые он указывает. Вот почему Sizeof считает, что любой срез имеет длину 24 байта в 64-битной системе: он реализован как два поля int, хранящие длину и емкость, и указатель на содержимое среза. Любая строка имеет длину 16 байт в 64-битной системе (поле int для хранения длины и указатель на содержимое строки). Любое отображение в 64-битной системе имеет длину 8 байт, потому что в Go любое отображение — это указатель на довольно сложную структуру данных.

Массивы являются типами значений, поэтому их размер вычисляется умножением длины массива на размер одного элемента.

Размер структуры — это сумма размеров полей плюс некоторые корректировки для учета выравнивания. Процессоры быстрее обрабатывают данные, которые занимают в памяти целое число машинных слов и начинаются и заканчиваются на границах этих слов, и медленнее, когда обрабатываемое значение начинается в середине одного машинного слова и заканчивается в середине другого. Поэтому для достижения наибольшей эффективности компилятор добавляет отступы между полями, чтобы они выстраивались по границам машинных слов. Компилятор также стремится правильно выровнять всю структуру. В 64-битной системе он добавит отступы в конец структуры, чтобы довести ее размер до кратного 8 байтам.

Другая функция, Offsetof, сообщает позицию поля в структуре. Давайте применим Sizeof и Offsetof и посмотрим, как порядок расположения полей влияет на размер структуры. Допустим, у нас есть две структуры:

Доступ к неэкспортируемым полям
Вот еще немного волшебства, которое можно творить с помощью unsafe, но этот прием следует использовать только в самом крайнем случае: вы можете объединить рефлексию и unsafe для чтения и изменения неэкспортируемых полей в структурах. Давайте посмотрим, как это сделать.

Сначала определим структуру в одном пакете:

type HasUnexportedField struct {

    A int

    b bool

    C string

}

Обычный код за пределами пакета не сможет получить доступ к полю b. Но давайте посмотрим, возможно ли это сделать, используя unsafe:

func SetBUnsafe(huf *one_package.HasUnexportedField) {

    sf, _ := reflect.TypeOf(huf).Elem().FieldByName("b")

    offset := sf.Offset

    start := unsafe.Pointer(huf)

    pos := unsafe.Add(start, offset)

    b := (*bool)(pos)

    fmt.Println(*b) // читает значение

    *b = true       // записывает значение

}

Здесь с помощью механизма рефлексии извлекается информация о типе поля b. Метод FieldByName возвращает экземпляр reflect.StructField для любого поля в структуре, даже неэкспортированного. Этот экземпляр содержит также смещение связанного с ним поля. Далее huf преобразуется в unsafe.Pointer и используется метод unsafe.Add для добавления смещения к указателю, чтобы перейти к местоположению b в структуре. После этого остается только привести указатель unsafe.Pointer, полученный вызовом Add, к типу *bool. Теперь можно прочитать или изменить значение b. Исходный код этого примера вы найдете в каталоге sample_code/unexported_field_access в репозитории (https://oreil.ly/jAIdQ).

Вспомогательные инструменты для пакета unsafe
Будучи языком, поощряющим использование вспомогательных инструментов, Go предоставляет флаг компилятора, позволяющий выявлять случаи неправильного применения типов Pointer и unsafe.Pointer. Запустив свой код с флагом -gcflags=-d=checkptr, вы обеспечите проведение такой дополнительной проверки на этапе выполнения. Как и детектор состояний гонки, эта проверка не гарантирует выявление абсолютно всех проблем с небезопасным кодом и замедляет работу программы. В то же время использование этого флага вполне уместно на этапе тестирования кода.

Дополнительную информацию о пакете unsafe можно найти в документации (https://oreil.ly/xmihF).


Пакет unsafe — мощное и низкоуровневое средство! Используйте его, только когда точно знаете, что делаете, и вам действительно нужен обеспечиваемый им прирост производительности.

Пакет cgo обеспечивает интеграцию, а не повышает производительность

Как и пакеты reflect и unsafe, пакет cgo чаще всего используется на внешней границе Go-программы. Если пакет reflect обеспечивает интеграцию с внешними текстовыми данными, а пакет unsafe — интеграцию с операционной системой и сетевыми данными, то пакет cgo предназначен главным образом для интеграции с C-библиотеками.

Несмотря на то что язык C существует уже почти 50 лет, он по-прежнему лингва франка в мире языков программирования. Поскольку все основные операционные системы написаны главным образом на C или C++, в их комплект поставки входят библиотеки, написанные на C. Это также означает, что практически все современные языки программирования предоставляют определенный способ интеграции с C-библиотеками. В Go роль интерфейса внешней функции (Foreign Function Interface, FFI) для сопряжения с C-кодом выполняет пакет cgo.

Как мы уже не раз видели, Go поощряет более явное определение тех или иных вещей. Go-разработчики иногда иронично называют магией существующее в других языках автоматическое поведение, однако использование пакета cgo вызывает во многом сходные ощущения. Посмотрим, как выглядит этот магический связующий код.

Начнем с очень простой программы, которая вызывает C-код для выполнения некоторых математических вычислений. Ее исходный код вы найдете на GitHub в каталоге sample_code/call_c_from_go в репозитории (https://oreil.ly/jAIdQ). Сначала рассмотрим код в main.go:

package main

 

import "fmt"

 

/*

    #cgo LDFLAGS: -lm    

    #include <stdio.h>

    #include <math.h>

    #include "mylib.h"

 

    int add(int a, int b) {

        int sum = a + b;

        printf("a: %d, b: %d, sum %d\n", a, b, sum);

        return sum;

    }

*/

import "C"

 

func main() {

    sum := C.add(3, 2)

    fmt.Println(sum)

    fmt.Println(C.sqrt(100))

    fmt.Println(C.multiply(10, 20))

}

Заголовочный файл mylib.h находится в одном каталоге с файлом main.go:

int multiply(int a, int b);

А вот содержимое mylib.c:

#include "mylib.h"

int multiply(int a, int b) {

    return a * b;

}

Если на вашей машине уже установлен компилятор языка C, то вам останется лишь скомпилировать свою программу, используя стандартные инструменты языка Go:

$ go build

$ ./call_c_from_go

##Go Lang идиомы
1) Go присваивает нулевое значение для переменной, для которой не задано значение.
У разных типов разные нулевые значения
2) Go позволяет разделять числовые литералы при помощи "_" - 1_2_3_4 или 1_234
3) Иногда в Go не делается явного указания типа, в таких случаях для литерала 
используется тип по умолчанию.
4) Каждая объявленная переменная должна быть прочитана.
Надо использовать сканеры качества кода.
5) Неиспользуемые константы не включаются в бинарник после компиляции.
6) Имена идентификаторов должны начинаться с буквы, символов или _, также могут содержать цифры.
Буквой или цифрой может быть любой символ Unicode.
7) В идиоматическом Go принято использовать camelCase
8) В Go регистр первой буквы в имени элемента, объявляемого на уровне пакета,
определяет его доступность за пределами пакета.
9) Чем меньше область видимости переменной, тем более коротким должно быть ее имя.
10) reflect.DeepEqual может сравнить почти все что угодно. Но ее использование оправдано только для тестирования.
11) В языке Go передача параметров производится по значению.
12) Среда выполнения языка Go берет на себя такие функции как выделение памяти,
сборка мусора, поддержка конкурентности, работа с сетью и реализация встроенных типов и функций.
13) Среда выполнения Go включается в состав каждого скомпилированного бинарника.
14) Недостаток включения среды - даже самая маленькая программа будет весить 2 Мбайт
15) Согласно спецификации Go исходный код программ на этом язке всегда должен записываться в кодировке UTF-8.
За исключением литералов шестнадцатеричных экранирующих последовательностей.
16) Начиная с версии Go 1.15 команда go vet блокирует преобразование в строку любого другого целочисленного типа,
помимо rune и byte.
17) При объявлении переменных, констант, типов и функций вне какой-либо функции они размещаются в блоке пакета.
18) Операторы import определяют, имена каких других пакетов допускается применять внутри содержащего их файла.
Эти имена находятся в блоке файлов.
19) Функция высшего порядка - это более замысловатый способ казать о том,
что функция задействует другую функцию в качестве входного параметра.
20) В статье, опубликованной в 2017 году в журнале Empirical Software Engineering, Вард Антинян
и другие описали результат исследования, согласно которому "из одинадцати предложенных характеристик кода
только две заметно повышают степень его сложности: глубина вложенности и недостаточная структуризация"
