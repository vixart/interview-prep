# Финтех: типовые вопросы про деньги и платежи

Вопросы, которые почти гарантированно звучат на собеседовании в финтех.

## 1. Деньги и float

`float` даёт ошибки округления из-за двоичного представления
(0.1 + 0.2 ≠ 0.3). В финтехе деньги хранят и считают:

- **int в минимальных единицах** (minor units: копейки, центы) — основной способ;
- **decimal-типы** (`NUMERIC` в БД, decimal-библиотеки в коде);
- **Money value object** — сумма + валюта одним неизменяемым типом.

Все расчёты — детерминированные и без плавающей точки. Правила округления
(банковское, вверх/вниз) фиксируются явно на уровне домена.

## 2. Уровни изоляции транзакций

- **READ COMMITTED** — минимум для платежей;
- **REPEATABLE READ** — для консистентных расчётов балансов;
- **SERIALIZABLE** — безопасен, но часто слишком дорог по производительности
  (ретраи по serialization failure).

Подробный разбор уровней и аномалий — [`sql/locks.md`](../sql/locks.md);
хорошая статья по изоляции в PostgreSQL:
<https://datafinder.ru/products/postgresql-16-izolyaciya-tranzakciy-chast-2>

## 3. Идемпотентность платежей

Используется **idempotency key**, который сохраняется вместе с результатом
операции. Повторный запрос с тем же ключом возвращает сохранённый результат
без повторного списания. Ключ генерирует клиент; хранение ключа и
выполнение операции — в одной транзакции (уникальный индекс по ключу).

## 4. Optimistic vs pessimistic locking

- **Optimistic** — через поле версии (`version`, сравнение при UPDATE):
  подходит при **редких** конфликтах, при конфликте — ретрай.
- **Pessimistic** — `SELECT ... FOR UPDATE`: нужен при **высокой конкуренции**
  за одну строку (баланс счёта), конфликтующие транзакции ждут.

Детали и виды блокировок — [`sql/locks.md`](../sql/locks.md).

## 5. Race conditions в платежах

Решаются транзакциями, блокировками строк и **атомарными SQL-операциями**
(`UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1`).
Правило: **никогда не рассчитывать баланс в памяти** без гарантий БД —
«прочитал → посчитал → записал» без блокировки это lost update.

## 6. Финансовые агрегаты: ledger

Баланс не хранится как число, а **считается из ledger-записей**: каждая
операция — неизменяемая проводка (append-only) с чётким бизнес-смыслом.

- Ничего не редактируется и не удаляется: корректировка — новая проводка
  (сторно).
- Баланс = сумма проводок; для скорости — кешируемый снапшот, который
  всегда можно пересчитать и сверить.
- Двойная запись (double-entry): каждая операция — дебет одного счёта и
  кредит другого, сумма проводок всегда сходится в ноль.

## 7. Exactly-once / at-least-once

Exactly-once на практике почти недостижим (сеть, ретраи, сбои после
выполнения, но до подтверждения). Рабочая схема:
**at-least-once доставка + идемпотентная обработка** (дедупликация по
event_id / idempotency key). Разбор гарантий доставки на примере Kafka —
[`messaging/kafka.md`](../messaging/kafka.md).

## 8. Работа с платёжными провайдерами

- Всегда **таймауты** на исходящие вызовы;
- **ретраи с backoff** (и только для идемпотентных операций);
- **подпись запросов** (HMAC) — и проверка подписи входящих;
- **webhooks** обрабатываются **идемпотентно и асинхронно**: быстро
  ответить 200, положить в очередь, обработать с дедупликацией — провайдер
  будет слать повторы;
- статус «неизвестно» (таймаут на charge) — это не ошибка и не успех:
  нужна выверка (reconciliation) по API провайдера.

## Для собеседования

Сквозная идея всех пунктов: деньги требуют **детерминизма и гарантий БД** —
целочисленная арифметика, транзакции с правильной изоляцией, идемпотентность
на каждом стыке систем и append-only история как источник истины.
