# CQRS

**Command Query Responsibility Segregation** — разделение операций
изменения состояния (команды) и чтения состояния (запросы).

## Принцип

| | Command → write | Query → read |
|---|---|---|
| Делает | Изменяет состояние | Читает состояние |
| Возвращает | Ничего, кроме статуса/ID | Данные |
| Инвариант | Одна команда ничего не читает наружу | Один запрос **никогда** не меняет данные |

Команда — это намерение с именем из предметной области
(`ChangeUserEmail`, `CancelOrder`), а не «UPDATE поля». Команды идут через
обработчики (command bus → handler), запросы — отдельным путём, часто мимо
доменной модели сразу в оптимизированную читающую модель.

## Зачем разделять

- Читающая и пишущая нагрузка масштабируются независимо (чтений обычно
  на порядки больше).
- Read-модель можно денормализовать под конкретные экраны (проекции,
  материализованные представления) — без JOIN'ов на лету.
- Запись остаётся строгой: валидация, инварианты, транзакции — в одном месте.
- Хорошо сочетается с event-driven подходом: команда → событие → обновление
  проекций (см. [Transactional Outbox](outbox.md)).

## Уровни применения

1. **Разделение на уровне кода** — отдельные типы/обработчики для команд
   и запросов, база одна. Дёшево, стоит почти всегда.
2. **Разные модели** — write-модель нормализована, read-модель — проекции.
3. **Разные хранилища** — запись в PostgreSQL, чтение из Elasticsearch/Redis;
   синхронизация событиями. Здесь появляется eventual consistency — read-модель
   отстаёт, и это надо явно проговаривать.

## Для собеседования

- CQRS ≠ Event Sourcing: их часто применяют вместе, но это независимые вещи.
- Главная цена — консистентность: после команды запрос может вернуть
  старые данные (лечится read-your-writes, версиями, UI-оптимизмом).
- Не стоит тащить полный CQRS (уровень 3) в CRUD-приложение — достаточно
  уровня 1: разделения командных и читающих путей в коде.
