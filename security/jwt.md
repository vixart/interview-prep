# JWT

[TLS](tls.md) · **JWT** · [OAuth 2.0](oauth.md)

**JWT** (RFC 7519) — формат самодостаточного токена: получатель проверяет его **по подписи**,
не ходя в базу и не спрашивая эмитента. В 99% случаев под JWT имеют в виду **JWS** —
подписанный, но **не зашифрованный** токен. Есть еще JWE (зашифрованный), встречается редко.

Как такой токен выдается — в [OAuth 2.0](oauth.md), чем защищен канал, по которому он
летит, — в [TLS](tls.md).

---

## Структура

```
  eyJhbGciOiJSUzI1NiIsImtpZCI6IjIwMjQtMDEifQ . eyJzdWIiOiIxMjMiLCJleHAiOjE3...  . MEUCIQD...
  └──────────── header ────────────────────┘   └────────── payload ────────┘    └ signature ┘
        base64url(JSON)                            base64url(JSON)              подпись первых
                                                                                двух частей
  header  : {"alg":"RS256","typ":"JWT","kid":"2024-01"}
  payload : {"iss":"https://auth.example.com","sub":"user-123","aud":"api",
             "exp":1735689600,"iat":1735686000,"jti":"a1b2","scope":"orders:read"}
```

**base64url — это кодирование, а не шифрование.** Payload читает кто угодно; секреты
в него класть нельзя. Подпись гарантирует лишь то, что содержимое не подменили.

## Claim'ы: зачем каждый и от чего защищает

Подпись доказывает только одно: **токен не подделали**. Она не отвечает на вопросы
«а этот токен вообще для меня?» и «он еще действует?». На них отвечают claim'ы, и каждый
закрывает свой класс атак.

| Claim | Что это | Что будет, если не проверить |
| --- | --- | --- |
| `iss` | кто выдал: URL сервера авторизации | примете токен чужого эмитента |
| `aud` | кому предназначен: идентификатор вашего API | примете токен, выданный для другого сервиса |
| `sub` | о ком токен: идентификатор пользователя | не поймете, чей это токен |
| `exp` | до какого момента действителен | токен становится вечным паролем |
| `nbf` | не раньше какого момента | токен «из будущего» сработает раньше времени |
| `iat` | когда выдан | не отсечете подозрительно старые токены |
| `jti` | уникальный номер токена | нечем отозвать конкретный токен и нечем ловить повторы |

### `aud` — от чего защищает

Это самый недооцененный claim. Токен — **предъявительский**: кто его держит, тот и
пользователь. А значит, сервис, которому вы дали токен, может пойти с ним в другой сервис.

```
  Пользователь ── токен (aud: "analytics") ──▶ сервис аналитики
                                                     │
                                                     │  берет ТОТ ЖЕ токен
                                                     ▼
                                              платежный API
                                              ├─ проверяет aud → "analytics" ≠ "payments" → 401 ✅
                                              └─ не проверяет  → выполняет платеж от лица
                                                                 пользователя            ❌
```

Классическая иллюстрация того же — **`id_token` вместо access-токена**: у него `aud` равен
`client_id` приложения, а не имени API. Если API не смотрит на `aud`, оно примет токен,
который вообще не предназначался для доступа к данным.

### `iss` — от чего защищает

Подпись проверяется ключом из JWKS, а **какой JWKS брать — определяет как раз `iss`**.
Если эмитентов несколько (свой сервер, Google, партнер, отдельный issuer на каждого
тенанта), то без проверки `iss` токен, честно подписанный «соседним» эмитентом, пройдет
проверку подписи и попадет к вам как валидный.

Правило: `iss` сверяется со **строкой из конфига**, а не «раз в токене написано, туда
и пойдем за ключами» — иначе атакующий укажет `iss` на свой сервер со своим JWKS
и подпишет что угодно.

### `sub` — что это на самом деле

`sub` — идентификатор субъекта **в пространстве имен своего эмитента**.
Отсюда два практических следствия:

- уникален не сам `sub`, а пара **`iss` + `sub`**: `user-123` от вашего auth-сервера
  и `user-123` от партнера — разные люди;
- в базе связываем аккаунт именно с `sub`, а не с email или логином: почту пользователь
  сменит, а `sub` остается. Для сервисных токенов (client credentials) в `sub` обычно
  лежит идентификатор клиента, а не человека.

### Прочитали `sub` — где взять профиль пользователя

Токен намеренно содержит **идентификатор, а не анкету**. Дальше есть четыре варианта,
и выбирают их по тому, чьи это данные и как часто они меняются.

| Откуда | Как | Когда уместно |
| --- | --- | --- |
| **`/userinfo`** сервера авторизации | `GET /userinfo` с access-токеном → `{sub, email, name, ...}` | профиль живет в IdP, нужны email/имя |
| **`id_token`** | пришел при логине, парсим на клиенте | нужен минимум и только в момент входа |
| **Claims в access-токене** | `email`, `roles` кладет сам auth server | данные редко меняются, лишний запрос дорог |
| **Свой сервис пользователей (IAM)** | `GET /users/by-external-id?iss=..&sub=..` | нужны бизнес-атрибуты: роли, тариф, лимиты, настройки |

На практике в проде обычно **четвертый вариант плюс первый**: при первом входе сервис
создает у себя запись (`provisioning`), связывая ее с парой `iss` + `sub`, и дальше живет
со своим внутренним `user_id`. В IdP лежит «кто это», в вашей базе — «что ему можно
и как он настроил продукт».

```
  запрос ──▶ gateway: проверил подпись, exp, aud → в контекст sub + scope
                │
                ├─ сервису достаточно sub (например, «мои заказы») → в БД по user_id
                │
                └─ нужен профиль → user-service/IAM по (iss, sub), результат В КЭШ
                                    └─ /userinfo дергаем только если профиль в IdP
```

Что важно не сделать:

- **ходить в IAM на каждый запрос** — профиль меняется редко, кэш на минуты обязателен,
  инвалидация по событию «профиль изменен»;
- **затащить весь профиль в токен** — токен растет, летит в каждом запросе, PII оседает
  в логах и у клиента, а данные все равно протухают только по `exp`;
- **использовать email как ключ** — он меняется; ключ это `iss` + `sub`.

Отдельно про права: грубые (`scope`, роль) удобно держать **в токене** — проверка бесплатна;
тонкие («владелец ли он этого заказа») все равно проверяются на месте по данным сервиса,
потому что в момент выдачи токена этого никто не знал.

## Алгоритмы подписи

| alg | Тип | Когда |
| --- | --- | --- |
| `HS256` | HMAC, **общий секрет** | эмитент и проверяющий — одна система |
| `RS256` / `PS256` | RSA, пара ключей | проверяющих много, приватный ключ только у эмитента |
| `ES256` | ECDSA P-256 | то же, но подпись и ключи короче — предпочтительнее RSA |
| `none` | — | **никогда**; существует только как источник уязвимостей |

Асимметричная схема — норма для OAuth: подписывает **только** сервер авторизации, своим
приватным ключом; проверить подпись может кто угодно публичным ключом. Приватный ключ
никуда не уезжает, а публичный не секрет — его можно спокойно раздавать.

## JWKS и `kid`: откуда сервис берет публичный ключ

Публичный ключ можно было бы положить каждому сервису в конфиг, но тогда смена ключа =
выкатка всех сервисов разом. Поэтому сервер авторизации **публикует свои публичные ключи
по HTTP** — это и есть **JWKS** (JSON Web Key Set), обычный JSON по адресу вида
`https://auth.example.com/.well-known/jwks.json`:

```json
{ "keys": [
  { "kid": "2024-01", "kty": "RSA", "alg": "RS256", "use": "sig", "n": "0vx7ag...", "e": "AQAB" },
  { "kid": "2024-07", "kty": "RSA", "alg": "RS256", "use": "sig", "n": "mF9pQ2...", "e": "AQAB" }
]}
```

Ключей в наборе обычно несколько. Какой из них нужен для конкретного токена, говорит
поле **`kid`** (key id) в заголовке токена — это просто метка, одинаковая в токене и в JWKS:

```
   токен:  header {"alg":"RS256","kid":"2024-07"}  ──┐
                                                     │  ищем ключ с таким же kid
   JWKS:   [ {"kid":"2024-01", ...},                 │
             {"kid":"2024-07", ...} ] ◀──────────────┘  им и проверяем подпись
```

**Ротация без простоя** работает так:

```
 1. auth server генерит новую пару и добавляет публичный ключ в JWKS
    → в наборе ДВА ключа: старый 2024-01 и новый 2024-07
 2. новые токены подписываются новым ключом (kid=2024-07),
    выданные ранее токены с kid=2024-01 еще живы до своего exp
 3. сервисы, увидев незнакомый kid, перечитывают JWKS и находят новый ключ
    — перезапуск и выкатка не нужны никому
 4. когда истекли последние старые токены, ключ 2024-01 убирают из JWKS
```

Практика на стороне проверяющего:

- JWKS **кэшируется** (минуты–часы), а не запрашивается на каждый токен;
- незнакомый `kid` → однократное обновление кэша **с ограничением частоты**: иначе поток
  токенов с мусорным `kid` превращается в DoS на сервер авторизации;
- ключ так и не нашелся → `401`, а не «ну и ладно, проверим чем есть»;
- адрес JWKS не хардкодят, а берут из discovery-документа
  `/.well-known/openid-configuration` (поле `jwks_uri`).

С `HS256` всего этого нет: секрет общий, и его смена — это согласованная выкатка всех,
кто им пользуется. Поэтому для нескольких сервисов берут асимметричный алгоритм.

## Как правильно проверять

```
 1. разобрать header, взять kid
 2. взять ключ из JWKS по kid  (кэш + обновление; неизвестный kid → 401, не «доверять»)
 3. проверить, что alg — из СПИСКА РАЗРЕШЕННЫХ (жестко заданного в коде!)
 4. проверить подпись
 5. exp / nbf  (с небольшим допуском на рассинхрон часов)
 6. iss — тот ли эмитент
 7. aud — токен выдан ИМЕННО этому API
 8. scope / roles — хватает ли прав на операцию
```

Пункты 3 и 7 пропускают чаще всего — и именно они ловят две классические атаки.

## Атаки и типовые ошибки

- **`alg: none`** — библиотека принимает токен без подписи. Лечится белым списком алгоритмов;
- **подмена алгоритма RS256 → HS256**: атакующий берет **публичный** ключ (он всем доступен)
  и подписывает им токен как HMAC-секретом. Если код доверяет полю `alg` из токена — проходит.
  Ожидаемый алгоритм задается в коде, а не берется из заголовка;
- **не проверен `aud`/`iss`** — токен, выданный для другого сервиса, принимается вашим;
- **слабый HMAC-секрет** — подбирается офлайн (hashcat), для HS256 нужны 256 бит случайности;
- **нет `exp`** — вечный токен;
- **инъекция через `kid`** — путь к файлу или SQL в `kid`, если по нему лезут в ФС или базу;
- **чувствительные данные в payload** — виден всем;
- **отзыв**: JWT нельзя «погасить» по определению — он валиден до `exp`. Отсюда:
  короткий TTL access-токена (5–15 минут) + refresh-токен, а для срочных случаев —
  denylist по `jti` (что возвращает поход в хранилище — цена компромисса).

## Где хранить в браузере

| Место | Риск |
| --- | --- |
| `localStorage` | любой XSS уносит токен; JS-доступ — главный минус |
| cookie `HttpOnly; Secure; SameSite=Lax/Strict` | JS не читает, но нужна защита от CSRF (SameSite + токен формы) |
| в памяти вкладки | пропадает при перезагрузке — обычно так держат access, а refresh кладут в cookie |

Практика для SPA: **access-токен в памяти, refresh — в `HttpOnly`-cookie с ротацией**.

## JWT или серверная сессия

| | Сессия (cookie + хранилище) | JWT |
| --- | --- | --- |
| Проверка | поход в Redis/БД | локально, по подписи |
| Отзыв | мгновенно | только по `exp` или denylist |
| Масштабирование | нужно общее хранилище | ничего не нужно |
| Размер | id ~30 байт | 300–1000 байт в каждом запросе |
| Данные | на сервере | видны клиенту |

Монолит с одной базой — берите сессии, это проще и отзывается мгновенно.
Много независимых сервисов и внешние клиенты — JWT.

## В Go

```go
// golang-jwt/jwt/v5: ожидаемый алгоритм задаем явно, aud и iss проверяем
tok, err := jwt.ParseWithClaims(raw, &jwt.RegisteredClaims{},
    func(t *jwt.Token) (any, error) { return publicKey, nil },
    jwt.WithValidMethods([]string{"RS256"}),   // защита от alg confusion
    jwt.WithAudience("orders-api"),
    jwt.WithIssuer("https://auth.example.com"),
    jwt.WithLeeway(30*time.Second),            // допуск на часы
)
```

Для JWKS с кэшем и ротацией удобнее `github.com/lestrrat-go/jwx/v2/jwk` или `go-oidc`.
