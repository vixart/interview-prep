# TLS/SSL

**TLS** · [JWT](jwt.md) · [OAuth 2.0](oauth.md)

Что защищает канал: шифрование, целостность и ответ на вопрос «тот ли это сервер».
Место темы среди соседних:

```
        ┌──────────────────────────────────────────────────────────┐
  TLS   │ защищает КАНАЛ: шифрование, целостность, кто такой сервер │
        └──────────────────────────────────────────────────────────┘
        ┌──────────────────────────────────────────────────────────┐
 OAuth  │ ПРОТОКОЛ выдачи доступа: как клиент получил токен         │
        └──────────────────────────────────────────────────────────┘
        ┌──────────────────────────────────────────────────────────┐
  JWT   │ ФОРМАТ токена: что внутри и как проверить подпись         │
        └──────────────────────────────────────────────────────────┘
```

TLS — транспорт, OAuth — процесс, JWT — структура данных. Они независимы: OAuth может
выдавать непрозрачные (opaque) токены без JWT, JWT бывает без OAuth, а TLS нужен всем.

## TLS/SSL

### Терминология и версии

**SSL** — старое название протокола (Netscape, 1994–1996), **TLS** — то же самое после
передачи в IETF. «SSL-сертификат» — исторический термин, технически это X.509-сертификат
для TLS.

| Версия | Статус |
| --- | --- |
| SSL 2.0 / 3.0 | сломаны (POODLE), запрещены |
| TLS 1.0 / 1.1 | deprecated с 2021 (RFC 8996), выключать |
| **TLS 1.2** | рабочий минимум, если нужна совместимость |
| **TLS 1.3** | текущий стандарт (RFC 8446, 2018): быстрее и безопаснее по умолчанию |

Что дает TLS: **конфиденциальность** (шифрование), **целостность** (данные не подменили),
**аутентификация сервера** (и опционально клиента). Чего не дает: авторизации, защиты
от уязвимостей приложения и от вредоносного сервера с валидным сертификатом.

### Из чего собран

- **асимметричная криптография** (RSA, ECDSA) — только для аутентификации сервера и обмена
  ключами; она медленная, данными по ней не гоняют;
- **обмен ключами** (ECDHE) — стороны получают общий секрет, не передавая его по сети;
- **симметричное шифрование** (AES-GCM, ChaCha20-Poly1305) — весь трафик после рукопожатия;
- **AEAD** — шифрование и проверка целостности одной операцией (в TLS 1.3 только AEAD).

### Рукопожатие TLS 1.2 — два круга (2 RTT)

```
   Клиент                                              Сервер
      │                                                   │
      │ ── ClientHello ──────────────────────────────────▶│  версии, шифронаборы,
      │    (random_c, cipher suites, SNI, ALPN)           │  какой хост нужен (SNI)
      │                                                   │
      │ ◀───────────────────────────── ServerHello ───────│  выбранный шифронабор
      │ ◀───────────────────────────── Certificate ───────│  цепочка сертификатов
      │ ◀───────────────────────── ServerKeyExchange ─────│  параметры ECDHE + подпись
      │ ◀───────────────────────── ServerHelloDone ───────│
      │                                                   │
      │  проверяет цепочку, срок, hostname, подпись       │
      │                                                   │
      │ ── ClientKeyExchange ────────────────────────────▶│  своя часть ECDHE
      │ ── ChangeCipherSpec, Finished ───────────────────▶│  дальше все зашифровано
      │ ◀──────────────── ChangeCipherSpec, Finished ─────│
      │                                                   │
      │ ═══════════ прикладные данные (AES-GCM) ═════════ │
```

Из общего секрета (pre-master) и двух random'ов выводится master secret, из него —
ключи шифрования и MAC для каждой стороны.

### Рукопожатие TLS 1.3 — один круг (1 RTT)

```
   Клиент                                              Сервер
      │ ── ClientHello + key_share ──────────────────────▶│  клиент СРАЗУ шлет свою
      │    (сразу угадывает группу ECDHE)                 │  часть ключа
      │                                                   │
      │ ◀── ServerHello + key_share ──────────────────────│  общий секрет готов
      │ ◀── {EncryptedExtensions, Certificate,            │  все, что дальше, уже
      │      CertificateVerify, Finished} ────────────────│  зашифровано
      │ ── Finished + данные ────────────────────────────▶│
```

Что изменилось в 1.3:

- **всегда forward secrecy**: RSA key transport и статический DH выброшены, только ECDHE;
- вырезаны слабые примитивы: RC4, 3DES, CBC, SHA-1, сжатие, renegotiation, кастомные группы;
- сертификат сервера передается **в зашифрованном** виде;
- **0-RTT**: при повторном подключении данные летят вместе с первым пакетом, но их можно
  **переиграть (replay)** — только для идемпотентных запросов, никогда для «списать деньги».

**Forward secrecy**: ключи сессии эфемерные, поэтому утечка приватного ключа сервера завтра
не расшифрует записанный сегодня трафик. Ради этого 1.3 и выкинул RSA-обмен ключами.

### Что еще происходит в рукопожатии

- **SNI** — имя хоста открытым текстом в ClientHello: так один IP держит сотни сайтов.
  Скрывает его только ECH (Encrypted Client Hello), пока не везде;
- **ALPN** — согласование протокола: `h2`, `http/1.1`, `h3`;
- **возобновление сессии**: session ticket / PSK в 1.3 — пропускаем полное рукопожатие;
- **mTLS** — сервер тоже требует сертификат клиента. Типично для service-to-service
  и zero-trust: клиента опознают по сертификату, а не по паролю или токену.

### Частые ошибки

- `InsecureSkipVerify: true` в Go — выключает проверку сертификата целиком, то есть весь
  смысл TLS. Если нужен свой CA — кладите его в `RootCAs`, а не отключайте проверку;
- **не отдана промежуточная цепочка**: в браузере работает (он дотягивает по AIA),
  а `curl`, Go и мобильные клиенты падают. Сервер обязан отдавать leaf + intermediates;
- протух сертификат — самая частая авария на проде; лечится автоматизацией (ACME) и алертом
  за 30 дней;
- разрешены старые версии и слабые шифронаборы → downgrade-атаки; ставьте `MinVersion: TLS 1.2`;
- нет **HSTS** — пользователь может остаться на http и словить MITM на первом заходе;
- терминация TLS на балансировщике, а дальше по внутренней сети открытым текстом — если сеть
  не доверенная, это дыра.

### В Go

```go
// клиент: свой CA, минимальная версия, без InsecureSkipVerify
tr := &http.Transport{TLSClientConfig: &tls.Config{
    MinVersion: tls.VersionTLS12,
    RootCAs:    pool,          // x509.NewCertPool() + AppendCertsFromPEM
}}
client := &http.Client{Transport: tr, Timeout: 30 * time.Second}

// сервер
srv := &http.Server{Addr: ":443", TLSConfig: &tls.Config{MinVersion: tls.VersionTLS12}}
srv.ListenAndServeTLS("cert.pem", "key.pem") // cert.pem = leaf + intermediates

// mTLS на сервере
cfg.ClientAuth = tls.RequireAndVerifyClientCert
cfg.ClientCAs  = clientPool
```

## Сертификаты и цепочка доверия

Сертификат X.509 связывает **имя** (домен) с **открытым ключом** и подписан удостоверяющим
центром. Доверие строится цепочкой до корня, который уже лежит в системном хранилище.

```
   Root CA  (самоподписанный, в хранилище ОС/браузера)
      │  подписывает
      ▼
   Intermediate CA  (его отдает сервер вместе со своим)
      │  подписывает
      ▼
   Leaf: CN/SAN = api.example.com, публичный ключ, срок действия
```

Что проверяет клиент:

1. подпись каждого звена цепочки и то, что корень — доверенный;
2. срок действия (`notBefore` / `notAfter`);
3. **имя хоста против SAN** (поле CN устарело и игнорируется современными клиентами);
4. назначение ключа (`KeyUsage`, `ExtendedKeyUsage: serverAuth`);
5. отзыв: **CRL** (списки), **OCSP** (запрос к CA), **OCSP stapling** (сервер сам приносит
   свежий ответ CA — быстрее и приватнее). На практике браузеры к отзыву относятся мягко.

Мелочи, которые спрашивают:

- **wildcard** `*.example.com` покрывает `api.example.com`, но **не** `a.b.example.com`
  и не сам `example.com`;
- **самоподписанный** сертификат = нет цепочки доверия, годится только для внутренних систем
  со своим CA в хранилище;
- **Let's Encrypt / ACME**: бесплатно, срок 90 дней, обновление автоматическое
  (в Go — `golang.org/x/crypto/acme/autocert`);
- **pinning** (прибить конкретный ключ в клиенте) защищает от скомпрометированного CA,
  но ломает ротацию — в вебе от него отказались, в мобильных приложениях встречается;
- приватный ключ **никогда** не покидает сервер и не лежит в репозитории.

## Шпаргалка

| Вопрос | Ответ в одну строку |
| --- | --- |
| Чем SSL отличается от TLS | это одно и то же, SSL — старое имя; живые версии — TLS 1.2 и 1.3 |
| Зачем в TLS и асимметрика, и симметрика | асимметрика медленная: ею только аутентифицируют и договариваются о ключе, дальше AES/ChaCha |
| Что такое forward secrecy | эфемерный ECDHE: утечка ключа сервера не расшифрует записанный ранее трафик |
| Чем 1.3 лучше 1.2 | 1 RTT вместо 2, только AEAD и ECDHE, сертификат шифруется, слабые примитивы вырезаны |
| Чем опасен 0-RTT | ранние данные можно переиграть (replay) — только для идемпотентных запросов |
| Как проверяется сертификат | цепочка до доверенного корня, срок, hostname против SAN, назначение ключа, отзыв |
| В браузере работает, в Go нет | сервер не отдает промежуточные сертификаты; браузер их дотягивает сам, Go — нет |
| Что такое mTLS | сервер тоже проверяет сертификат клиента; типично для service-to-service |
