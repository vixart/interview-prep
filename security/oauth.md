# OAuth 2.0 и OIDC

[TLS](tls.md) · [JWT](jwt.md) · **OAuth 2.0**

Протокол выдачи доступа: как приложение законно получает токен от имени пользователя.
Сам токен чаще всего в формате [JWT](jwt.md), а канал защищает [TLS](tls.md).

---

## OAuth 2.0

**OAuth 2.0 (RFC 6749) — это делегирование доступа, а не аутентификация.** Он отвечает на
вопрос «можно ли этому приложению читать мои заказы», а не «кто этот пользователь».
Для второго есть OIDC — надстройка над OAuth ([ниже](#oidc-openid-connect)). Фраза «войти через Google» —
это уже OIDC, хотя все говорят «OAuth».

### Четыре роли

| Роль | Кто это |
| --- | --- |
| **Resource owner** | пользователь, чьи данные |
| **Client** | приложение, которому нужен доступ |
| **Authorization server** | выдает токены (Keycloak, Auth0, Google, свой) |
| **Resource server** | API, которое проверяет токен и отдает данные |

Клиенты делятся на **confidential** (бэкенд, умеет хранить секрет) и **public** (SPA,
мобильное, CLI — секрет спрятать негде, поэтому обязателен PKCE).

### Какой flow выбирать

| Grant | Когда | Статус |
| --- | --- | --- |
| **Authorization Code + PKCE** | веб, SPA, мобильные — всё, где есть пользователь | **дефолт** |
| **Client Credentials** | сервис к сервису, пользователя нет | норма |
| **Device Code** | телевизор, CLI, устройство без браузера | норма |
| **Refresh Token** | обновление access-токена | норма (с ротацией) |
| Implicit | токен приходил прямо в URL | **выпилен** в OAuth 2.1 |
| Password (ROPC) | приложение собирает логин/пароль само | **выпилен** |

Implicit и ROPC — готовый вопрос «почему их убрали»: токен в URL утекает в историю, логи
и Referer; ROPC заставляет пользователя отдавать пароль стороннему приложению и несовместим
с MFA.

### Authorization Code + PKCE

```
 Пользователь        Клиент (SPA/бэкенд)      Auth Server            API (resource server)
      │                     │                      │                        │
      │  «войти»            │                      │                        │
      │────────────────────▶│                      │                        │
      │                     │ 1. генерит code_verifier (случайные 43+ симв.)│
      │                     │    code_challenge = BASE64URL(SHA256(verifier))
      │                     │                      │                        │
      │ 2. редирект на /authorize?response_type=code&client_id&redirect_uri │
      │    &scope=orders:read&state=xyz&code_challenge=...&method=S256      │
      │◀────────────────────│                      │                        │
      │──────────────────────────────────────────▶ │                        │
      │ 3. логин + согласие (это происходит НА auth server, клиент          │
      │    пароля не видит)                        │                        │
      │◀────────────────────────────────────────── │                        │
      │ 4. редирект обратно: ?code=SplxlO&state=xyz │                        │
      │────────────────────▶│                      │                        │
      │                     │ 5. проверяет state == свой                    │
      │                     │ 6. POST /token: code + code_verifier          │
      │                     │    (+ client_secret, если confidential)       │
      │                     │─────────────────────▶│                        │
      │                     │                      │ сверяет SHA256(verifier)
      │                     │                      │ с сохраненным challenge│
      │                     │◀─────────────────────│                        │
      │                     │ 7. access_token (+ refresh_token, id_token)   │
      │                     │                      │                        │
      │                     │ 8. GET /orders  Authorization: Bearer <access>│
      │                     │──────────────────────────────────────────────▶│
      │                     │                      │  проверяет подпись/    │
      │                     │                      │  introspection, aud,   │
      │                     │◀──────────────────────  scope, exp            │
```

Зачем каждый защитный элемент:

- **`state`** — CSRF: злоумышленник не сможет подсунуть свой `code` в ваш сеанс, потому что
  не знает случайный `state`, который клиент сам сгенерировал и проверит;
- **PKCE** (RFC 7636) — перехват `code`: код летит через редирект и может быть перехвачен
  (особенно на мобильных, где redirect_uri — кастомная схема). Без `code_verifier`,
  который остался у клиента, перехваченный код бесполезен. В OAuth 2.1 обязателен для всех;
- **точное совпадение `redirect_uri`** — иначе код уедет на сайт атакующего;
  никаких wildcard'ов и открытых редиректов;
- **обмен кода на токен идет с бэкенда** (или как минимум по HTTPS с PKCE) — код одноразовый
  и короткоживущий (~60 секунд).

### Три токена — не путать

| Токен | Кому предъявляют | Формат | Жизнь |
| --- | --- | --- | --- |
| **access** | API (`Authorization: Bearer`) | JWT или opaque | минуты |
| **refresh** | только auth server | opaque | дни–месяцы, **с ротацией** |
| **id_token** (OIDC) | сам клиент, чтобы узнать, кто вошел | всегда JWT | минуты |

**id_token нельзя использовать как access-токен** — у него другая аудитория (`aud` = client_id),
и API его принимать не должно. Это самая частая ошибка новичков в OIDC.

**Ротация refresh-токена**: при каждом обновлении выдается новый refresh, старый гасится.
Если старый предъявили снова — значит его украли, вся цепочка отзывается.

### Как resource server проверяет access-токен

- **JWT** — локально: подпись по JWKS, `iss`, `aud`, `exp`, `scope`. Быстро, но отзыв
  не мгновенный;
- **opaque** — запрос `POST /introspect` (RFC 7662) к auth server: `{"active": true, ...}`.
  Мгновенный отзыв ценой сетевого вызова на каждый запрос (лечится коротким кэшем).

Гибрид на практике: JWT + короткий TTL + интроспекция для критичных операций.

### Частые ошибки

- **OAuth вместо аутентификации**: «есть access-токен → это точно тот пользователь» — нет,
  токен могли выдать другому приложению. Личность подтверждает `id_token` (OIDC) или `/userinfo`;
- нет проверки `state` → CSRF на логине;
- wildcard в `redirect_uri` или открытый редирект на своем домене;
- refresh-токен в `localStorage` вместо `HttpOnly`-cookie;
- слишком широкие scope: просят `admin`, когда нужен `orders:read`;
- токены в query-параметрах (попадают в логи и Referer) вместо заголовка;
- нет ротации refresh и нет отзыва при выходе.

### В Go

```go
cfg := &oauth2.Config{
    ClientID: id, ClientSecret: secret,
    Endpoint: google.Endpoint,              // или oidc-провайдер через discovery
    RedirectURL: "https://app.example.com/callback",
    Scopes: []string{"openid", "email"},
}
verifier := oauth2.GenerateVerifier()       // PKCE
url := cfg.AuthCodeURL(state, oauth2.S256ChallengeOption(verifier))
// после редиректа: сверить state, затем
tok, err := cfg.Exchange(ctx, code, oauth2.VerifierOption(verifier))
client := cfg.Client(ctx, tok)              // сам обновит по refresh
```

## OIDC (OpenID Connect)

Тонкий слой поверх OAuth 2.0, добавляющий **аутентификацию**:

- scope `openid` в запросе → в ответе появляется **`id_token`** (JWT с `sub`, `iss`, `aud`,
  `exp`, `nonce`, при желании `email`, `name`);
- **`nonce`** — клиент кладет случайное значение в запрос и сверяет его в `id_token`:
  защита от повторного использования чужого токена;
- **`/userinfo`** — эндпоинт с профилем по access-токену;
- **discovery**: `GET /.well-known/openid-configuration` отдает все URL'ы и адрес JWKS —
  ничего не хардкодим.

Проверка `id_token`: подпись по JWKS, `iss`, `aud == client_id`, `exp`, `nonce`.

## Как это собирается вместе

```
   Браузер                     Ваш бэкенд                Auth Server          API
      │                            │                          │                │
      │══ TLS 1.3 ════════════════▶│══ TLS ══════════════════▶│                │
      │   (канал защищен: шифр,    │   OAuth: получили         │                │
      │    целостность, сервер     │   access + refresh        │                │
      │    аутентифицирован)       │                           │                │
      │                            │══ TLS + Bearer <JWT> ═════════════════════▶│
      │                            │                                     проверка
      │                            │                                     подписи по
      │                            │                                     JWKS, aud,
      │                            │                                     scope, exp
```

- **TLS** отвечает за то, что токен не подсмотрят и не подменят в пути;
- **OAuth** — за то, как клиент этот токен законно получил;
- **JWT** — за то, что API может проверить токен сам, без похода к эмитенту.

Уберите TLS — и всё остальное бессмысленно: bearer-токен работает как пароль,
кто его перехватил, тот и пользователь.

## Шпаргалка

| Вопрос | Ответ в одну строку |
| --- | --- |
| OAuth — это аутентификация? | нет, авторизация (делегирование доступа); аутентификация — OIDC и `id_token` |
| Зачем `state` | защита от CSRF на этапе редиректа обратно в приложение |
| Зачем PKCE | перехваченный `code` бесполезен без `code_verifier`; в OAuth 2.1 обязателен всем |
| Почему выпилили implicit | токен приходил в URL: история, логи, Referer |
| access vs refresh vs id_token | к API / только к auth server за новой парой / клиенту, чтобы узнать пользователя |
| Как API проверяет токен | JWT — подпись по JWKS + `iss`/`aud`/`exp`/`scope`; opaque — интроспекция |
| Что делать при утечке refresh-токена | ротация уже сработала: повтор старого токена гасит всю цепочку |
